# 03 — Data model and storage

> Round 2 design. Decisions: TD-005 (event store), TD-006 (PostgreSQL 18), TD-007 (transcripts as partitioned rows), TD-011 (Drizzle), TD-012 (redaction). Evidence: research/07, research/06.

## Principles
- **PostgreSQL 18 is the only database.** Events, state, transcripts, cost, audit, KB indexes, jobs — one backup, one restore, one `DATABASE_URL`.
- **Append-only where the audit demands it** (`events`, `run_messages`, `cost_entries`, `integration_actions`, `config_audit`, `redaction_log`): `REVOKE UPDATE, DELETE` from the application role; partition by month; purge only by dropping partitions and only when the operator configures a retention window (default: never — Q13).
- **Typed columns for anything filtered or aggregated; JSONB only for opaque payloads.** Never keep mutable status or counters inside a large JSONB document (TOAST rewrite cost).
- **`uuidv7()` primary keys** (time-ordered, PG 18 built-in) on all entity tables.
- **Derived data is rebuildable** (KB index rows, code maps, rollups) and carries the commit/model/price-list version it was built from.

## Schema (logical; DDL written by the implementer with Drizzle + hand-written SQL migrations for partitions, GIN, generated columns)

### Identity and configuration
- `organizations(id, name, timezone, settings jsonb, created_at, updated_at)` — one row.
- `users(id, email unique, name, role enum(admin|maintainer|member|viewer), password_hash nullable, status, created_at)`; `sessions(id, user_id, expires_at, …)`.
- `user_identities(user_id, provider, external_id, email, display_name)` — PK `(provider, external_id)`.
- `projects(id, org_id, key unique, name, repo_url, default_branch, agentic_dir, knowledge_dir, config jsonb, config_source jsonb, config_hash, autonomy_level, autonomy_policies jsonb, readiness_level, status, created_at, updated_at)` — `autonomy_policies` is the materialised preset with its version (migration 0021, WP-30, BD-027:14); `null` means never materialised.
- `project_members(project_id, user_id, role)`.
- `integrations(id, org_id, type, provider, name, config jsonb, secret_ids uuid[], health jsonb, created_at, updated_at)`; `bindings(id, project_id, integration_id, config jsonb)`.
- `secrets(id, ciphertext bytea, key_id, created_at, rotated_at)` — encrypted with `APP_SECRET_KEY` (envelope); never joined into API responses. **One row is one credential**, and its plaintext is the JSON document `{"field", "value"}` — the provider config field the value belongs to travels *with* it, because `integrations.secret_ids` is a `uuid[]` with no names in it and an operator reordering that array must not be able to swap a webhook secret for an API token (WP-15a, `packages/infrastructure/src/secrets/postgres-secret-store.ts`). The envelope is a per-row AES-256-GCM data key wrapped under a key derived from `APP_SECRET_KEY` by HKDF; `key_id` is a fingerprint of the *derived* key, so a half-finished rotation is a readable state rather than a corrupt one, and a row sealed under another key is refused by name rather than reported as a bad tag.
- `config_audit(id, entity_type, entity_id, user_id, diff jsonb, created_at)` — append-only; secret values appear as `"changed"`.

### Pipeline
- `tasks(id, project_id, ticket_provider, ticket_key, ticket_url, template, mode enum(normal|shadow), state, current_stage, size, priority, requested_by_user_id, requested_by_identity jsonb, template_snapshot jsonb, ticket_snapshot jsonb, ticket_snapshot_at, ticket_signal_at, config_snapshot_hash, mr_head_at, branch, mr_ref jsonb, workpad_ref jsonb, iteration_counters jsonb, stage_attempts jsonb, iteration_limits jsonb, review_subject jsonb, cost_actual numeric(12,6), estimate_usd numeric(12,6), estimate_basis, estimate_samples, risk_classes text[], blocked_by text[], version int, created_at, updated_at, completed_at)` — idx `(project_id, state)`, `(project_id, created_at)`, `UNIQUE(project_id, ticket_key, mode)`. **Amended at WP-15f (migration 0015):** `ticket_snapshot`/`ticket_snapshot_at` are new. `ticket_snapshot` is the ticket's own title, description and newest comments — **untrusted stored external text** (BD-022), like `inbox.payload` and `kb_chunks`, and the third place the platform keeps somebody else's words. It is written **redacted** through the binding's redactor — TD-012 step 1 *and* step 2, the same pair `inbox` gets — with a `redaction_count` inside the document and **bounded at the write**, because the store is the consumer (Q54): title 512 characters, description 20 000, the newest 20 comments at 1 000 each, with `truncated` and `comment_count` declaring what was cut — one unbounded `readTicket` was measured at 53 284 565 bytes. It is read once at intake and again at a stage that finds none — **and, since WP-60 (migration 0044), at a stage that finds it older than `ticket_signal_at`**, the receipt time of the newest `ticket.updated` for the ticket, written only by `TaskRepository.recordTicketSignal` (forward only, on every live task of the ticket, no version bump) and never by the insert; both writers of `ticket_snapshot_at` stamp the read's **start**, so an edit announced during a read is dated after it (Q61 (b)) — is readable by anyone who can read the task, and **dies with the task** by the row it sits on; `null` means *the platform has not read this ticket* and is never how a ticket with an empty description is spelled. `ticket_snapshot_at` is a column rather than a field so "which tasks are running on an old snapshot" is a query, and `tasks_ticket_snapshot_at_paired` keeps the two null together. **Amended at WP-47 (migration 0035):** `cost_estimated` is **dropped**. It was `not null default 0` from migration 0004, published on the task DTO as `cost_estimated_usd`, and written by **nothing** — so every task the product ever served reported `$0.00` of estimated spend, which is standing rule 16 one layer out: *"nobody counted"* served as *"nothing was estimated"*. The field is now a **projection** over `cost_entries where is_estimate` (`apps/server/src/queries/pipeline-queries.ts`), because `cost_entries.is_estimate` has carried the per-row flag since WP-19: no fourth running total to keep in step, no backfill for tasks that already exist, and no new writer to add to this row's column partition. A task with one priced run and one reported run therefore publishes the **priced** amount and not the sum, which is what the field's own definition says and what the column never could. **Amended at WP-15e (migration 0019):** `version` is the row's optimistic-concurrency token, and it exists because a whole-row write is correct only while nothing else writes the row — a fact about the callers, which WP-15d falsified by moving a provider call into a job. `TaskRepository.save` writes `… , version = version + 1 where id = $1 and version = $n`, so a write over a row another transaction has moved is **refused** rather than silently winning. **Amended at WP-59 review round 1:** `save` is no longer the only writer of `version` — `TaskRepository.bumpVersion` moves it (with the bookkeeping `updated_at`) and **no column of the aggregate**, for a writer that appends to a task's stream from outside the task's own transactions (the conflict warning's pair, `recordRebaseCheck`): it bumps first, in sorted id order, which takes the row lock, so an owner that loaded before it meets the retried `TaskConcurrentModificationError` at its `save` rather than an unretried `StreamConflictError` at its append; the column-ownership census lists `version` as a deliberately shared column for that reason; the caller re-reads and decides again, bounded, and a task whose write loses every attempt is escalated to `needs_human` rather than dropped. The columns of this row are **partitioned by writer**: `save` writes the aggregate's own (`state`, `current_stage`, `branch`, `mr_ref`, `stage_attempts`, `iteration_counters`, `cost_actual`) and bumps `version`; `workpad_ref`, `ticket_snapshot`/`ticket_snapshot_at`, `ticket_signal_at` and `size`/`estimate_usd` each have exactly one narrow writer and are **not** named by `save`, so they neither cause nor suffer a false conflict. **Amended at WP-60:** `mr_ref` is the one column with **two** writers by decision — `save`, and `TaskRepository.saveMergeRequestHead`, which rewrites only its `head_sha` key (`jsonb_set`) when the provider announces a push the platform did not make (PROGRESS backlog 182) and **bumps `version` in the same statement**, so a `save` over a snapshot read before it is refused rather than putting the old revision back; the census names both statements by shape. It moves the head **forward only**: `mr_head_at` (migration 0044, its only writer) is the provider's `updated_at` of the recorded head, and a delivery stamped no later than it moves nothing — the CI gate asks the pipeline status of this head, and GitLab documents no delivery order (WP-60 review round 1). The partition is enforced off disk by `packages/infrastructure/src/pipeline/tasks-column-ownership.test.ts`, because it was a docblock claim that `save` had already falsified (it named `workpad_ref`, so the executor put back the `null` the workpad job had just filled in). **Residual, stated because an optimistic check is a claim about every writer of the row and is only true while every writer carries the token**: a *pre-WP-15e* process writes `where id = $1` with no predicate and does not bump `version`, so it wins silently **and** leaves the token unmoved — a concurrent new-process `save` then succeeds as well and one of the two updates is lost. No deployment shape in this build produces it: the image runs `migrate` and then `server` from one artefact, and two versions of this code never serve at once. A rolling deploy would have to close it (a `version`-bumping write in the old binary first, or a drain), which is why the sentence lives here and in `TaskRepository.save`'s docblock rather than in migration 0019 — an applied migration is never edited (TD-011).
- `task_stages(id, task_id, stage, attempt, state, entered_at, exited_at, outcome, return_reason, returned_to, caused_by_event_id)`. **Amended at WP-55 (migration 0040).** `state` has **one declared vocabulary**, `taskStageStateSchema` in `packages/contracts/src/pipeline.ts` — `pending | running | completed | returned | skipped | failed`, the words the task-detail DTO has published since WP-15h — which the store parses before writing, `apps/server` parses on the way out (an unknown word is an error, never a default) and `task_stages_state_known` holds the database to. Until then the store wrote `entered`/`exited` and the projection mapped them, publishing a returned stage as `completed`; 0040 rewrote every existing row (`entered` with no exit → `running`, a closed row → `returned`/`failed` by its `outcome`, otherwise `completed`). `running` is written on entry; `completed` by an agent stage with a verdict, a system stage and a **gate the pipeline settled and walked past** (its `outcome` is the gate verdict, `pass` or `fail` — before WP-55 no gate row was ever closed, measured); `returned` by the attempt that sent the task back; `failed` by an attempt that ended without a verdict and escalated. `pending` and `skipped` are **declared and unused**: a row exists only for a stage the task entered. `returned_to` is new: the stage a return targeted. The database enforces one direction — a non-null `returned_to` requires `state = 'returned'` (`task_stages_returned_to_is_a_return`); the other — every return written from WP-55 on names its target — is enforced by the store (`recordStageExited` refuses a return without one), not by the schema, because a `returned` row written before 0040 has a null target the migration could not recover. The return's `return_reason` stays on the attempt that produced it, and the next run's feedback is read by target — *the newest return naming this stage that closed after the stage's previous attempt (counted by its entry when that attempt is itself a return to this stage — a human return or rework at the stage the task is at) and no later than this attempt's entry* (`TaskRepository.lastReturnReason`). An agent verdict's return carries the verdict's own findings (`verdictReturnReason`: one line per finding, each opening with a platform tag; no cut of its own — the prompt block's `MAX_FEEDBACK_CHARS` cut is the only one, announced as `truncated="true"` on the marker), not the interpreter's literal `requested changes`; before WP-55 it was read off the entering stage's own rows, which on every shipped edge served a re-run stage its own last complaint. Both writes stamp `clock_timestamp()` rather than `now()` so rows one transaction writes are ordered.
- `runs(id, task_id, task_stage_id, project_id, role, mode, attempt, run_key, session_id, model, effort, permission_mode, provider_mode, prompt_version, system_prompt text, user_prompt text, settings_snapshot jsonb, settings_hash, allowed_tools text[], disallowed_tools text[], mcp_servers jsonb, skills text[], status, terminal_reason, exit_detail jsonb, started_at, ended_at, last_output_at, lease_owner, lease_expires_at, num_turns, input_tokens, output_tokens, cache_write_5m_tokens, cache_write_1h_tokens, cache_read_tokens, usd_reported numeric(12,6) null, usd_estimated numeric(12,6), price_list_id, wall_ms, redaction_count, context_budget_tokens int null, context_total_tokens int null, context_kb_commit null, created_at)` — idx `(task_id)`, `(project_id, started_at)`, `(status) WHERE status IN ('created','starting','running')` *(corrected at WP-03: `queued` is not a value of the `run_status` enum; the live index uses the three non-terminal states)*, `UNIQUE(run_key)` for memoisation. **Amended at WP-47 (migration 0035), which gave three of these columns their first writer.** `lease_owner`/`lease_expires_at` had **no reader and no writer** from 0004 until then; the process executing the run now claims the lease in the transaction that creates the row and renews it on a heartbeat inside the `stage.execute` job (`packages/application/src/pipeline/lease.ts`), and `packages/application/src/recovery/run-lease.ts` ends a run nothing is renewing — `run.failed` with the **new** terminal reason `lease_expired`, never `cancelled` and never `crash`, because a missing heartbeat licenses only *"no process is renewing this lease"* and says nothing about the session. The bound is **both**: the lease is the primary signal and `started_at + wallClockMs + grace` is the backstop for rows written before the column had a writer. `usd_estimated` becomes **nullable and loses its default**, exactly as `run_model_usage.usd_estimated` did at 0017 and for the same reason — `not null default 0` cannot say *"nobody priced this run"*, which a zero spells as a free run — and it too gains its first writer: `RunRepository.finish` writes the run's own figure there when the cost is an estimate (BD-004 `local` mode) and into `usd_reported` when it is not, so the pending term reads `coalesce(usd_reported, usd_estimated, 0)` and a `local`-mode run stops reading as free on `GET /api/runs/:id`. **Both columns null is a third answer** — *nobody measured this run* — and it is what the lease sweep leaves behind, with no `cost_entries` row written for it either. A run ended by somebody other than the process running it (a human's cancel, the sweep) gets its real cost later through the narrow `RunRepository.recordCost`, which refuses a live run, a row that already carries a figure and a run the ledger has already charged (Q70 (b)). **Amended again at WP-52 (migration 0038), which gave `system_prompt`, `user_prompt` and `redaction_count` their first writer.** All three had been unwritten since 0004 (Q64): the assembled prompt is stored **at run creation**, from the same `RunSpec` the runner is handed and never re-derived — the delimiter nonce is drawn per prompt and the context pack is a point-in-time read — through the run's own TD-012 redactor, with the replacements it made in those two columns on `redaction_count`. `redaction_count` **keeps** its `not null default 0`, deliberately: every row written before 0038 already reads `0` from that default, so dropping it could not repair the past, and the legible boundary is the column pair — `system_prompt is null` is exactly *"no WP-52 writer touched this row"*, and `system_prompt is not null and redaction_count = 0` is exactly *"the redactor ran over this run's prompts and replaced nothing"*. `GET /api/runs/:id/prompt` still answers **409 `prompt_not_recorded`** for a pre-0038 run, and that refusal is now a statement about the row rather than about the build. **Amended at WP-57 (migration 0041):** `context_budget_tokens`, `context_total_tokens` and `context_kb_commit` are the header of the run's context pack, written at creation beside the prompt; `run_context_pack` below says what they mean and what their nulls mean.
- `run_model_usage(run_id, model, input_tokens, output_tokens, cache_write_5m, cache_write_1h, cache_read, usd_estimated null, usd_reported null)` PK `(run_id, model)`. **Amended at WP-19 (migration 0017), which wrote the first row this table has ever held.** `usd_reported` is new and `usd_estimated` became nullable: the SDK's per-model `costUSD` is a *reported* number and storing it in a column named `usd_estimated` makes the two indistinguishable from one row, while `not null default 0` cannot say "the price table has no row for this model" — a real state (a model released after the operator's last price update) that a zero spells as a free run (standing rule 18). The pair is the one `runs` has carried since 0004, and `GET /api/runs/:id` reads it the same way: reported first, estimate second.
- `run_context_pack(run_id, tier smallint, source_path, reason, score double precision, tokens int, validated bool, kb_commit_sha, ordinal int)` PK `(run_id, source_path)`. **Amended at WP-57 (migration 0041), which wrote the first row this table has ever held** (PROGRESS backlog 31, option (a): keep the table). Until then nothing inserted into it and it could not have held the record if something had: `ContextPackRecord.budget_tokens` had no column, and `reason`/`score` were nullable where the published tier-1 entry requires them. Now: **(1) the pack's header lives on the run row** — `runs.context_budget_tokens`, `runs.context_total_tokens` and `runs.context_kb_commit`, written by the same `RunRepository.insert` that creates the row, in the transaction that commits the run (both `runs.insert` call sites — the stage executor and the ask executor — pass the `ContextPackRecord` their planner built, which is the record `run.started` carries). **`context_budget_tokens is null` is exactly *"no pack was recorded for this run"*** (a row written before 0041), and a non-null budget with **zero** rows is an **empty** pack — the two are what `GET /api/runs/:id/context-pack` tells apart (409 `context_pack_not_recorded` with the row count, or 200 with empty tiers). `runs_context_pack_header_paired` keeps the budget and the total null together. **(2) `reason` and `score` are filled at the write, not relaxed in `@platform/contracts`**: every tier-1 entry the assembler produces carries both, so the DTO keeps requiring them; a tier-0 row carries **neither** (the published tier-0 entry has no such fields, and its audit label — `index`, `rules`, `root_instructions`, `code_map` — is not a `context_pack_reason`). `run_context_pack_row_complete` (`NOT VALID`, so a row from before 0041 is exempt and still refused by the reader) requires an `ordinal` on every row and a `reason` and `score` on every tier-1 row. **(3) `ordinal` is the entry's position within its tier**, because the record is ordered (tier 1 by score, ties by path under JavaScript's `localeCompare`) and neither the primary key nor a database collation reproduces that order. **(4) `score` is `double precision`, not `real`**: the reader re-publishes the record, and a `real` rounds the planner's score, so the served record would differ from the one `run.started` carries in the seventh digit. A tier-1 entry recorded `validated: false` is a row too — the audit of technical/07 step 3 — and it is **not** counted in `context_total_tokens`, exactly as the assembler does not count it.
- `artifacts(id, task_id, type, version int, markdown text, data jsonb, schema_version, produced_by_run_id, redaction_count null, created_at)` — `UNIQUE(task_id, type, version)`. `data` is **redacted at the write** since migration 0038 (TD-012, WP-52): prose through the run's own injected-secret redactor composed with the platform's pattern rules (steps 1 and 2), and a field the platform *addresses something with* — `mr.head_sha`, a vault `target_path` — **refused** rather than rewritten, because a redacted identifier addresses the wrong row. **One type is an exception and it is named here rather than left to be discovered**: a `ShadowReport` has no run to build a step-1 secret set from and is written through an empty redactor, so neither step is applied to it and its `redaction_count` is `0` by construction (PROGRESS backlog **131**, which owns the write); its exposure is unchanged, because the same document is already served by `GET /api/shadow-batches/:id`. `redaction_count` is nullable with no default and a `NOT VALID` check: `null` is "written before 0038, when no redactor ran", `0` is "the redactor ran and replaced nothing", and a new row that omits the column is refused by the database.

### Event log and jobs
- `events(position bigint generated always as identity, id uuid not null default uuidv7(), stream_type, stream_id uuid, stream_seq int, type, payload jsonb, actor jsonb, cause_event_id uuid null, cause_event_position bigint null, correlation_id uuid, occurred_at timestamptz, xact_id xid8 default pg_current_xact_id())` — **partitioned by range on `occurred_at` (monthly)**; PK `(occurred_at, position)`; `UNIQUE(stream_type, stream_id, stream_seq)`; idx `(type, occurred_at)`, `(correlation_id)`. Append-only. Consumers track per-stream `stream_seq` or fence on `pg_snapshot_xmin(pg_current_snapshot())` (research/07: global position is not gapless).
- `handler_executions(event_position, handler, priority, status, attempts, error, started_at, finished_at)` PK `(event_position, handler)` — idempotency guard for the dispatcher.
- `event_dispatch(event_position, occurred_at, stream_type, stream_id, stream_seq, attempts, error, available_at, enqueued_at, dead_lettered_at, dead_letter_handler)` PK `event_position` — the dispatch queue TD-005 needs, written by a trigger on `events` and deleted when every handler of the event reached a terminal status (migration 0010; it was missing from this list, and the two columns at the end are **WP-49**, migration 0037). It is a work queue and holds no audit value — what ran is in `handler_executions`. `dead_lettered_at` is the terminal state an event reaches after `APP_DISPATCH_MAX_ATTEMPTS` failed attempts: the sweep's window, the ordering guard and the backlog count all exclude a row that carries it, which is what lets the rest of the stream move on, and `dead_letter_handler` names the handler whose failure spent the bound. The row is **kept**, not deleted — it is the only record that this event was never dispatched, it is what `event_dispatch_dead_lettered` counts, and clearing the two columns is how an operator re-queues one. `events` itself is untouched, so a dead-lettered event is still replayable.
- `inbox(provider, delivery_id, integration_id, received_at, headers jsonb, payload jsonb, processed_at, error, redaction_count, verified)` PK `(provider, delivery_id)` — webhook dedup and audit. **Amended at WP-15c (migration 0014):** the two columns at the end are new, and "raw audit" is now "audit" because the row is **not** raw. `headers` and `payload` are stored `redactJson`-redacted — GitLab's legacy scheme sends the binding's own webhook secret as plain text in `X-Gitlab-Token`, so a raw row is a live credential on every delivery — and `redaction_count` is the only signal a redactor that stopped working would leave (the sum over the row's redactions, not the delivery key's, which is ~always 0). `verified` is the signature verdict at receipt, stored because a redacted payload can no longer produce it; it defaults to `false`, so an unwritten verdict understates trust rather than overstating it. A row exists only for a delivery that **verified**: writing one for a forgery would let anyone who can address the endpoint occupy a dedup key a genuine delivery will need. `processed_at` is written at insert while normalisation happens in the request, so `inbox_unprocessed_idx` selects nothing in this build and becomes live the day normalisation moves to a sweep.
- `notifications(id, project_id, task_id null, class, cause_event_id, title, detail, url, urgent bool, planned_delivery, mode, created_at, delivered_at null, delivered_as null, digest_day date null, redaction_count)` — the chat outbox (**added at WP-32**, migration 0023); `UNIQUE(project_id, cause_event_id, class)`, partial idx `(project_id, created_at) WHERE delivered_at IS NULL` and `(project_id, digest_day) WHERE digest_day IS NOT NULL`. It exists because product/18:33 batches a notification raised inside the quiet window into a daily digest, and the decision, the delivery and the collection happen in three different jobs (and possibly three replicas): the thing that survives all three is a row. `delivered_at` is the only column that says a human was told — `planned_delivery` is what the policy decided when the notification was *raised*, which is the only moment the quiet window can be evaluated for it, and `digest_day` is a **claim** by the day's digest, so a retry posts the same set and a claim a failed day left behind is re-claimed by the next one rather than stranded. `title`/`detail`/`url` are the **third** place the platform stores external text after `inbox` and `tasks.ticket_snapshot`, so they are bounded and redacted at write (TD-012) — the URL by dropping rather than truncating, because a cut link resolves somewhere else and `urlSchema` accepts any scheme (Q49) with `redaction_count` as the only signal a redactor that stopped working would leave. `mode` is the task's, because the digest groups by it: a shadow task's lines must not ride in a message a real one is in (BD-021).
- `pgboss.*` — pg-boss's own schema (jobs, timers, cron) in the same database (TD-004).

### Cost and governance
- `cost_entries(id, run_id, task_id, project_id, stage, model, input_tokens, output_tokens, cache_write_5m, cache_write_1h, cache_read, usd numeric(12,6), is_estimate bool, late bool, price_list_id, created_at)` — append-only ledger (one per run per model); `UNIQUE(run_id, model, created_at)` since WP-19 (migration 0017). **What makes the ledger idempotent is `handler_executions`, and that is true of the backfill too**: the rows and the claim that the handler ran commit in one transaction (TD-005), and `events/replay.ts` claims `(position, handler)` exactly as the dispatcher does — so a redelivered event, a second backfill pass and a range that overlaps live traffic all skip. The unique key does **not** add a cross-transaction guard and must not be read as one: `created_at` defaults to `now()`, which in PostgreSQL is the *transaction's* start, so two passes in two transactions produce two different timestamps and two rows. What it catches is a duplicate **inside one transaction** — one derivation emitting the same `(run_id, model)` twice, which is what a future caller assembling entries from more than one source would do — and `created_at` is in the key at all because a range-partitioned table requires its partition key in every unique constraint. *(Migration 0017's own comment overstates this as "a replay within the same microsecond"; the file is applied and forward-only, so the correction lives here — WP-19's notes carry it for the next migration to fix at the line.)*
> **Who writes what, since WP-19.** `cost_entries`, `cost_rollup_daily`, `run_model_usage` and `budget_windows` have exactly one writer: the `cost.ledger` handler on `run.finished` / `run.failed` (`packages/application/src/cost/ledger.ts`), in TD-005's core band at priority 10. It appends the entries, folds the rollup with `INSERT … ON CONFLICT DO UPDATE`, and records the spend against every applicable budget — all in the handler's own transaction. `runs` and `wall_ms` land on **one** entry per run (the run's own model), so summing a day's rollup gives runs and wall time rather than a multiple of them, while the token and USD columns are per entry — which is what makes `sum(cost_entries.usd) = sum(cost_rollup_daily.usd)` the reconciliation the work package is measured by. A **task-scoped** `budgets` row is projected but not enforced: the task cap is the stage executor's own check against the project's configuration (product/09's "$50 default, per template"), and one question with two answers is worse than one answer in the wrong place.
- `price_list(id, model_id, effective_from, effective_to null, input, output, cache_write_5m, cache_write_1h, cache_read, batch_multiplier, fast_input null, fast_output null, source_url, verified_at)` — never mutated; pick the row with `effective_from <= run.started_at`.
> **Amended at WP-47 (migration 0035): `cost_entries` gains `late boolean not null default false`.** A cancelled or lease-expired run's spend reaches the ledger from the process that *ran* it, after the row was already terminal, and that row is a **late report**: an operator reconciling an invoice is asking a different question of a charge the ledger made when the run ended and one it made afterwards, so the two are labelled rather than merged. `false` is right for every row written before it, because all of them were made by the handler on the run's own terminal event.

- `cost_rollup_daily(org_id, project_id, template, stage, model, day date, mode enum(actual|estimated), runs, input_tokens, output_tokens, cache_write_5m, cache_write_1h, cache_read, usd numeric(14,6), wall_ms bigint, turns int)` PK `(project_id, day, template, stage, model, mode)` — `INSERT … ON CONFLICT DO UPDATE` on run finish; nightly recompute of yesterday.
- `budgets(id, scope, scope_id, window, limit_usd, notify_pct int[], created_by, updated_at)`; `budget_windows(budget_id, window_start, spent_usd, notified_pct int[])` projection.
- `human_time_entries(task_id, kind enum(review|question|approval|**steer**), user_id null, **external_author null**, started_at, ended_at, minutes)` derived from events by a projector. **The projector exists since WP-29** (`packages/application/src/human-time/`), and so does the fourth kind: product/19 §16 defines *"steer = 5 min flat per steer"* and `human_time_kind` could not express it, so migration **0025** appends the label (forward-only, TD-011) and adds `external_author`. That column is the **segment key** for review minutes when no platform user is mapped: `user_identities` has had a writer since WP-31 and is empty until an operator maps an account, so on a default instance every review minute has `user_id: null`, and two reviewers of one merge request would otherwise extend one another's window. It is registered `read_write` rather than `append_only` because a review entry is a window that **grows** — the first human comment opens it and every later activity moves its ending — which makes this a projection like `budget_windows`, rebuildable by replaying a range of `events` into it (`events/replay.ts`). One handler writes it, at TD-005 priority 230, and `packages/infrastructure/src/human-time/human-time-writers.test.ts` is the census that keeps that true.
- `integration_actions(id, integration_id, project_id null, task_id null, direction enum(in|out), action, payload jsonb, result jsonb, status, duration_ms, redaction_count, attempts, created_at)` append-only.
> **Three columns added at WP-15b (migration `0013`).** `IntegrationActionEntry` (WP-07) has carried
> `projectId`, `redactionCount` and `attempts` since the port was written, and the table created at
> migration `0007` had no home for any of them — so the first adapter of `IntegrationAuditLog` needed a
> migration as well as code. Each earns its column:
> - **`project_id`** because an action is scoped to a project even when it has no task: a binding health
>   check or an inbound normalisation belongs to a project's audit, and `task_id` is nullable precisely
>   for those. Reconstructing it through `integrations` would be wrong — one integration serves many
>   projects.
> - **`redaction_count`** because it is the only signal that a row which *should* have hidden something
>   did not (TD-012). A redactor that silently stops working writes rows that look exactly like clean
>   ones; a zero next to a payload that carried a credential is the discrepancy an auditor can see. It is
>   a **count on the row**, never part of an identity (the idempotency *key* is refused rather than
>   redacted — technical/06 § "Outbound: actions").
> - **`attempts`** because "the provider was called and it worked" and "the provider was called four
>   times and the fourth worked" are different facts about an integration's health, and the executor's
>   retry loop is the only place that knows.
>
> **`task_id` and `project_id` carry no foreign key** — `task_id`'s was dropped by the same
> migration. An audit row commits in a transaction of its own (with its event, per BD-003) while the
> *caller* is usually still inside one: technical/06 says actions are triggered by event handlers,
> and the intake saga reads the repository's default branch in the same transaction that inserts the
> task. A referential constraint refuses that row **because the caller has not committed**, making
> the audit the thing that fails the action — measured, as an e2e that died on its first event. The
> residual is stated: `task_id` may name a task that no longer exists, or that a rolled-back
> transaction never created, which is still the honest record because the provider call really
> happened. Dropping it is also what lets a project be deleted at all, since a RESTRICT from an
> append-only table nobody may delete from is permanent. `integration_id` keeps its foreign key: a
> binding is always committed before a call is made through it.
>
> **So every reader of this table `LEFT JOIN`s `tasks` and `projects`, and must render a row whose
> task or project is missing rather than dropping it.** An inner join silently hides exactly the
> rows an audit exists for — an action attributed to a task that was rolled back, or to a project
> somebody has since deleted — and "the audit shows nothing" is indistinguishable from "nothing
> happened". This is written here rather than only in the migration because **no reader exists
> today**: there is no route, no projection and no query over `integration_actions` outside the
> writer and its tests, so the whole cost of the trade falls on whoever builds the audit view
> (`GET /api/org/audit`, WP-19's audit and health projections), and they will read this document
> and not a commit message.
>
> Both `redaction_count` and `attempts` are `not null` **with no default**: an INSERT that omits either is
> refused by the database rather than recorded as a zero, because "nothing was redacted" and "nobody wrote
> the column" must not be spelled the same way (standing rule 18). `platform_table_policy` keeps the table
> `append_only` on `created_at`, unchanged.

- `integration_idempotency(storage_key pk, integration_id, action, result jsonb, created_at)` — the
  `IdempotencyStore` port's table (WP-15b). `storage_key` is `idempotencyStorageKey(scope)`, the one
  composition of `(integration_id, action, key)` the port exports so no adapter invents its own; the
  parts are stored beside it so an operator can read the table without decoding the key. `result` is
  `jsonb not null` and holds the **redacted** remembered result, so a JSON `null` (a legitimate remembered
  value) stays distinguishable from "never seen", which is the absence of the row. Not append-only and not
  partitioned: nothing expires a key today, and when something does it will delete rows.

## Storage sizing (from research/07 measurements)
~1–2 MB and 1–3 k rows per run; 1 000 runs/month ≈ 2 GB and 3 M rows/month. Partitioning from day 1; storage gauge = `pg_total_relation_size('run_messages')` on the org dashboard (Q13-b).

## Retention and backups
- Default keep forever. Optional `APP_TRANSCRIPT_RETENTION_DAYS` drops whole `run_messages` partitions older than N days; metadata, artifacts, events, cost stay.
- Compose ships a `db-backup` sidecar (`pg_dump` daily/weekly/monthly rotation) with a documented restore; pgBackRest/WAL-G as a later profile.
- Docker: mount `/var/lib/postgresql` (not `/data`) for the `postgres:18` image (research/07 gotcha).

## Redaction (TD-012)
Single persistence path function applied to `run_messages`, `integration_actions`, `events.payload`, `config_audit`: (1) exact match of every secret value the platform injected into the run, (2) regex rules derived from gitleaks' rule set (generic API keys, private keys, cloud/provider tokens, JWTs, connection strings), (3) optional entropy heuristic; placeholders `[REDACTED sha256:ab12cd]`; counts and `redaction_log` rows; originals never stored.
