# 03 — Data model and storage

> Round 2 design. Decisions: TD-005 (event store), TD-006 (PostgreSQL 18), TD-007 (transcripts as partitioned rows), TD-011 (Drizzle), TD-012 (redaction). Evidence: research/07, research/06.

## Principles
- **PostgreSQL 18 is the only database.** Events, state, transcripts, cost, audit, KB indexes, jobs — one backup, one restore, one `DATABASE_URL`.
- **Append-only where the audit demands it** (`events`, `run_messages`, `cost_entries`, `integration_actions`, `config_audit`, `redaction_log`): `REVOKE UPDATE, DELETE` from the application role; partition by month; purge only by dropping partitions and only when the operator configures a retention window (default: never — Q13).
- **Typed columns for anything filtered or aggregated; JSONB only for opaque payloads.** Never keep mutable status or counters inside a large JSONB document (TOAST rewrite cost).
- **`uuidv7()` primary keys** (time-ordered, PG 18 built-in) on all entity tables.
- **Derived data is rebuildable** (KB index rows, code maps, rollups) and carries the commit/model/price-list version it was built from.

## Schema (logical; DDL written by the implementer with Drizzle + hand-written SQL migrations for partitions, GIN, generated columns)

### Identity and configuration
- `organizations(id, name, timezone, settings jsonb, created_at, updated_at)` — one row. `settings` is the **organisation settings document** (WP-93, technical/12 § "The organisation settings document"): the command, autonomy and WIP maximums and the organisation's notification settings, written only by `PATCH /api/org` (under a `for update` lock on the row) and **parsed at every read** through `organisationSettingsSchema` — a stored value it refuses is a named refusal, never a cast. No migration: the column has existed since 0003 with default `'{}'`, which is the document that states nothing.
- `users(id, email unique, name, role enum(admin|maintainer|member|viewer), status, email_verified bool, image null, banned null, ban_reason null, ban_expires null, created_at, updated_at)`; `sessions(id, user_id, expires_at, token unique, ip_address null, user_agent null, impersonated_by null, created_at, updated_at)`. **Corrected at WP-97 from migration 0011**, which gave Better Auth (TD-022) the columns it needs and **dropped `users.password_hash`**: a credential lives in `accounts.password`, and this line named the dropped column for sixty migrations.
- `accounts(id, account_id, provider_id, user_id → users, access_token null, refresh_token null, id_token null, access_token_expires_at null, refresh_token_expires_at null, scope null, password null, created_at, updated_at)` — unique `(provider_id, account_id)`, idx `(user_id)`, `read_write`. **Added at WP-06 (migration 0011); entry written at WP-97.** One row per credential or external identity a user can authenticate with: `provider_id` is `credential` for e-mail and password, and TD-022's OIDC path adds rows with the issuer's id. `password` is an **Argon2id hash**, never a password, and is kept out of every API response by never being selected into one. Separate from `user_identities`, which maps *ticket* authors to users and can authenticate nobody (BD-006, Q10). The shape is Better Auth's (`getMigrations()` for the platform's auth configuration, camelCase fields mapped to snake_case), and `test/integration/auth/better-auth-schema.integration.test.ts` fails when a Better Auth upgrade wants more.
- `verifications(id, identifier, value, expires_at, created_at, updated_at)` — idx `(identifier)`, `read_write`. **Added at WP-06 (migration 0011); entry written at WP-97.** Pending e-mail verification and password-reset tokens: short-lived, expired and deleted by Better Auth itself, so neither partitioned nor under a retention policy.
- `user_identities(user_id null, provider, external_id, email, display_name, **kind** text(person|machine))` — PK `(provider, external_id)`. A `person` row names its platform user; a `machine` row (WP-61, migration 0045) is an account an operator **declared** a bot and has `user_id null` by a check constraint — it resolves to nobody, so nothing it writes is acted on and its merge-request activity is never human review time. Declared, never inferred.
- `projects(id, org_id, key unique, name, repo_url, default_branch, agentic_dir, knowledge_dir, config jsonb, config_source jsonb, config_hash, autonomy_level, autonomy_policies jsonb, readiness_level, proposed_risk_classes jsonb null, maintenance_last_blocker null, status, created_at, updated_at)` — **every writer is narrow, and there is no `version` column** (WP-129): each column's writing statements are declared and checked off disk by `packages/infrastructure/src/db/projects-column-ownership.test.ts`, which refuses a whole-row `update projects` and an undeclared writer, so the optimistic token `tasks` carries (WP-15e) has nothing to arbitrate here. `default_branch` (migration 0003's default `main`) is written by the create and, since **WP-139**, by `PUT …/default-branch` alone — under the row's lock, refused while any of the project's tasks is not `done` or `cancelled`; the wizard always sends it. **Since WP-142 it is the one default branch every reader takes** (checkout, the merge request's target, the mirrors, the intake protection check, R9, the poll's default head, coverage's baseline, `CODEOWNERS`); the change also clears the project's `bindings.mr_poll_default_head` in its transaction (and, since **WP-147**, turns its `project_repository_config` row — the old branch's reading — `invalid`, so runs wait for the new branch's), and every task insert takes the row `for share` first, so a task cannot be created unseen by the change's live-task count. `proposed_risk_classes` (migration 0026, WP-37) is a discovery run's config-shaped proposal, never applied. `maintenance_last_blocker` (migration 0069, WP-113, Q111 (c)) is the blocker the last nightly maintenance pass recorded, one of the four `MaintenanceBlocker` codes held by a check constraint, `null` for none; its one writer is the pass's compare-and-set (`MaintenanceBlockerStore.recordBlocker`), and a change into or out of `paused_at_observe` is one digest line. `autonomy_policies` is the materialised preset with its version (migration 0021, WP-30, BD-027:14); `null` means never materialised. **`config` is the settings layer** — what the screens and `PUT …/config` write — and not the effective configuration: since WP-63 the effective configuration is computed on read from it, the organisation settings document (`organizations.settings`: the command maximum and, since WP-91/WP-93, the WIP and autonomy maximums) and the repository's own file (`project_repository_config`), and `config_source` is no longer what `GET …/config` publishes as `sources` (that is computed by the merge).
- `project_repository_config(project_id PK → projects, status absent|valid|invalid, commit_sha, config jsonb null, not_applied jsonb, detail null, read_at, prompts jsonb null, prompts_redaction patterns|exact, prompts_withheld jsonb null)` — **added at WP-63** (migration 0050, PROGRESS backlog 44, Q94). The last reading of the project's own `.agentic/config.yml` on its **default branch** (BD-025 §1): one row per project, **replaced** on every reading (derived state, BD-012 — the repository's history is the history), and no row means *never read*. Since **WP-147** `PUT …/default-branch` rewrites an existing row in its transaction to `invalid` (the old commit, `config` and `prompts` null, a `detail` naming the change), so every run is refused until a reading of the new branch — which the route makes right after the commit — replaces it; a missing row would have been *no repository layer*, failing open. `config` exists exactly when the file parsed and is the file minus `version` and minus what `not_applied` names (`policies.autonomy`); `detail` exists exactly when it did not and names the key paths, redacted and bounded at 600 characters. A reading that cannot reach the repository writes nothing. Written by `refreshRepositoryConfig` after every knowledge index run, by `POST …/config/refresh` and, since WP-147, right after a change of the default branch; a reading is taken as *older* than the recorded one only when the recorded commit is on the branch read now, so the previous branch's reading never outranks the new branch's; read by the pipeline's settings port and by `GET …/config`, and an `invalid` row refuses every run of the project. **`prompts` since WP-92** (migration 0063): `.agentic/prompts/` at the same commit — `{files: {<path>: file|oversized|not_a_file}, truncated}`, at most 64 direct `<name>.md` children of at most 16 KiB each, every text redacted (TD-012 step 1 over the project's binding credentials since WP-107, then step 2) — which a stage's `project_prompt` data blocks are built from (technical/04, technical/12); `null` means this reading did not read the directory (every row written before 0063), and a prompt file a key names is then rendered `unread`. **`prompts_redaction` and `prompts_withheld` since WP-121** (migration 0073, TD-012's M7 amendment): `prompts_redaction` is `patterns` (every row written before 0073 — TD-012 step 2 alone) or `exact` (every reading since: step 1 over every credential the platform holds for the project, then step 2), `not null` with no default; a `patterns` row serves no prompt text to any reader, and the knowledge process re-reads each one at start. `prompts_withheld jsonb null` is why the reading serves no prompt text — `{reason, integrations: [{integration, reason}]}`, the integrations whose credentials could not be decrypted, or empty for a `patterns` reading that could not be read again — and `null` when nothing was withheld; a check keeps `prompts` null beside it.
- `project_members(project_id, user_id, role)`.
- `integrations(id, org_id, type, provider, name, config jsonb, secret_ids uuid[], health jsonb, created_at, updated_at, retired_at timestamptz?)` — **`retired_at` is WP-114's** (migration 0070, PROGRESS backlog 331): set once by `DELETE /api/integrations/:id`, which deletes the integration's `secrets` rows and empties `secret_ids` and `health` in the same transaction and keeps the row, because `integration_actions.integration_id` names it (BD-003); `null` while live. A retired row is never loaded, refuses every write and keeps its `(org_id, type, name)`. `secret_ids` is rewritten by `POST /api/integrations/:id/secrets` (the re-seal), each named field's row replaced by a new one and the old row deleted; `bindings(id, project_id, integration_id, config jsonb, poll_cursor timestamptz?, mr_poll_cursor timestamptz?)` — `poll_cursor` is the ticket poller's (WP-87, migration 0061): the provider's newest `updated_at` a poll of this binding recorded, moved forward only, `null` until the first poll (which then reads the binding's last interval only). Polling itself is switched in `config` (`poll_enabled`, `poll_interval_seconds`), and each polled match is an `inbox` row keyed `<provider>:poll:<project>:<ticket>@<updated_at>`. **Amended at WP-110 (migration 0068):** `mr_poll_cursor` is the merge-request poller's, the same rules for a **git** binding (its own column, because the two pollers read different providers' timelines); each listed merge request is an `inbox` row keyed `<provider>:poll:<project>:<path>!<iid>@<updated_at>`. **Amended at WP-123 (migration 0074):** `bindings(…, mr_poll_default_head text?)` — the default branch's head a **poll-only** git binding (no webhook secret) last read; `null` until its first such poll, which records no move — and `null` again after a change of `projects.default_branch` (WP-142), so the poll then reads the new branch as a first reading. It is written only while the branch it was read of is still the stored one. A different head is an `inbox` row keyed `<provider>:poll:<project>:<path>@default:<old>..<new>` carrying `default_branch.moved`, written before the column; and each review note such a binding records for a task at `ready_for_merge` is an `inbox` row keyed `<provider>:poll:<project>:<path>!<iid>#note:<id>` carrying `mr.review.comment`. **Amended at WP-148 (backlog 444):** `PUT …/bindings` updates a binding whose identity — `(project_id, integration_id)`, the table's unique key — is unchanged **in place** (`config` and `updated_at` only), so its row id and all three poll columns survive a re-save; a binding left out is deleted, and one to an integration not bound before (or removed and added back) is a new row that starts with all three `null`. Before WP-148 the PUT deleted and re-inserted every row, resetting all three — which migrations 0061, 0068 and 0074 state as of their time. A request naming one integration twice is refused `400 invalid_request`.
- `held_connection_liveness(integration_id PK → integrations, holder, renewed_at, expires_at)` — `check (length(holder) between 1 and 200)`, `check (expires_at > renewed_at)`, `read_write`. **Added at WP-72 (migration 0054, PROGRESS backlog 200); entry written at WP-97.** Whether any process holds an account's inbound connection (Slack's Socket Mode) **now** — the question a binding's configuration cannot answer. `startInboundConnections` writes the row when a connection opens and renews it while it is held; the notify duty reads it before posting an approval with buttons and posts text naming the task page when it is not fresh. Freshness is `expires_at > now()` with **both** halves on the database's clock, so two processes whose wall clocks disagree cannot disagree about a holder. The key is the account, not the holder: the last renewal wins and `holder` is a diagnostic; a stopping holder deletes the row only while it is the one named there, and a dead one leaves it to expire. At most one row per integration, cascaded with it.
- `secrets(id, ciphertext bytea, key_id, created_at, rotated_at)` — encrypted with `APP_SECRET_KEY` (envelope); never joined into API responses. **One row is one credential**, and its plaintext is the JSON document `{"field", "value"}` — the provider config field the value belongs to travels *with* it, because `integrations.secret_ids` is a `uuid[]` with no names in it and an operator reordering that array must not be able to swap a webhook secret for an API token (WP-15a, `packages/infrastructure/src/secrets/postgres-secret-store.ts`). The envelope is a per-row AES-256-GCM data key wrapped under a key derived from `APP_SECRET_KEY` by HKDF; `key_id` is a fingerprint of the *derived* key, so a half-finished rotation is a readable state rather than a corrupt one, and a row sealed under another key is refused by name rather than reported as a bad tag.
- `config_audit(id, entity_type, entity_id, user_id, diff jsonb, created_at)` — append-only; secret values appear as `"changed"`.

### Pipeline
- `tasks(id, project_id, ticket_provider, ticket_key, ticket_url, ticket_id, template, mode enum(normal|shadow), state, current_stage, size, priority, requested_by_user_id, requested_by_identity jsonb, template_snapshot jsonb, pipeline_dial jsonb, settings_refreeze_pending bool, refreeze_routing jsonb, ticket_snapshot jsonb, ticket_snapshot_at, ticket_signal_at, config_snapshot_hash, mr_head_at, ready_head_sha, ci_head_sha, ci_excused_paths text[], dependency_recovery_attempted_at, stage_recovery_attempted_at, branch, mr_ref jsonb, workpad_ref jsonb, iteration_counters jsonb, stage_attempts jsonb, iteration_limits jsonb, review_subject jsonb, review_threads jsonb, cost_actual, budget_cap_usd numeric(12,6) null check (budget_cap_usd > 0) numeric(12,6), estimate_usd numeric(12,6), estimate_basis, estimate_samples, risk_classes text[], blocked_by text[], version int, created_at, updated_at, completed_at)` — idx `(project_id, state)`, `(project_id, created_at)`, `UNIQUE(project_id, ticket_key, mode)`, `UNIQUE(project_id, ticket_provider, ticket_id, mode) WHERE ticket_id IS NOT NULL`. **Amended at WP-134 (migration 0077, PROGRESS backlog 418):** `ticket_id` is the provider's **stable** ticket id (`TicketRef.id` — Jira's numeric issue id, which a move to another project keeps while the key changes), written once by the insert and never updated, outside the `save` partition; **amended at WP-145 (PROGRESS backlog 437):** `ticket_key` and `ticket_url` are no longer insert-only — `rekeyTicket` moves them to the key a moved issue holds now, compare-and-set on the old key, for a live task matched by `ticket_id` (and refused while another task of the project holds the new key in the same mode), filling `branch` with `agentic/<old key>` **only while it is null** and bumping `version`, so `branch` is co-owned by `save` and that statement (`tasks-column-ownership.test.ts`); the move is recorded as `task.ticket.rekeyed` on the task's stream. `ticket_id` itself is still never updated; `null` for a provider with none and for every task created before 0077 (no backfill — the id is the provider's). `findByTicket` answers a task by its key **or** its id, so one task per ticket holds across a move; the partial unique index is the backstop for two intakes that race past it, and `tasks_ticket_id_shape` bounds the provider text (1–64 of `A–Z a–z 0–9 . _ : -`). **Amended at WP-62 (migration 0049):** `pipeline_dial` is the autonomy dial's two pipeline policies — `{ level, preset_version, business_review, stop_after_stage }` (`taskPipelineDialSchema`) — copied off the project's **materialised** preset (BD-027:14) by the site that creates the task and read by every `compilePipeline` over it, frozen for `template_snapshot`'s reason: a dial moved while a task runs does not move that task. **Written by the insert only**, so it is outside the `save` partition below; `null` means *no dial applies* (a dial never materialised, a task kind the dial does not shape — review-only, the linter, shadow, maintenance, discovery, history bootstrap — or a row older than the column) and compiles the template as before; a document that fails its schema is refused on load rather than read as `null`, because `null` is the permissive direction. **Amended at WP-15f (migration 0015):** `ticket_snapshot`/`ticket_snapshot_at` are new. `ticket_snapshot` is the ticket's own title, description and newest comments — **untrusted stored external text** (BD-022), like `inbox.payload` and `kb_chunks`, and the third place the platform keeps somebody else's words. It is written **redacted** through the binding's redactor — TD-012 step 1 *and* step 2, the same pair `inbox` gets — with a `redaction_count` inside the document and **bounded at the write**, because the store is the consumer (Q54): title 512 characters, description 20 000, the newest 20 comments at 1 000 each, with `truncated` and `comment_count` declaring what was cut — one unbounded `readTicket` was measured at 53 284 565 bytes. **Amended at WP-83 (PROGRESS backlog 290):** `comment_count` is the number of **human comments the platform read**, not the ticket's comment count — a provider may answer a page (Jira's newest fifty) — and `truncated` is also set when the provider's `Ticket.comment_total` says the thread is longer than the page it returned. It is read once at intake and again at a stage that finds none — **and, since WP-60 (migration 0044), at a stage that finds it older than `ticket_signal_at`**, the receipt time of the newest `ticket.updated` for the ticket, written only by `TaskRepository.recordTicketSignal` (forward only, on every live task of the ticket, no version bump) and never by the insert; both writers of `ticket_snapshot_at` stamp the read's **start**, so an edit announced during a read is dated after it (Q61 (b)) — is readable by anyone who can read the task, and **dies with the task** by the row it sits on; `null` means *the platform has not read this ticket* and is never how a ticket with an empty description is spelled. `ticket_snapshot_at` is a column rather than a field so "which tasks are running on an old snapshot" is a query, and `tasks_ticket_snapshot_at_paired` keeps the two null together. **Amended at WP-47 (migration 0035):** `cost_estimated` is **dropped**. It was `not null default 0` from migration 0004, published on the task DTO as `cost_estimated_usd`, and written by **nothing** — so every task the product ever served reported `$0.00` of estimated spend, which is standing rule 16 one layer out: *"nobody counted"* served as *"nothing was estimated"*. The field is now a **projection** over `cost_entries where is_estimate` (`apps/server/src/queries/pipeline-queries.ts`), because `cost_entries.is_estimate` has carried the per-row flag since WP-19: no fourth running total to keep in step, no backfill for tasks that already exist, and no new writer to add to this row's column partition. A task with one priced run and one reported run therefore publishes the **priced** amount and not the sum, which is what the field's own definition says and what the column never could. **Amended at WP-15e (migration 0019):** `version` is the row's optimistic-concurrency token, and it exists because a whole-row write is correct only while nothing else writes the row — a fact about the callers, which WP-15d falsified by moving a provider call into a job. `TaskRepository.save` writes `… , version = version + 1 where id = $1 and version = $n`, so a write over a row another transaction has moved is **refused** rather than silently winning. **Amended at WP-59 review round 1:** `save` is no longer the only writer of `version` — `TaskRepository.bumpVersion` moves it (with the bookkeeping `updated_at`) and **no column of the aggregate**, for a writer that appends to a task's stream from outside the task's own transactions (the conflict warning's pair, `recordRebaseCheck`): it bumps first, in sorted id order, which takes the row lock, so an owner that loaded before it meets the retried `TaskConcurrentModificationError` at its `save` rather than an unretried `StreamConflictError` at its append; the column-ownership census lists `version` as a deliberately shared column for that reason; the caller re-reads and decides again, bounded, and a task whose write loses every attempt is escalated to `needs_human` rather than dropped. The columns of this row are **partitioned by writer**: `save` writes the aggregate's own (`state`, `current_stage`, `branch`, `stage_attempts`, `iteration_counters`, `cost_actual`, and `mr_ref` until WP-138 — amended below) and bumps `version`; `workpad_ref`, `ticket_snapshot`/`ticket_snapshot_at`, `ticket_signal_at`, `review_threads` and `size`/`estimate_usd` each have exactly one narrow writer and are **not** named by `save`, so they neither cause nor suffer a false conflict. **Amended at WP-60:** `mr_ref` is the one column with **two** writers by decision — `save`, and `TaskRepository.saveMergeRequestHead`, which rewrites only its `head_sha` key (`jsonb_set`) when the provider announces a push the platform did not make (PROGRESS backlog 182) and **bumps `version` in the same statement**, so a `save` over a snapshot read before it is refused rather than putting the old revision back; the census names both statements by shape. **Amended at WP-138:** `mr_ref` **left `save`'s columns** — the merge request a task has is the platform's record, written by `TaskRepository.recordMergeRequest` when the developer's `open_mr` tool opens or adopts one (compare-and-set: only while the column is `null` or names the same iid, and only while `branch` is `null` or the merge request's own), cleared by `releaseMergeRequest` in the rework's transaction, and moved one key at a time by `saveMergeRequestHead`, which still bumps `version`; `save` ignores a snapshot's `mr` and returns the row's own, and the saga no longer takes the reference from `ImplementationNotes.mr` (a different report is noted on the stored artifact). The census names all three statements by shape. It moves the head **forward only**: `mr_head_at` (migration 0044, its only writer) is the provider's `updated_at` of the recorded head, and a delivery stamped no later than it moves nothing — the CI gate asks the pipeline status of this head, and GitLab documents no delivery order (WP-60 review round 1). The partition is enforced off disk by `packages/infrastructure/src/pipeline/tasks-column-ownership.test.ts`, because it was a docblock claim that `save` had already falsified (it named `workpad_ref`, so the executor put back the `null` the workpad job had just filled in). **Residual, stated because an optimistic check is a claim about every writer of the row and is only true while every writer carries the token**: a *pre-WP-15e* process writes `where id = $1` with no predicate and does not bump `version`, so it wins silently **and** leaves the token unmoved — a concurrent new-process `save` then succeeds as well and one of the two updates is lost. No deployment shape in this build produces it: the image runs `migrate` and then `server` from one artefact, and two versions of this code never serve at once. A rolling deploy would have to close it (a `version`-bumping write in the old binary first, or a drain), which is why the sentence lives here and in `TaskRepository.save`'s docblock rather than in migration 0019 — an applied migration is never edited (TD-011). **Amended at WP-67:** `requested_by_user_id` — product/19:138's third reviewer step — is written **by the insert** of the three task-creating commands that hold an actor: discovery, a shadow batch, and a history bootstrap's chunk tasks (from the batch's `requested_by`). Every other creation site writes `null` and says why (intake's ticket reporter was PROGRESS backlog 92's unbuilt half (b) until WP-79, below; review-only and the linter are started by a provider delivery; the maintenance scheduler is the platform's own). Like `pipeline_dial` it is outside the `save` partition. **Amended at WP-84 (migration 0059, PROGRESS backlog 240):** `dependency_recovery_attempted_at` is the mark of the deferred-dependency-gate recovery (`packages/application/src/recovery/deferred-dependency.ts`, a row of `recovery/stranded.ts`'s table): the instant the pass re-enqueued the `dependency_gate_resume` duty for an `active` task still carrying `dependencies.deferred_stage` a pass interval after its newest `task.resumed`. The pass acts again only for a later `task.resumed` than the mark — one attempt per resume. Its one writer is `packages/infrastructure/src/recovery/postgres-deferred-dependency-store.ts`, outside the `save` partition. **Amended at WP-108 (migration 0067, PROGRESS backlog 320):** `stage_recovery_attempted_at` is the mark of the stranded-stage recovery (`packages/application/src/recovery/stranded-stage.ts`, a row of `recovery/stranded.ts`'s table): the instant the pass re-enqueued `stage.execute` for a task left at an agent or gate stage with no `stage.execute` job queued, retrying or active, no live run, and an open `task_stages` row entered more than a pass interval ago. A mark older than that row's `entered_at` belongs to an earlier entry, so the pass attempts once per stage entry; a mark at or after the entry and older than the pass's ending window escalates the task to `needs_human` with a brief. Its one writer is `packages/infrastructure/src/recovery/postgres-stranded-stage-store.ts`, outside the `save` partition. **`settings_refreeze_pending`** (migration 0066, WP-106): the task was created while its project's stored configuration (or the organisation's) could not be read, so its `iteration_limits` and `pipeline_dial` are the platform's defaults. The stage executor's admission takes both again from the parsed document before the first run it admits (`TaskRepository.refreezeSettings`, the only `update` writer of those columns), and clears the mark. **`refreeze_routing`** (review round 2): intake's routing inputs (`issue_type`, `can_create_tickets`), kept while the mark is set, so the ticket is routed to its template again at `intake` on the parsed document; the same writer also rewrites `template` and `template_snapshot` then, and clears it.
- **Amended at WP-79 (migration 0056, PROGRESS backlogs 267 and 243).** Two changes to `tasks`, each with its writers named. **`ready_head_sha`** is the branch head the platform's gates judged on the way into `ready_for_merge` — the head the CI or rebase gate read when its settlement moved the task to Ready — and `null` when Ready was entered by anything that judged no head (a template whose gates are disabled, or a row older than the column). The migration marks **every undelivered `immediate` row that existed before it** as attempted, so an upgrade does not re-post months-old rows (a backfill rather than an upper age bound, which would also drop a post-upgrade row after a long outage). **Review round 1 added `question_id`** (`references questions on delete set null`): the question a `question` row asks or a `reminder` row reminds about — an approval's reminder names its approval in `approval_id` and carries no `message_ref` — which the notify duty re-checks before a retry or a re-post sends anything. **Review round 2 added a third delivery outcome, `delivered_as = 'withheld'`** (with `delivered_at` set, so `notifications_delivered_pair` holds): a `question`, `reminder` or `approval` row whose aggregate was settled before a retry, a re-post or the digest reached it is closed as withheld rather than left undelivered, so the gauge, the re-post sweep and the digest — all reading `delivered_at is null` — skip it, and `digestDelivered` (`delivered_as = 'digest'`) is not fooled by it. The digest re-checks a claimed `question`/`reminder`/`approval` row's aggregate by the same rule as the duty before carrying it.

### Cost and governance
- `cost_entries(id, run_id, task_id, project_id, stage, model, input_tokens, output_tokens, cache_write_5m, cache_write_1h, cache_read, usd numeric(12,6), is_estimate bool, late bool, price_list_id, created_at)` — append-only ledger (one per run per model); `UNIQUE(run_id, model, created_at)` since WP-19 (migration 0017). **What makes the ledger idempotent is `handler_executions`, and that is true of the backfill too**: the rows and the claim that the handler ran commit in one transaction (TD-005), and `events/replay.ts` claims `(position, handler)` exactly as the dispatcher does — so a redelivered event, a second backfill pass and a range that overlaps live traffic all skip. The unique key does **not** add a cross-transaction guard and must not be read as one: `created_at` defaults to `now()`, which in PostgreSQL is the *transaction's* start, so two passes in two transactions produce two different timestamps and two rows. What it catches is a duplicate **inside one transaction** — one derivation emitting the same `(run_id, model)` twice, which is what a future caller assembling entries from more than one source would do — and `created_at` is in the key at all because a range-partitioned table requires its partition key in every unique constraint. *(Migration 0017's own comment overstates this as "a replay within the same microsecond"; the file is applied and forward-only, so the correction lives here — WP-19's notes carry it for the next migration to fix at the line.)*

> **Three columns added at WP-15b (migration `0013`).** `IntegrationActionEntry` (WP-07) has carried
> `projectId`, `redactionCount` and `attempts` since the port was written, and the table created at
> migration `0007` had no home for any of them — so the first adapter of `IntegrationAuditLog` needed a
> migration as well as code. Each earns its column:
> - **`project_id`** because an action is scoped to a project even when it has no task: a binding health
>   check or an inbound normalisation belongs to a project's audit, and `task_id` is nullable precisely
>   for those. Reconstructing it through `integrations` would be wrong — one integration serves many
>   projects.
> - **`redaction_count`** because it is the only signal that a row which *should* have hidden something
>   did not (TD-012). A redactor that silently stops working writes rows that look exactly like clean
>   ones; a zero next to a payload that carried a credential is the discrepancy an auditor can see. It is
>   a **count on the row**, never part of an identity (the idempotency *key* is refused rather than
>   redacted — technical/06 § "Outbound: actions").
> - **`attempts`** because "the provider was called and it worked" and "the provider was called four
>   times and the fourth worked" are different facts about an integration's health, and the executor's
>   retry loop is the only place that knows.
>
> **`task_id` and `project_id` carry no foreign key** — `task_id`'s was dropped by the same
> migration. An audit row commits in a transaction of its own (with its event, per BD-003) while the
> *caller* is usually still inside one: technical/06 says actions are triggered by event handlers,
> and the intake saga reads the repository's default branch in the same transaction that inserts the
> task. A referential constraint refuses that row **because the caller has not committed**, making
> the audit the thing that fails the action — measured, as an e2e that died on its first event. The
> residual is stated: `task_id` may name a task that no longer exists, or that a rolled-back
> transaction never created, which is still the honest record because the provider call really
> happened. Dropping it is also what lets a project be deleted at all, since a RESTRICT from an
> append-only table nobody may delete from is permanent. `integration_id` keeps its foreign key: a
> binding is always committed before a call is made through it.
>
> **So every reader of this table `LEFT JOIN`s `tasks` and `projects`, and must render a row whose
> task or project is missing rather than dropping it.** An inner join silently hides exactly the
> rows an audit exists for — an action attributed to a task that was rolled back, or to a project
> somebody has since deleted — and "the audit shows nothing" is indistinguishable from "nothing
> happened". This is written here rather than only in the migration because **no reader exists
> today**: there is no route, no projection and no query over `integration_actions` outside the
> writer and its tests, so the whole cost of the trade falls on whoever builds the audit view
> (`GET /api/org/audit`, WP-19's audit and health projections), and they will read this document
> and not a commit message.
>
> Both `redaction_count` and `attempts` are `not null` **with no default**: an INSERT that omits either is
> refused by the database rather than recorded as a zero, because "nothing was redacted" and "nobody wrote
> the column" must not be spelled the same way (standing rule 18). `platform_table_policy` keeps the table
> `append_only` on `created_at`, unchanged.

- `kb_term_statistics(project_id, term, documents int)` PK `(project_id, term)` — **added at WP-58 (migration 0042)**, Q58. One row per keyword the project's indexed chunks contain (the platform's splitter: lowercased `[\p{L}\p{N}_]+`, four characters or more — *not* PostgreSQL's `simple` parser, so a query term and its frequency are the same word), counted by `termStatisticsOf` in `@platform/domain` and replaced with the documents in one transaction. `KnowledgeStore.search` drops a query term found in more than `N/2 + √N` of the `term_documents` (and in at least two) before it queries — the architect's WP-58 ruling, TD-008's amendment. Derived state (BD-012).
- `kb_index_refusals(project_id, path, reason, line int null, commit_sha, recorded_at)` PK `(project_id, path)` — **added at WP-57 (migration 0041)**, PROGRESS backlog 37's second half. A document the parser refuses (malformed frontmatter, a value outside product/05's vocabulary) is never indexed, so until this table it was in no table at all and in no health report — `IndexReport.invalid` lived for the length of one job. The index run now **replaces** the project's refusals in the same transaction as its documents, so the table always describes the commit `kb_index_state` names; an `unchanged` run and an unreadable vault touch neither. `reason` is the parser's diagnosis and can quote a frontmatter key a human wrote, so it is **untrusted text** (BD-022) and bounded at the write (1 000 characters, the cut declared with a trailing `…`). It is derived state like the rest of the index (BD-012): a rebuild re-creates it. The nightly pass reads it and reports each row as an `invalid` finding. 0041 also nulls every `kb_index_state.commit_sha` so each project's next index run rebuilds and fills it (technical/07 § "Source of truth and sync").
- `kb_health_reports(id, project_id, commit_sha null, documents int, findings jsonb, source, created_at)` — technical/07 § "Librarian pipeline" step 6 names this table and no migration created it until **0018** (WP-18b). `findings` is `[{kind, path, detail}]`, the vocabulary the `LibrarianProposals` artifact uses **plus `invalid`** (WP-57: a document the parser refused, read from `kb_index_refusals`; the artifact's own schema is deliberately not widened, because a Librarian reads indexed pages and cannot observe a refusal) **and `unresolved_paths`** (WP-58: a page whose `paths:` globs match nothing in `kb_index_state.path_witnesses`, which is technical/07 step 3's *"flag the document"*; not in the artifact's vocabulary for the same reason), and `documents` is how many indexed pages the pass looked at — so a report of no findings over no documents is distinguishable from a clean vault. It is an observation: nothing in the platform deletes or edits a page because a report names it.
- `code_files(project_id, blob_sha, path, language, symbols jsonb)` PK `(project_id, blob_sha)`; `code_maps(project_id, commit_sha, focus_hash, token_budget, map_text, created_at)`.
- `readiness_evaluations(id, project_id, level, criteria jsonb, evaluated_at, source, notices jsonb)`. `criteria` is `[{id, passed, evidence, unlocks, detected_by, not_checked?}]`; `not_checked: true` (BD-026's 2026-10-06 amendment, always with `passed: false`) marks R1, R2 or R6 that the run workspace could not run — it does not block its rung of the level, and a row without the key reads as checked. `notices` (migration 0079, WP-143) is `[{code, severity, message}]`, the platform's notices beside the criteria — the CI-rules **warning** `ci_rules_skip_agent_branch` (the default branch's CI rules give an `agentic/` branch no test job in a push or a merge-request pipeline), the **note** `ci_rules_not_seen` (what the evaluator could not read), or the **note** `verification_mode_ci_suggested` (a criterion was not checked and the project has a CI configuration: `verification.mode: ci` would read it from there; platform text only); never a criterion, never a level, `[]` for every row before it; `message` quotes bounded, redacted job names and one rule from the CI file (untrusted). `source` is `discovery` (WP-21, the onboarding run), `rediscovery` (WP-94, Q107 (a): a maintainer's re-evaluate — a second discovery task, keyed `onboarding-rediscovery-<latest evaluation id>[-<attempt>]` so the first run's record stands) or `recheck` (WP-64, the re-check after an index run that read a new default-branch commit; it re-answers R3, R8, R9, R11 and R12, since WP-94 also R10 and R13 from named files — R3, R10 and R13 pass-only — and carries the other seven, saying so in their evidence).
- `shadow_reports(task_id, human_mr_ref jsonb, comparison jsonb, **redaction_count int null**, created_at)`. **Amended at WP-80 (migration 0057, PROGRESS backlog 131):** `comparison` is the **redacted** document — the same bytes the `ShadowReport` artifact stores, redacted once through the project's git binding redactor (TD-012 steps 1 and 2) — and `redaction_count` is that redaction's count; `null` is a row written before 0057, when the column held the pre-redaction copy and nothing counted. `human_mr_ref` is written from the same redacted document. **First written at WP-34**, twenty-six migrations after it was created: `comparison` is `shadowReportDataSchema`, parsed before the write and after the read, and the row is written in the same transaction as `shadow.report.created` and as the `ShadowReport` artifact. The primary key is the **task**, so a second delivery of the at-least-once report job writes nothing and appends no second event.
- `shadow_batches(id, project_id, requested_by, budget_usd numeric(12,6) null, created_at, completed_at null)` and `shadow_batch_tickets(batch_id, ticket_key, task_id null, base_sha null, human_mr_ref jsonb null, human_mr_source null, human_mr_merged_at null, human_mr_candidates int null, refused_reason null, **redaction_count int null**, created_at)` — **added at WP-34** (migration 0029), primary keys `id` and `(batch_id, ticket_key)`. A batch is the set of tickets somebody selected on one day, which `shadow_reports` (a row per task) cannot express and which product/19 §13's *"aggregate report per shadow batch"* is about. `task_id` is null **exactly** when `refused_reason` is not (`shadow_batch_tickets_task_or_refusal`): Q82 (a) refuses a ticket whose comparison base the provider will not publish rather than running it against today's default branch, and such a ticket has no task at all. `base_sha` and `human_mr_source` are the other two halves of Q82 — the commit both diffs are taken against, and which of the two lookups found the merge request. `human_mr_merged_at` and `human_mr_candidates` are what the **match already knew and the report needs later** (added in the same migration at WP-34's review round 2): product/19 §16's review window runs *“to merge or last activity”* and the alternative to storing the merge instant is a fourth provider read per report, and the count is what lets the report say that the most recently merged winner **understates** the human's side when several merge requests name one ticket. `budget_usd` is `features.shadow_mode.budget_usd` **as it stood when the batch was created**, copied so that a later settings edit does not rewrite what this batch was allowed to spend. There is no aggregate column anywhere: the report per batch is computed from these rows on every read. **Amended at WP-80 (migration 0057, backlog 131):** `human_mr_ref` is the provider's merged-merge-request entry passed through the project's git binding redactor before it is written, and `redaction_count` counts that pass (`0` for a ticket with no merge request, `null` for a row written before 0057).
- `history_bootstrap_batches(id, project_id, requested_by null, merge_requests int, batch_size int, days int, cap_usd numeric(12,6), estimated_usd numeric(12,6), status, detail null, created_at, completed_at null, recovery_attempted_at null)` and `history_bootstrap_chunks(id, batch_id, chunk_index int, task_id, merge_requests int, tickets int, commits int, redaction_count int, truncated bool, recorded_at null, proposals int, refused_proposals int, merge_requests_read int null, created_at, recovery_attempted_at null, abandoned_at null, detail null)` — **added at WP-35** (migration 0030), `recovery_attempted_at` on the batch at WP-36 (0032), the chunk's `recovery_attempted_at`/`abandoned_at`/`detail` at WP-48 (0036) and `merge_requests_read` at WP-66 (0052). A **batch** is one history bootstrap an operator started (product/19 §18, product/06 step 3b); a **chunk** is one mining run of it — a task of its own on `HISTORY_BOOTSTRAP_TEMPLATE`, created in the chunk's transaction, which is why `task_id` is `not null` and `(batch_id, chunk_index)` is unique. The batch copies `merge_requests` (the N asked for), `batch_size`, `days`, `cap_usd` and `estimated_usd` **at creation**, for `shadow_batches.budget_usd`'s reason: the figure shown beside a batch's spend has to be the one that applied to it, and the estimate is re-derivable from the three inputs beside it. `status` is `text` with a check (`collecting`, `mining`, `completed`, `empty`), and `detail` is **platform** text — why a batch is `empty` or what the collection left out — never a provider's words. The chunk's `merge_requests`, `tickets`, `commits`, `redaction_count` and `truncated` are the **platform's** count of what the collection put in that run's sample (`tasks.history_sample`, where the text itself lives), kept here so the batch screen never reads a megabyte of somebody else's review comments; `redaction_count` is counted over the text as it was **read**. `proposals` and `refused_proposals` are written once by the recorder, in the same `markChunkRecorded` call that stamps `recorded_at`. **`merge_requests_read` is the model's claim, not the platform's count** (WP-66, PROGRESS backlog 102): the historian's `HistoryFindings.merge_requests_read`, written by that same call and by nothing else, and stored **bounded by what the run was shown** — the recorder writes `min(claim, merge_requests)`, because the artifact schema admits any non-negative safe integer and a model that claims 10¹² would otherwise overflow the `integer` column or publish a pair that reads more than it was given; `history_bootstrap_chunks_read_within_shown` holds the column to `0 ≤ merge_requests_read ≤ merge_requests` behind the recorder. It is `null` for a run that has not reported (and for a run recorded before migration 0052), which is not *read nothing*; the batch DTO publishes the **pair** — the claims summed and the platform's count of what exactly those runs were shown — never a ratio, and labels it as the model's. Two facts the migrations argue for rather than a column list alone. **`history_bootstrap_batches_one_live`** is a partial unique index on `(project_id) where completed_at is null`: a batch's ending is **one fact with two columns** (`history_bootstrap_batches_completed_pair` ties `status in ('completed','empty')` to `completed_at is not null`), and the index is what decides two start commands that race past the command's own `already_running` read — a second batch would re-read the same history and spend a second cap; the adapter maps its `23505` to `LiveHistoryBootstrapError`, and it is also why a batch nobody can complete is a permanent refusal for its project, which is what the recovery columns exist to end. **`history_bootstrap_chunks_counts_need_a_report`** is `recorded_at is not null or (proposals = 0 and refused_proposals = 0 and merge_requests_read is null)` (re-declared under the same name by 0052 to take the new column): a count of what a run proposed — or read — is a **claim about a run that reported** (standing rule 18), so a zero before `recorded_at` would publish silence as a finding. `history_bootstrap_chunks_one_ending` (a chunk is recorded **or** abandoned, never both) and `history_bootstrap_chunks_abandon_pair` (`abandoned_at` and its platform-text `detail` together) are WP-48's: an abandoned chunk is the recovery's ending for a `record` wake-up that never took, `completeIfDone` counts it as reported so the batch can finish, and the batch then shows `chunks_recorded < chunks`. Both tables are **operational, not knowledge**: nothing here is rebuilt from a repository, the proposals the runs wrote live in `kb_proposals` with source `history`, and a batch's spend is summed from `cost_entries` through its chunks' tasks rather than stored.

## Storage sizing (from research/07 measurements)
~1–2 MB and 1–3 k rows per run; 1 000 runs/month ≈ 2 GB and 3 M rows/month. Partitioning from day 1; storage gauge = `pg_total_relation_size('run_messages')` on the org dashboard (Q13-b).

## Retention and backups
- Default keep forever. Optional `APP_TRANSCRIPT_RETENTION_DAYS` drops whole `run_messages` partitions older than N days; metadata, artifacts, events, cost stay.
- Compose ships a `db-backup` sidecar (`pg_dump` daily/weekly/monthly rotation) with a documented restore; pgBackRest/WAL-G as a later profile.
- Docker: mount `/var/lib/postgresql` (not `/data`) for the `postgres:18` image (research/07 gotcha).

## Redaction (TD-012)
Single persistence path function applied to `run_messages`, `integration_actions`, `events.payload`, `config_audit`: (1) exact match of every secret value the platform injected into the run, (2) regex rules derived from gitleaks' rule set (generic API keys, private keys, cloud/provider tokens, JWTs, connection strings), (3) optional entropy heuristic; placeholders `[REDACTED sha256:ab12cd]`; counts and `redaction_log` rows; originals never stored.
