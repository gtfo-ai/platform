# 05 — Workspaces and security

> Round 2 design. Decision: TD-021, TD-012, TD-022. Sources: research/10, research/05, BD-021, BD-022, BD-024, BD-025.

## Workspace lifecycle
1. **Mirror:** per project, a bare mirror on the `repo-cache` volume; `git remote update --prune` before each run; gc disabled while workspaces reference it. **This is the launcher's mirror and serves run workspaces only.** It is written by a helper container (the volume is never mounted into the launcher's own filesystem) and can therefore be advanced only by the component TD-021 allows near the Docker socket. The knowledge indexer reads a **second**, platform-side bare mirror that the platform process clones and fetches itself — TD-026 — with gc left **on**, because nothing alternates to it. Two mirrors per project is the decided state, not an oversight.
   **WP-74 (a run with no checkout):** a run whose tool list holds no file tool and no shell — on this build the ask and the history miner — is given `WorkspaceSpec.repo: null` (`runNeedsCheckout`, `packages/infrastructure/src/workspace/spec.ts`). Its create skips this step and the clone below, runs no `mirror-` and no `clone-` helper, mounts no `repo-cache`, puts no git host on its egress list, and the runner sends the launcher no credential request. It **keeps** everything else in step 2 — volume, network, sidecar, control socket and the platform skills, under an empty `/work/repo` the prepare helper creates — because the CLI runs inside the container and a run has no other transport; running it in the platform process is ruled out by TD-021's decision body (*"spawns `claude` inside the container"*), not merely by its WP-15g amendment. `export` refuses such a workspace by name.
2. **Create (launcher):** volume `ws-<run>`, network `run-<run>` (`internal: true`), egress sidecar with the rendered allow-list, workspace container (`platform-runtime` image: Claude binary pinned to the SDK version, git, CLIs; no platform code) with hardening flags; `git clone --shared --branch <default> /cache/<project>.git` (**amended at WP-14**: cloning *from* the mirror sets the same `objects/info/alternates` entry `--reference` would and needs **no network at all**, so the one step that handles repository content at create time runs with `NetworkMode: none`; the origin URL is set afterwards. The consequence is unchanged and is the reason gc stays disabled: every object older than the run lives in the mirror, so anything that reads the workspace later — the export included — must mount the mirror read-only too. **WP-75:** "the mirror" is the project's **own**, never the volume: the run container and the export helper mount `repo-cache` with `VolumeOptions.Subpath: <key>.git` at `/cache/<key>.git` — the path the alternates name — so a run sees no other project's mirror, which is TD-021's *"per-project bare mirror ro at `/cache`"* as written. The sub-path exists because `updateMirror` runs before `create` and the clone helper, which keeps the whole volume read-only for that reason, refuses a missing mirror by name before any container that mounts one is created; the mirror helper keeps the whole volume read-write because it creates `<key>.git`. **The export helper's git reads no configuration the run wrote** (WP-75, folding backlog 152): the tree, its `.git/config`, its hooks and its `.gitattributes` are the agent's, and before WP-75 run-planted hooks, a `core.fsmonitor`, a clean filter, `commit.gpgSign` + `gpg.program`, a `pushurl`/`insteadOf` redirect and a repository `credential.helper` all ran there (measured), in a container holding the push credential with a route to the git host. So the helper refuses a `.git` that is a symlink, a gitfile or a linked worktree by name; reads only the platform's configuration (`GIT_CONFIG_NOSYSTEM=1`, a `GIT_CONFIG_GLOBAL` it writes, and a `.git/config` it **replaces** with the repository format and origin URL read off the platform-written mirror); removes `.git/hooks` and runs every git command with `-c core.hooksPath=/dev/null`; pushes to the mirror's URL by name rather than through a remote; and refuses by name a checkout holding a **nested repository** — a `.git` directory or gitfile below the top level, found before the first git command that reads the work tree — because that repository's own config is one the helper does not replace, and `git add -A` was measured running its `core.fsmonitor`. The helper runs as the run's own uid, so a directory the run left unlistable once hid a nested repository from that walk while git reached it through the index: the tree is normalised to the owner's `u+rwX` first, and a walk that still fails or prints an error is itself a refusal. The export also stops the run container before its helper exists, so nothing the run left running can change the tree between the checks and the push. A gitlink with no `.git` behind it has no configuration and is not refused, so a project with submodules exports (orchestrator's ruling; both directions in the e2e). An attribute naming a filter no configuration defines runs nothing — measured by the same e2e. What this does **not** claim: the helper's git still reads the run's index, objects and attributes); checkout of the task branch for re-entries (a branch the remote does not have yet — a task's first run — is created at the default branch's head); **a shadow task's base commit is checked out detached, and one the mirror does not hold refuses the create by name** (`invalid_spec`, terminal) rather than running on another tree — WP-105, Q82 (a): until then the commit travelled as a branch name and the create-a-branch fallback turned a missing base into a branch named after the sha at the default branch's head; the **tracked-path listing** the path guard reads, taken from the fresh checkout by a no-network helper after `create` and before the runner starts the CLI (WP-99, § "Command and tool policy"); `.agentic/workspace/setup` script executed if present (from the default branch); readiness commands verified during discovery reused here.
3. **Attach (TD-025):** the container's entrypoint is the run shim listening on `/ctl/ctl.sock` (per-run sub-directory of the shared `ctl` volume). The runner connects, authenticates with the run token, and its `spawnClaudeCodeProcess` sends `spawn{command,args,cwd:/work/repo,env}`; stdio, stderr, signals and the exit code travel as frames. If the connection drops, the shim terminates the CLI. The workspace has no network path to the platform; the git credential helper uses the same socket to obtain its run-scoped token.
4. **Run:** hooks and policy on the platform; git pushes only to `agentic/*` with the run-scoped token from the broker; per-run port `APP_PORT` for dev servers.
5. **Finish:** commit/push WIP on interruption (`wip:` commit); remove container, sidecar and network; keep the volume per retention (3 days default, 14 days for paused/taken-over); `workspace.destroyed` on purge. **WP-27 (as measured):** the 14-day window is not a relabel — on Engine 29.7.2 / API 1.55 a volume label cannot be updated (a re-`create` silently keeps the old label and `volume update` refuses anything but cluster volumes), so the launcher writes a `hold-<run-id>` marker volume carrying the later `keep_until` and the sweep takes the later of the two instants.
6. **Export:** branch pushed + optional tarball (excluding `.git`, `node_modules`) written to the shared export volume; both files are **served, not copied** (Q93, WP-44): the redacted transcript at `GET /api/runs/:run_id/transcript.jsonl`, a JSONL rendering of `run_messages` (nothing writes `blobs`, so it lasts exactly as long as the transcript), and the tarball at `GET /api/runs/:run_id/export.tar`, read through the realpath guard and removed 14 days after it was written by the launcher's own retention sweep — the workspace's own retention; resume instructions posted to the ticket. **WP-14:** the tarball also drops any symlink whose target escapes the workspace — an archive is unpacked somewhere else, and a link out of it is a write outside the workspace on whatever machine unpacks it — and the count is reported. The *transcript* half is the platform's, not the launcher's: the transcript lives in `run_messages`, and `WorkspaceProvider.export` returns the branch, the commit and the tarball.

## Hardening flags (per run container)
`user: 1000:1000`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `read_only: true`, `tmpfs: /tmp (size from config)`, `mem_limit`, `cpus`, `pids_limit`, `init: true`, `stop_grace_period: 20s`, `runtime: runc|runsc`, no port publishing, no host mounts, no Docker socket. Timeouts: stage wall clock → SDK `interrupt()`/abort → `stop` (SIGTERM) → SIGKILL.

## Network policy

> **The *platform process* has an egress allow-list too, since WP-51** (PROGRESS backlog 48). This section is about the run container and was, until then, the only egress control in the product: the server process that holds every decrypted credential would call whichever host an `integration.write` caller had typed into a binding's `base_url`. `APP_INTEGRATION_HOSTS` (technical/06 § "Outbound: actions", technical/12) is the other half — operator-declared, exact, empty and therefore closed by default, refused at `POST /api/integrations` and again inside `IntegrationActionExecutor`. The two lists are separate on purpose: this one is rendered per run from what the *stage* needs, that one is instance configuration about what the *platform* may dial.

Workspace has no default route; the sidecar allows: Anthropic API host (or the configured Bedrock/Vertex/proxy host), the git host — and, for a deploy-key run only (WP-146, TD-028 decision 13b), `altssh.gitlab.com`, reached by `CONNECT` on port 443 like every other host, never port 22 — package registries (operator-declared since WP-82, not from discovery — see the amendment below), read-only observability hosts when the stage may use them; everything else denied and logged (denied hosts shown in the run detail as a hint). Telemetry hosts blocked; `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` reaches the `claude` process through `platformEnvironment` since WP-104 (PROGRESS backlog 285) — the run shim replaces its child's environment with the spawn frame's, so the copy on the run container reaches the shim and nothing it starts. **The same was true of the proxy itself until WP-118**: `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` were set only on the run container, so the CLI had no route off the `internal: true` network at all — measured, a real `claude` retried its first request until the wall clock stopped it and **nothing reached the sidecar** (PROGRESS backlog 342). Since WP-118 the launcher answers the proxy, `HOME`, `CLAUDE_CONFIG_DIR`, the image's `PATH` and the credential helper beside `claudeCodePath` and the runner composes them into the CLI's environment (TD-025's amendment); the same measurement now shows the CLI's `CONNECT api.anthropic.com` at the sidecar. What the variable changes about the hosts the pinned CLI contacts is still unmeasured (WP-33, PROGRESS backlog 137); **what it contacts up to authentication is measured** (WP-133): under the shipped list, with an obviously fake `CLAUDE_CODE_OAUTH_TOKEN` in `local` mode, every host the CLI asked for was on the run's list and none was refused, and the API refused the token with 401 — an allowed `CONNECT` is below the sidecar's `Notice` log level, so the log shows only that nothing was refused, not which allowed hosts were used (`launcher-control-plane-check.mjs`, the `backlog 137 (local)` records). What a run that *is* authenticated contacts after that still needs a credential; **WP-140** built the leg that measures it (`launcher-control-plane-check.mjs --real-model`, one turn with the product owner's subscription token from the environment), whose sidecar alone is rendered at `LogLevel Connect` — a check-only option no configuration can set — so its log names the allowed hosts too (with a fake token: `api.anthropic.com`, allowed, nothing else seen). A production sidecar stays at `Notice`. Phase 2: Envoy sidecar injecting the Anthropic key and git token so neither is present in the container.

**Amended by WP-82 (PROGRESS backlog 140).** *Package registries* do not come from discovery. They are `APP_RUN_REGISTRY_HOSTS` (technical/12): operator-declared, exact host names, empty and therefore **closed** by default, with no wildcard, and not settable through the API or `.agentic/config.yml`. They join a run's list **only** when the run may install from a lockfile, which means it holds `Bash` and its effective `allow` still carries a `LOCKFILE_INSTALL_ALLOW` entry. The `verification` and `implementation` baselines carry those entries. A `read_only` run never gets a registry, whatever is declared (`runMayInstallFromLockfile`, `packages/infrastructure/src/workspace/spec.ts`). Discovery has existed since WP-21 and derives no host, and a list read out of a repository would let repository content widen a run's egress. The residual is stated: a declared host is reachable by every process in the run container, not only by the install command, so a private mirror is the narrower thing to declare. *(Until WP-82 the sentence above read "package registries for the project's ecosystems (from discovery)". Nothing produced one, so the lockfile installs WP-54 allowed had nowhere to fetch from.)*

## Credentials and identity
- Platform: long-lived group/project access token or service account per GitLab, Jira API token, Slack tokens, Sentry Internal Integration token, Loki credentials — encrypted at rest, decrypted only in the process that uses them, never logged.
- Per run with a checkout: the **runner** mints a GitLab project access token through `IntegrationActionExecutor` against the project's git binding (one `integration_actions` row per mint and per revoke; `write_repository` for a writing run, `read_repository` only for a read-only one; a 24-hour request that GitLab grants as a date, so the token lives 24–48 h — `expiryForTtl` rounds up to the next midnight UTC that covers it) and carries it to the launcher on the create request, which holds it for the mirror fetch and the take-over export push; the workspace's credential helper requests it through the run shim (`cred.get`) over the control socket, and the **runner** answers from its own copy, exact host only, only while the run is active; the runner revokes it once, after `endRun` returns or when the create fails; a terminal run whose credential no audit row confirms revoked — the runner died between mint and revoke, or that revoke failed — is revoked once more, **by address** from the mint row's `revoke_id`, by the recovery pass a pass interval after the run ends, and a provider `not_found` there is recorded as *unconfirmed*, never as revoked (WP-77, PROGRESS backlog 155; `packages/application/src/recovery/run-credential.ts`). A binding that cannot mint refuses a writing run and never hands over its own token; read-only stages get no git write token at all; a shadow task's runs get a read token, and every revocation is performed for a shadow task too (Q98 (a); revoking only removes access). *(Amended by WP-76 — TD-028's WP-76 amendment; until then this read "the launcher mints … and hands it to the runner", which the launcher, holding no binding, could not do: PROGRESS backlog 133.)* Loki/Sentry read credentials injected as env only for stages whose tool policy includes them.
  - **Amended by WP-80 (TD-028 decision 10, TD-012's M5 amendment).** *Revoked through the integration that minted it.* The teardown revoke and the recovery revoke both build their adapter from the **minting** `integrations.id` — the mint row's `integration_id` — whether or not the project still binds it (`PipelineIntegrationsPort.forMintingIntegration`), so a project unbound from, or re-bound away from, the integration that minted is still revoked on the host that issued the token, with one audit row under that integration's id. A revoke is never sent through any **other** integration (WP-73b's refusal stands, now structural). When the minting `integrations` row itself is gone there is no host the platform may call: the credential is **reported** (one warning per address per process) and lives to its expiry. A `not_found` answer stays *unconfirmed*. *Redacted everywhere by its shape.* The minting process records a **non-secret shape** of every minted value — the prefix the provider declares, a closed character class and the exact length, never a character of the random part — in `minted_credential_shapes`, in the transaction of the mint's own audit row; every product process compiles one pattern rule per unexpired shape at start and on a refresh timer (`MINTED_CREDENTIAL_SHAPE_REFRESH_MS`) — and since WP-107 (TD-012's M6 amendment (1)) on the commit itself: the same transaction publishes a hint on the transactional broadcast, which every process subscribes whatever its `ROLE`, so a shape reaches another process in the time a `NOTIFY` takes rather than up to one five-second interval later, with the timer kept as the guarantee for a hint a reconnecting listener missed; twelve consecutive failed re-reads (a minute at the default interval) are reported once at `error` — so a run credential quoted into a merge-request comment, a CI log or a ticket is redacted by `app` as well as by the runner that minted it, whatever prefix a GitLab administrator chose. A provider that declares credential minting must declare a stable shape at registration or it is refused there, by name; a minted value that does not have the declared shape is revoked and refused, like one too short to redact. GitLab's shape prefix is the binding's `token_prefix` (default `glpat-`), which an operator on an instance with a custom personal-access-token prefix sets to that prefix. The rule over-redacts any other token of the same shape, which is the safe direction. *(Until WP-80 the exact-value registry of the minting process was the only defence outside GitLab's default `glpat-` shape — PROGRESS backlog 259 — and an unbound credential was reported and left live — backlog 156 half 3.)*
  - **Amended by WP-137 (TD-028 decision 13, BD-025's and TD-021's amendments of 2026-10-03 — the founder's answer to Q98 (b)).** *A static run credential, opt-in, where the provider cannot mint.* An integration that declares `run_credential: static` (GitLab; refused beside `mint_credentials: true`) gives each of its runs a dedicated `run_token` — a dedicated user's personal access token, Developer on the one bound project, `read_repository` + `write_repository` — instead of a minted one, on the **same** path: `runCredentialWrites.mint` answers `static`, the runner registers the value with the run's injected-secret redactor exactly as it does a minted one, the create request carries it (`source: static`, scope `push`, the declared expiry), the launcher's broker holds it and the runner answers `cred.get` from its own copy — never an environment variable, the image, the prompt or a log. No provider call is made, so there is no `mint_credential`/`revoke_credential` row and the recovery revoke never finds the run; `runs.credential_source` (`minted` | `static` | `none`, migration 0078) and `credential_integration_id` say which credential a run had. It is a declared secret field, so every process that loads the integration redacts it by exact value, and the adapter is built **without** it (`gitlabAdapterInput`), so no platform API call carries it. A shadow task gets **no** credential (it is push-capable and cannot be narrowed to the read Q98 (a) admits). The run's start refuses — terminally, before the create, naming the integration — a missing token, one equal to the API token (the decrypted values compared), a configuration fault and an expiry passed; the write refuses the same and a second project's binding. **What is lost, in decision 13 item 5's words**: no per-run revocation and no run-lifetime bound — the token lives to its declared expiry; code in the container can read it through the helper, and the run's egress admits the git host, so it can be pushed **into the repository itself**, where, unlike a revoked minted token, it still works; its reach is bounded by the dedicated user's memberships (one project) and its scopes (`read_repository`/`write_repository` grant no REST API), not by the platform; a read-only stage holds a push-capable token. The platform's one added control: the dependency gate searches each merge request's added lines for the exact value (`addedLinesContain`) and a hit parks the task *Needs human* with a brief that says **rotate the run token** and never prints it. The sentence above — *"A binding that cannot mint refuses a writing run and never hands over its own token"* — stands for the binding's own token; the refusal now names both settings. **A defence-in-depth loss, stated (review round 1):** the launcher's BD-021 check — *a read-only spec may not hold a push credential* (`createRunRequestSchema`, `RunCredentialBroker.hold`) — now admits a push credential labelled `source: 'static'`, and the label is the **runner's** word: the launcher holds no integration and cannot tell a static token from a minted one. Before WP-137 that check was a second, independent refusal of a runner that sent a push token to a read-only stage; it is now one only for credentials labelled `minted`. The runner remains the one place that decides the label (`runCredentialWrites.mint`, from the integration's own configuration), so a compromised or defective runner can hand a read-only stage a push-capable token the launcher no longer refuses — which, for a static integration, every read-only stage holds anyway (decision 13 item 5).
  - **Amended by WP-141 (TD-028 decision 13a, BD-025's and TD-021's amendments of 2026-10-04 — the founder's *"let the admin decide"*).** *The operator's own repository-only token.* `run_token_owner: dedicated_user | operator` on a static GitLab integration (default `dedicated_user`, the paragraph above unchanged). For `operator` the run token is the operator's own personal access token with `read_repository` + `write_repository` only, and the role check is **replaced**: any role is accepted, because protection, membership and settings are API operations a repository-only token cannot perform. Two checks stand in for it. The **scope proof**: the probe makes exactly one `GET /user` **with the run token** (`GitProviderPort.runTokenApiAccess`, on a transport built for that call alone, through `IntegrationActionExecutor` as `check_run_token_scope`, the value in no audit row) and refuses unless GitLab answers `403` with `error: insufficient_scope` (any other 403 — a proxy, a firewall — is refused); it is the platform's only use of a run token against a provider API, and `emitted-secrets.test.ts`'s census admits exactly that request. The **push control**: with the API token, the bound project's stored `projects.default_branch` must be protected with push **No one** and force push off by **every** matching rule, exact and wildcard, combined most-permissive as GitLab applies them (`branchPushProtection`, which lists the project's rules) — read at the probe and **again before every create** of a run that receives the token (`runCredentialWrites.mint`, `check_default_branch_protection`, one read per run), so a protection loosened after the probe refuses the next run `invalid_spec`, by name, before its workspace exists. **What is lost, in decision 13a item 3's words**, in addition to decision 13 item 5: the token reaches **every repository the user can access**, not one project — a read-only stage holds read access to all of them and a writing stage push access to every unprotected branch of all of them; a second binding is refused on the integration, but another integration holding the same value is not detected; `read_repository` also grants the repository files API, a read the platform does not use; pipelines on the branches and tags a run pushes run under the operator's identity, and a tag matching a protected-tag rule open to Maintainers receives protected CI/CD variables (the guides tell the operator to protect release tags with *No one*); group-level protected branches are not read; the scope proof is made at the probe only, not per run. A third form, a project SSH deploy key (`run_credential: deploy_key`, decision 13b), is WP-146's.
  - **Amended by WP-146 (TD-028 decision 13b, BD-025's and TD-021's amendments of 2026-10-04).** *A project SSH deploy key, which never enters the run container.* `run_credential: deploy_key` on a GitLab integration (gitlab.com only; a self-managed `base_url` is refused by name, because the egress sidecar admits no SSH port and tinyproxy's `ConnectPort` is global) seals an **unencrypted OpenSSH Ed25519** private key (`run_ssh_private_key`) beside its declared public key (`run_ssh_public_key`); the write derives the public key from the seed and refuses a mismatch, a passphrase, another key type, `mint_credentials: true` and a `run_token` beside it. `runCredentialWrites.mint` answers `deploy_key` (no provider call, no audit row, `runs.credential_source = deploy_key`); the **runner** holds the parsed key for the run's lifetime (`packages/infrastructure/src/launcher/deploy-key-signer.ts`) and the spec carries only the public route (`WorkspaceRepo.ssh`). The launcher writes the documented gitlab.com `known_hosts` to `/ctl/<run>/known_hosts`, and the run shim serves `/ctl/ssh-agent.sock` (`packages/infrastructure/src/runlet/ssh-agent.ts`): *list identities* is answered from the public key in its own environment, *sign* is relayed to the runner as an `ssh.sign` frame and answered from `ssh.sign.reply`, every other agent request is `SSH_AGENT_FAILURE`, and the relay is bounded per run and live only while the child runs. The CLI's git gets `GIT_SSH_COMMAND` (`-F /dev/null`, the agent socket, `StrictHostKeyChecking=yes` with `HostKeyAlias=gitlab.com`, `ProxyCommand=agentic-runlet connect --proxy <sidecar> %h %p`, `-p 443`) and one `url.ssh://git@altssh.gitlab.com:443/.insteadOf = https://gitlab.com/` pair through `cliEnvironment`, and **no** HTTPS credential helper; `altssh.gitlab.com` joins that run's egress list only. The shim's credential socket never answers with the key (the broker refuses `cred.get` for it). The launcher's mirror and export helpers fetch and push over SSH with the key in a `0600` file on their own tmpfs — the same exposure class as `GIT_PASS` in their environment — while the platform's vault mirror (TD-026) keeps HTTPS with the binding's API token. **What is lost, stated** (decision 13b item 8): no per-run revocation (removing the key from the project is it); a read-only stage can sign pushes; the container holds a **signing oracle** for the run's lifetime, which can authenticate to any SSH server the run's egress admits (only `altssh.gitlab.com`), so its reach is every project the key is enabled on — and nothing after the run ends. The added-lines search covers the key's private text. Known residual: the agent owns `/ctl/known_hosts` (the control directory is uid 1000's), so it can replace the pinned keys — which only lets it connect somewhere the sidecar already admits.
- Composite identity: every outbound action records the bot identity and the requesting human (BD-025).

## Command and tool policy
- Three lists per stage merged from platform defaults (org maximum) and project config; `PreToolUse(Bash)` evaluates: block → deny; allow → allow; else `ask` → Question to a mapped member/maintainer (timeout = question timeout; unattended default deny).
- File guards: writes limited to the workspace; under a protected path (`.agentic/`, `.claude/`, `CLAUDE.md`, `.gitlab-ci.yml`, tests; BD-024) a **new** file is allowed and an **existing** one only when the latest plan's `protected_path_changes` lists it; `.agentic/`, `.claude/` and `CLAUDE.md` writes are flagged for Code review (BD-025). *(Amended by WP-99. This read "allowed only when the plan lists them", which refused every new test, and the plan's list never reached the guard: PROGRESS backlog 279.)* **Where "existing" comes from:** it means tracked at the **merge base of the run's checkout and the default branch**, the base the merge request's diff is computed against, so a test an earlier run of the same task added is still new *(the orchestrator's amendment at WP-99 review round 1; it first read "tracked at the run's checkout ref")*. The hook runs outside the container and cannot `stat` it, so the launcher lists it right after the clone (§2), in a helper with no network, the workspace and the project's own mirror mounted read-only. It returns the regular files at that commit matching the run's protected patterns plus every symlink and submodule there, bounded at 100 000 entries read, 10 000 and 1 000 carried. **Fail closed:** a listing that is missing, unreadable, over a bound or not UTF-8, or with no default branch or merge base, counts every protected path as existing, and a target at or under a symlink or submodule at that commit is judged as an existing **protected** path whether or not its spelling matches a pattern (WP-104, PROGRESS backlog 283). A path with a `.git` segment anywhere is denied in every project, because git's configuration is not repository content, and the CLI's environment sets `core.fsmonitor=false` for every git it starts (WP-104, PROGRESS backlog 282). Content is refused by the redactor's current corpus, the minted-credential shapes included (TD-012's M6 amendment (3)). technical/04 § "Hooks and policies" has the whole rule; the CI gate's tamper check is the enforcement for the branch.
- Git guards: no push outside `agentic/*`, no force, no branch deletion, no history rewrite; server-side protected branches verified by the readiness check (R9).
- Network/tools: MCP servers limited to the stage's list; `strictMcpConfig`.

## Untrusted input handling (BD-022)
All external text is delimited as data in prompts; the Reviewer checklist includes "instruction-like content in inputs"; agent configuration (`.agentic`, `.claude`, `CLAUDE.md`, `.mcp.json`) is read from the default branch snapshot, never from the task branch; feedback/answers/approvals require mapped identities verified from webhook payloads.

## Redaction (TD-012)
Exact-match of injected secrets → gitleaks-derived regexes → optional entropy; applied before every persistence and before broadcasting to SSE; counts recorded.

**Amended by WP-80 (TD-012's M5 amendment).** Step (2) carries, beside the gitleaks-derived rules, one rule per unexpired **minted-credential shape** (`minted_credential_shapes`, technical/03), compiled into every process's pattern redactor at start and on a refresh — never a stored copy of a minted value. The rule's placeholder is the ordinary `[REDACTED sha256:…]` and its hits are counted like every other rule's.

**Amended by WP-107 (TD-012's M6 amendment (1) and (2)).** *On commit.* The refresh is triggered by the commit that records a shape — a hint published in that transaction on the transactional broadcast and subscribed by every process whatever its `ROLE` — and the five-second timer stays as the guarantee; a run of twelve failed re-reads is reported once at `error`, and the process keeps the rules it last read. *The repository reading.* What the reading of `.agentic/` stores — the prompt files of `.agentic/prompts/` and an invalid configuration's detail — goes through step (1) as well, over the **decrypted credentials of every binding of the project** (named like a binding's own, `<provider>:<integration>:<field>`), before step (2). A credential the platform holds for one of the project's bindings, committed to a prompt file in a shape no rule knows, is therefore not stored in `project_repository_config.prompts`, not sent to the model and not kept in `runs.user_prompt`. While any of the project's integrations has credentials that cannot be decrypted, the reading still stores the configuration (a broken binding never keeps a restriction from applying) and stores **no** prompt texts — neither new ones nor the previous reading's — naming the integration on `POST …/config/refresh`'s `prompts_withheld` and in an `error` log line (PROGRESS backlog 358). What it cannot do is un-leak a secret committed to the project's history; it stops the platform making more copies of it. *(Until WP-107 the reading was pattern-redacted only — PROGRESS backlog 316 — and a shape reached a process that did not mint it up to one interval late — backlog 276.)*

**Amended by WP-121 (TD-012's M7 amendment).** *Every credential the platform holds for the project.* The exact-value set of the repository reading is the bindings' decrypted `secret_ids`, **plus** each provider's declared secret fields (`secretFieldsOf`, the catalogue's `secretFields`) found in a binding's configuration — `integrations.config` with `bindings.config` over it, which only a row written before WP-100 or by SQL can carry (backlog 362) — **plus** the decrypted credentials of the organisation's communication accounts, which no project binds (backlog 364); a config-held copy that differs from the sealed value of the same field keeps its own placeholder name (`…:<field>.config`). An organisation account whose credentials cannot be decrypted withholds the prompt texts of **every** project, the direction WP-107 chose for a binding. *A reading says how it was redacted.* `project_repository_config.prompts_redaction` (migration 0073) is `patterns` for every row written before the migration and `exact` for every reading since; a `patterns` row serves **no** prompt text to the planner or to `GET …/config` (`snapshotOfRow`), and the process that runs the knowledge index re-reads every `patterns` project at start, eight per pass (`startPatternReadingReread`), replacing the row; a project whose repository cannot be read again keeps no prompt text and records why, and keeps the mark, so its next index run or `POST …/config/refresh` replaces it. *A withheld text is recorded.* `project_repository_config.prompts_withheld` stores why a reading serves no prompt text — the sentence and the integrations whose credentials could not be read — and `GET …/config` publishes it (`repository.prompts_withheld`); a run planned from such a reading freezes it on `runs.prompts_withheld`, served by `GET /api/runs/:id/prompt`, so a stage whose convention-append file is missing says why. The platform still cannot un-leak a credential committed to a project's history.

## Control channel (TD-025)
One Unix socket per run on the `ctl` volume: runner ↔ shim frames for spawn/stdio/signals/exit and `cred.get`; single authenticated connection; shim kills the child on disconnect; nothing listens on TCP in Docker mode. Kubernetes: same frames over TCP with mTLS.

### Amendment (WP-53, 2026-09-23) — the control plane beside the data plane

*"Nothing listens on TCP in Docker mode"* is no longer true of the **launcher**, and the sentence stands for the run: TD-028 splits the transport in two, and only the control half is new.

- **Data plane, unchanged.** The runner keeps the static mount of the whole `ctl` volume and opens `<ctl>/<run-id>/ctl.sock` itself. No stdio, no `stdin`/`stdout`, and no `cred.get` round trip crosses HTTP.
- **Control plane, new.** The launcher exposes an HTTP surface for the operations that are request/response — create a workspace, end a run, report health, and since WP-103 list the runs it labelled and destroy one by its id (below) — on a compose network with `internal: true` and no published port that **only** the launcher and the runner container join. It is authenticated on every request with a constant-time comparison of `APP_LAUNCHER_TOKEN`, *in addition to* the network isolation, because a compose file is a deployment property and an authentication check is a code property — and this surface creates containers.
- Every operation is **idempotent on the run id**: a create for a run that already has a handle answers the stored handle rather than starting a second container. The record is this process' memory, so a launcher that restarted has forgotten. A create replayed across a restart, after the first one completed, is **refused at the run's network** (`409 … already exists`, `workspace_failed` to the runner) before anything else is made: no second container, the live run's shim token untouched, nothing rolled back. The first run's container keeps running with no launcher holding a handle; until WP-103 nothing bounded it — the lease ends the row, WP-77's recovery revokes the credential, neither stops a container — and since WP-103 the runner's orphan pass removes it once its run is terminal (the amendment below). *(Amended by WP-82, measured on Docker Engine 29.7.2 by `scripts/launcher-control-plane-check.mjs`, PROGRESS backlog 136. It read "would start a second container; what bounds that is one level up (`stage.execute` is `stately` per task, and the run lease ends a row whose process is gone)", and neither half held.)*
- The run container still reaches **nothing but its egress sidecar**: it is on a per-run `internal: true` network and joins neither the control-plane network nor the daemon's.
- **Which process may run an agent is configuration, never `ROLE`** (TD-028 decision 5): a worker subscribes `stage.execute` and `task.ask` only when it has a launcher URL and token. The consequence the decision's WP-53 amendment writes down is that gate evaluation is a branch of the same handler on the same queue, so a deployment with no configured runner also stops evaluating `ci_gate`, `rebase_gate` and `merged_gate`. Nothing is lost — the jobs are durable and are taken when a runner starts — and the queue depth is the visibility that trade rests on: since WP-86 it is `jobs_queued{queue="stage.execute"}` and its oldest age on `/metrics`, and `/readyz`'s `agent_runs: degraded` (`details.agent_runs: unserved`) once a job has waited five minutes with nothing claiming (technical/08, PROGRESS backlog 135).

### Amendment (WP-103, 2026-09-30) — a run container nobody holds a handle for is found and removed

TD-028 decision 12 (M6), closing PROGRESS backlog **286**. The idempotency above is **bounded by one launcher process**, and three producers leave a run's objects with nobody holding its handle. They were measured before the fix was chosen (`scripts/launcher-control-plane-check.mjs`, Docker Engine 29.8.1, `linux/arm64`; the numbers are in 286):

- **A create that outlives the runner's client timeout, with the launcher alive, completes.** Each of a stage's three start attempts is a new run id (the run row is failed and the stage re-enqueued), so a task accumulated **three** running run containers, three sidecars, three networks and three control directories holding a live token. **Since WP-103 the launcher abandons a create whose every requester closed its connection before the answer** — it ends what it made, with no export — and the check asserts nothing is left. A create that finishes in the instant between the client giving up and the launcher's socket seeing it is the residual, and it is the reaper's.
- **A launcher stopped or killed during a create** answers nothing (`engine_unavailable` to the runner) and leaves the helper it was running (`clone-<run>`, `prep-<run>`), the run's network and its workspace volume — no run container. The labelled helper keeps the run's control directory `run_alive` to the retention sweep and its volume in use, **for ever**. The launcher cannot clean up after itself here: a killed process runs nothing, and a stopped one was measured not to finish the create — under the daemon's default grace. Since WP-132 (PROGRESS backlog 425) `compose.yml` gives the `launcher` service `stop_grace_period: 60s`, and a stop during a create was measured to drain it and answer it 11.7–12.6 s after the signal; a kill, or a create longer than the grace, still leaves what is described here. And since WP-132 every helper carries the instance label as well as the run label (backlog 426), so one a dead launcher left — `export-<run>`, `ctlempty-<run>`, `ctlrm-<run>` included — is listed and removed with its run.
- **An unattached shim does not exit**: three were still running ten minutes after their creates, and nothing in the shim arms a timer on a socket nobody connects to.

The bound, stated where an operator reads it: the launcher gains **one authenticated read verb**, `GET /v1/runs`, answering the run ids of the containers — any role, running or not — carrying the run label **and this instance's label** (and, since WP-118's pre-review round, of the networks carrying both: a launcher killed after a create's first object leaves only the run's network, measured) (`com.agentic.instance`, the control volume's name), read from the daemon, never from its memory; and `POST /v1/runs/<id>/destroy` removes a run **by label** with no handle — every labelled container, the sidecar's configuration volume, the network and the control directory — keeping the workspace volume for retention, idempotently, serialised behind any create or end of the same run in that launcher. The **runner** decides which ids are orphans, because it reads `runs` and the launcher reads no database (TD-021): a run that is terminal and ended at least one recovery interval ago, or a run id with **no row** whose oldest container is older than an hour, is destroyed — one attempt per id per pass, at most fifty per pass, each a `warn` line naming the run id and a count on `orphan_run_workspaces_total{outcome}`. A live run's container is **never** removed, whatever its age: the lease sweep ends a dead run's row first, and the next pass then removes its container. The pass runs on the runner's own timer at `APP_INTAKE_RECONCILE_INTERVAL_MS` (`0` switches it off with the rest of the recovery). **Residuals:** two instances configured with the same control volume are one instance to the listing (they already share every run token); a container created before WP-103 carries no instance label and is never listed, so an older orphan is removed by hand (`docker ps --filter label=com.agentic.run`).

### Amendment (WP-85, 2026-09-28) — a human command reaches a live run through the database, not a route

TD-028 decision 9 (M5 amendment). A steer or a take-over's stop — and since WP-101 a run cancel, below — is issued to the process that serves the API, and the session it is for is held by another process — on the shipped topology, always: `app` never holds a run and `runner` serves no route. The command crosses through the **database**, and nothing here gains a listener or an address (the reason decision 2 exists):

- The API process **records** it — a `run_commands` row (migration 0060) in the command's own transaction, after reading the run live under a `for share` lock — and answers that the command was **accepted**, never that the model heard it (`POST /api/runs/:id/steer` is `202`).
- It wakes the lease holder with `pg_notify` on a broadcast topic keyed by `runs.lease_owner`. The holder applies the command to its own live-run register — a steer becomes a user turn and a `steer` transcript entry; a take-over's stop is `RunHandle.stop` with the export instruction, which then drives this page's step 5 and 6 — and stamps the row **applied**, or **refused** `register_miss`.
- The notification is latency; the **lease heartbeat is the guarantee**: every beat that renews a run's lease also drains that run's pending commands, so a command recorded while the holder's `LISTEN` was reconnecting is applied within one beat.
- A command still pending when the run ends is closed **`run_ended`** by the run's own ending, in its transaction, so it is never applied late. `ROLE=all` takes the same path, so there is one mechanism.

The data plane above is unchanged: the command reaches the session through the holder's in-process handle, which already owns the run's Unix socket.

### Amendment (WP-101, 2026-09-30) — a run cancel rides the same row, and which branch it takes

TD-028 decision 11 (M6 amendment), PROGRESS backlog 294. Until WP-101 `POST /api/runs/:id/cancel` ended the run **as a record** in the answering process and the session kept running — and spending — in the holder until it ended on its own. Now the cancel takes one of two branches, decided by the run's lease under an exclusive lock on the run row:

- **The lease is live** (`runs.lease_expires_at` in the future): the task is paused and a `cancel` row is recorded in `run_commands` (migration 0064) in one transaction, the holder is woken as above, and the answer is `202`. The holder applies it as `RunHandle.stop({ reason: 'cancelled' })`: the session is interrupted and the run ends `cancelled` **in its own process**, with the cost the interrupted turn's result reports (the runner reads that result within the interrupt's grace), charged once by the ordinary ledger handler. There is one terminal writer, the holder.
- **No live lease** (absent or expired): nothing holds the session, so the record is ended in place, as before, and the answer is `200`.
- **A holder that dies before applying** leaves the row pending; the lease sweep ends the run `lease_expired` and its `finish` closes the row `run_ended`. The run then reads `lease_expired`, not `cancelled`: no process confirmed the stop.
- **A steer behind a stop is never delivered**: once a run has a `cancel` or `take_over` row that was not refused, the holder's drain no longer lists that run's pending steers, and the run's ending closes them `run_ended`.

## Amendment (WP-22, 2026-09-12) — the images exist, and two residuals they exposed

**The run container has no host mount.** §2's `platform-runtime` image is
`docker/runtime.Dockerfile`: the `claude` CLI pinned to the SDK version the platform runs (both come
out of one `pnpm install --frozen-lockfile`, so they cannot drift), the six agent CLIs, and the
bundled `agentic-runlet` as the entrypoint — one file with no runtime dependencies, held to that by
`scripts/assert-runlet-bundle.mjs` during the image build. With it, `WorkspaceImages.runtimeSourceDir`
is `null` and the create body carries **no binds at all**, which
`test/e2e/workspace/docker-workspace.e2e.test.ts` now asserts against the daemon's own record rather
than against the argument vector. Until WP-22 that same case asserted the opposite — one bind, the
repository at `/repo` — which is what "the one hole" in `hardening.ts` meant.

**The egress sidecar is tinyproxy, and the allow-list is now demonstrated rather than modelled.**
`platform-egress` (`docker/egress.Dockerfile`, tinyproxy 1.11.2 pinned) runs as uid 1000 with
`cap_drop ALL` and a read-only rootfs, and the e2e drives a request through it from inside the run
container: the allowed host answers 200 and a host that is not on the list is refused 403, where
both names are the **same container on the same address**. The rendered configuration lost its
`User nobody`/`Group nobody` lines — not because they broke it (measured: with them present the real
image starts and serves), but because the process does not honour them, which makes them a claim
nothing enforces.

**Residual 1: a filesystem that will not set a socket's mode.** The shim `chmod 0600`s its control
socket after `listen`. On Docker Desktop for macOS with the control volume bind-backed onto a host
directory (virtiofs), `chmod` answers `EINVAL` and the mode cannot be set at creation either — with
`umask(0o177)` the guest still reports `0666` while the host reports `0755`. A fatal refusal there
means the shim cannot start in the one arrangement a developer runs the real images in. It now
checks the **property** instead of the call: `<ctl>/<run-id>` is `0700` owned by the shim's uid (the
launcher creates it that way), and a Unix socket cannot be connected to without search permission on
every directory in its path, so the directory denies exactly the set the `0600` would. When the
directory does **not** carry that property the shim still refuses, naming both facts. Linux is
unaffected — `chmod` succeeds and the branch is never taken.

**Residual 2: the SDK computes the executable's path on the platform side.** `Options.pathToClaudeCodeExecutable`
is `null` outside `local` mode, so the SDK resolves its own bundled binary, checks it exists **in the
platform process' filesystem**, and hands that path to `spawnClaudeCodeProcess` — which the shim then
executes *inside* the run container, where the path is the image's `/usr/local/bin/claude` and not
the platform's `node_modules` path. No tier has run a real agent through the real image (WP-15g
scoped that out and no criterion here needs it), so this is recorded rather than fixed: the fix is a
`RunSpec.claudeCodePath` the workspace spec sets to the run image's path. PROGRESS carries it as
discovered work.
