# 13 — Implementation plan (handoff to the implementation orchestrator)

> This is the work breakdown for a Claude Code orchestrator and its agent team. Product scope: product/14 (v0.1 = M1 loop, M2 trust, M3 show-the-value). Every work package (WP) lists inputs, outputs, acceptance criteria and dependencies. The orchestrator should run WPs as tickets through its own process: plan → implement → review (fresh context) → tests green → merge.

## How the work is run
See `14-orchestration-protocol.md` (orchestrator loop, fresh-context implementer and reviewer subagents, ledger `PROGRESS.md`, commit/push policy).

## Ground rules for the implementer
1. Read `docs/README.md`, all `docs/product/*`, all decisions, then `docs/technical/*`. The docs are the spec; product questions go to `docs/OPEN-QUESTIONS.md`, not into code comments.
2. Follow the code structure in technical/01; dependency rule `domain ← application ← infrastructure ← apps`.
3. Tests per technical/10 are part of each WP's definition of done; contract tests for every integration port; golden fixtures for SDK streams.
4. No secrets anywhere; `.env.example` maintained with every new variable; gitleaks pre-commit.
5. Conventional commits with `Signed-off-by`; small MRs; each WP ends with docs updates (CHANGELOG via release-please, ADR if a decision changed).
6. Install `docs/technical/CLAUDE.md.proposed` as `CLAUDE.md` at repository root in WP-00 and keep it under 200 lines.

## Milestone M4 — a real installation

M1 built the loop, M2 the trust surfaces, M3 the value story, and every row of all three is merged except **WP-33**. M4 is the milestone after which somebody who is not us can install this product, point it at their own GitLab and Jira, and let a ticket reach a merge request without an operator standing beside it. Its content is not new product: it is **what the delivery of M1–M3 discovered** — `docs/technical/PROGRESS.md` § "Open findings backlog" entries 0b–119, and `docs/OPEN-QUESTIONS.md` Q63–Q90 — grouped into rows an implementer can build in one fresh context. The disposition of **every** open entry and every Q63–Q90 is the table in `PROGRESS.md` § "Architect ruling (M4, session 6)", and each entry now carries a one-line owner note under its own heading. **A row here names what it folds and deliberately does not restate the entry's evidence: read the entry first, then the row.** An open question is implemented per its recommendation and never waited on; where a row implements one, the row says so.

**The order, and the argument for each group.**

1. **Money and state that cannot be recovered come first** (WP-47…WP-52), before anything a human can see. A dead run holds a budget reservation in *every future window* and the only lever an operator has loses the spend (backlog **109** with **50**); a lost wake-up bricks a history bootstrap that a unique index then refuses to restart (**106**); a poisoned event is re-dispatched twelve times an hour for ever (**43**); twenty of the thirty-six variables the server reads never reach the container, so a stock instance cannot create an integration at all (**54**); a binding's host is whatever the caller typed and the platform process has no egress control (**48**); and a run's structured output is stored unredacted and copied into a field the API serves (**35**). Four of those are graded **blocker** and the rest **major**. None of them is visible on a screen, all of them are cheap relative to what they cost, and every one of them gets *worse* the moment the next group lands.
2. **The run that makes them live** (WP-53…WP-56, and **WP-74**, which sits between WP-54 and WP-55 in the table rather than at the end: it is WP-53's criterion (5) finished, and it waits on WP-54 because WP-54 rewrites its predicate's input).
