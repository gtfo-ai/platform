# 09 — UI architecture

> Round 2 design. Decisions: TD-013 (UI stack), TD-014 (real-time transport). Sources: product/10, /18, research/08.

## Stack
React 19 + Vite 8 + TypeScript; TanStack Router (SPA, code-based routes — one `createRoute` per screen in `apps/web/src/routes/tree.tsx`, no generated route tree (Q44) — zod search params) + TanStack Query; the hand-written primitive kit in `ui/` with `@base-ui/react` for menu, dialog, tooltip, popover and tabs (TD-033, not shadcn/ui) + Tailwind 4 + Octicons (`@primer/octicons-react`) + Inter Variable self-hosted; TanStack Table + Virtual (chat mode for transcripts); cmdk, sonner, react-hook-form + zod, react-hotkeys-hook, react-resizable-panels; CodeMirror 6 (+ yaml, markdown, lint, merge, json-schema); streamdown for live assistant markdown; react-markdown + rehype-sanitize + shiki (worker) for KB/artifacts; `@pierre/diffs` behind one `<Diff>` component (lazy-loaded); anser for ANSI; Recharts 3. Served as a static bundle by the app process with SPA fallback; same origin as the API and SSE — `apps/server/src/web/` since WP-15j, where the fallback is **allow-list shaped**: `index.html` is returned for a path whose first segment the route tree below declares and for nothing else, so `/api/*`, `/events`, `/webhooks/*` and the probes can never be answered with the shell, and a missing asset is a 404 rather than HTML. Hashed assets under `assets/` are immutable for a year; the shell itself is `no-cache`, because a shell a browser kept would pin a bundle a deploy deleted. `APP_WEB_ROOT` overrides the directory (technical/12); an absent bundle is named in a warning and leaves the API serving. The bundle is **coded on the wire** — `br` preferred, `gzip` otherwise, nothing below 1 024 bytes and nothing already compressed, each file coded once per coding and cached for the life of the process (`apps/server/src/web/encoding.ts`) — which is what makes TD-013:8's *gzipped* budget a statement about the bytes an instance ships rather than about a number only `pnpm bundle:check` ever sees; the API half is TD-002's `@fastify/compress`, with `text/event-stream` and `/api/auth/*` excluded. Every response the bundle answers carries `x-frame-options: DENY` and a **Content-Security-Policy measured on the built bundle** (`apps/server/src/web/csp.ts`): `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`. No `'unsafe-inline'` and no nonce: the shell has **no** inline script (there is one dark theme, set by `styles.css` alone, so nothing has to run before the first paint; `apps/web/index.html` says so on purpose), Tailwind emits one stylesheet at build time, and React applies a `style` prop through CSSOM, which `style-src` does not govern. What it excludes is stated where it is decided — `require-trusted-types-for` (react-dom writes `innerHTML` itself), `worker-src` beyond `'self'` (this bundle has no worker), and a library that writes a `style` attribute or injects a `<style>` element, which would be refused loudly rather than silently allowed. The proof that the application runs under it is a browser: the Playwright harness serves the built bundle under this exact header, `test/web-e2e/csp.spec.ts` fails on a single `securitypolicyviolation`, and a probe pair shows the policy is being enforced. zod's JIT compilation is turned off in the browser entry for the same reason (`apps/web/src/zod-jitless.ts`): its `Function("")` probe is refused by `script-src` and reported every page load, and a violation channel that is never empty is one nobody reads.

## Structure
```
apps/web/src/
  routes/            # code-based (tree.tsx, Q44): /, /sign-in, /projects, /projects/$key (a layout: the board is its index; knowledge, pipeline, shadow (`?batch=<id>`, one batch's page), budgets, settings/$section (S-23.11b; a bare `settings` redirects to the first section), tasks/$taskId its children), /tasks/$taskId, /runs/$runId, /agents, /inbox, /integrations (+ /new, the wizard; + /$integrationId, `?tab=`), /stats, /audit, /settings/$section (S-23.11b: one page per section, `features/settings-sections.ts`; a bare `/settings`, an unknown section and — for anybody but an admin — an Operations section redirect to the first the caller may open), /onboarding (`?project=<key>&step=<id>`, the New project wizard), /workers (+ /approve)
  app/               # the composition root, the query hooks, and the frame: shell.tsx (top bar, org UnderlineNav) and project-frame.tsx (the project's header and tabs)
  features/          # board, task-detail, run-transcript, questions, knowledge, pipeline-editor, integrations, budgets, stats, audit, wizard, shadow
  transcript/        # normaliser types (shared with server), reducer applyEvent(blocks, event), renderer registry per tool, virtual list
  realtime/          # one SSE connection per tab (topics), reconnect/replay, Query bridge
  api/               # typed client generated from the OpenAPI schema (08)
  ui/                # the primitive kit (TD-033): one file per primitive, dependency-light so the
                     # worker's local page can import it — see below
    bot/             # the office mascot: pose and prop grids, <Bot>, <Seat>, bot.css (React only; the worker page imports it)
  viz/               # the live visualisations (TD-033 decision 8); each draws from data the screens already read

    fleet/           # the Agents page's three views (S-23.6): fleetOf, the map (lazy, on the same canvas), the pixel office (lazy), the list
```

**The frame and the lazy screens since S-23.4 (TD-033 § 1, research/19 § 5.1).** `app/shell.tsx` is
the frame of every signed-in screen: the top bar (deep night, the page's own colour, separated from it by its bottom border — the wordmark, the project
switcher inside a project, the running indicator that also carries the connection state's dot and
live region, the `+` menu, the inbox count, the avatar menu) and, outside a project, the
organisation's UnderlineNav (`NAV`, held to the user guide by `user-guide-census.test.ts`). Inside a
project, the `/projects/$key` **layout route** (`app/project-frame.tsx`) draws the project's
PageHeader and tabs above an `<Outlet/>`; no URL changed when it arrived. A route tells the frame
about itself through `staticData` — its project `tab`, `fullWidth` (the board and the run log;
everything else is centred at 1280 px) and `ownsHeading` (a task's page, so the project's name above
it is not a second `<h1>`). **Every screen is a lazy route chunk** except the frame, the sign-in page
and Home: `lazyRouteComponent` per screen module, so the router preloads the chunk while it resolves
the match and shows `defaultPendingComponent` (a `Skeleton`) only past its pending delay. The chunks
are served from `'self'`, so the CSP is unchanged. The initial graph was 293 722 B gzipped before
the split and 260 557 B after it, frame included (`pnpm bundle:check`; BACKLOG 812 has the levers left
towards 250 kB). zod and `zod-jitless.ts` share a chunk of their own (`vite.config.ts`),
so the JIT is off before a shared chunk builds any schema.

**`ui/` since S-23.1 (TD-033).** The primitives are hand-written thin components on Tailwind classes,
except the three with real APG behaviour, which are Base UI's (`@base-ui/react`, adopted by TD-033;
Q46's release-candidate blocker is gone at 1.9). Icons are `@primer/octicons-react`, imported per icon
(`@primer/octicons-react/CheckIcon`), so only the glyphs used are bundled. No router import anywhere
in `ui/`: a link is the caller's element, handed the class and `aria-current` through a `render` prop
(`ui/nav-item.ts`), so `ui/` writes no `href` (`no-html.test.ts`) and the worker's local page, which
has no TanStack Router, can import it. Every primitive has a happy-dom test of its contract beside it.

**`viz/flow/` since S-23.5 (TD-033 decision 8 (a)).** The pipeline as a clickable graph, on the
project's **Pipeline** tab (a template, read-only: `PipelineFlow`, over `GET /api/projects/:id/pipeline`)
and at the top of a **task's page** (its progress, live: `TaskFlow taskId`, self-contained so S-23.9 can

layout library: the main path is one row left → right, a stage entered only by a failure or a disabled

a task's first view frames the current stage with two cards either side at zoom ≥ 0.75, a
template's every stage (zoom down to 0.2, so nothing is cut off; a two-row layout was weighed and rejected in `flow-canvas.tsx`), and *Fit all* shows every stage; on a task a loop pill
is drawn only once spent, or while its edge is pointed at or a card it touches has focus) and

visible cards), and shown instead of it below 768 px or when the reader presses **List**;
`stage-dialog.tsx` is the stage dialog, the first screen use of `ui/dialog.tsx` (`size="lg"`): for a run,

the end until the reader scrolls up), a watch-only note naming the seat and *Open run* / *Open artifact*;
for a template, the stage's configuration, loops and outcomes. A tool's name is the run's text: a
sub-label quoting it ("Using …") is filtered and bounded (`toolWords` in `ui/activity.ts`), and in
the log it is part of the filtered `text`, never of the platform's `prefix`. **`flow-canvas.tsx` and

wrapper carries `role="application"`, which it does not let a caller change. `csp.spec.ts` opens both

animation stops under reduced motion.

## Real-time state
- One multiplexed SSE stream per tab (`GET /events?topics=…`; topics `org`, `project:<id>`, `task:<id>`, `run:<id>`); subscribe/unsubscribe via POST; every event has `id: <seq>`; reconnect with `Last-Event-ID`; server replays from its ring buffer or sends `reset` → the client refetches via Query. Every stream a tab opens shares one `connection_id`, so the client (`realtime/client.ts`, S-23.16) POSTs a topic change only for a stream that has fired `open` — before it, the id can still name the stream being displaced — and on `open` sends one POST with the difference between the desired set and the set the stream's URL carried; at most one such POST is in flight, and a change made while one is pending is sent as one more POST when it settles.
- Resources (tasks, runs, questions, KB, settings) live in TanStack Query; events apply `setQueryData` for known shapes (card cost, time-in-stage, run status) and `invalidateQueries` for coarse changes.
- **What arrives live** (S-23.14): every `task.*` and `run.*` event reaches `org`, the event's `project:<id>` and its `task:<id>` as a `domain_event` frame whose `data` is ids and small enums only (technical/08 § "SSE contract") — so the bridge (`realtime/query-bridge.ts`) only ever **invalidates**: the project's and the task's and the run's prefixes from the ids, the inbox for `task.question.*`/`task.approval.*`, the agents list for any event naming a run, the workers list for a claim naming a worker. A mounted Agents, Inbox, board or task screen therefore refetches within the hint's round trip, without navigation; `setQueryData` on known shapes is still not built (a frame carries no DTO to set).
- Transcripts: event-sourced zustand store per run fed by `TranscriptEvent`s; rAF-batched delta application; coalesced text deltas; only the streaming block is "hot"; TanStack Virtual chat mode with follow-tail and "paused updates, N behind" indicator when scrolled up.
- Board (`features/board.tsx`, `features/board-card.tsx`, S-23.9a): below `xl` the five columns are a sideways-scrolling row that snaps per column, from `xl` a five-column grid; each card is the task's phase (`PhaseTrack` over the page's `stages`, with the agents read's activity while a run is live), its needs-you ◆ and count, its loop and conflict badges and a `···` menu (pause/resume, cancel and return-to-stage through Dialogs, the task page's commands; *Open ticket*/*Open MR* through `ActionMenuLinkItem`). `?view=list` is the same page as an Issues-style list with state/template/needs-you filters applied on the client. The start form is a Dialog opened by `#start-ticket`. Per-card selector subscriptions, a throttled `now` tick and virtualisation past ~200 cards are not built.

## Transcript model (shared package `@app/transcript`)
`TranscriptEvent { seq, runId, ts, kind: text|thinking|tool_use|tool_result|agent_start|agent_end|compaction|system|user|steer|result, parentToolUseId?, toolName?, payload }` produced by the server normaliser (versioned, golden-fixture tested); client reducer builds blocks; renderer registry: `Edit/Write/MultiEdit` → diff, `Bash` → ANSI terminal block, `Read/Grep/Glob` → code with line numbers, `Agent` → nested transcript, `WebFetch/WebSearch` → link cards, `mcp__*` → JSON viewer, `AskUserQuestion`/platform `ask_human` → question card, default → generic card.

> **2026-10-06 (PROGRESS backlog 496):** the stored kinds are `@platform/contracts`' `transcriptKindSchema`, and it gained `progress` — a line the agent reported through `report_progress` (`summary`, `percent_complete`, `truncated`). The run page renders it as a *progress* row of its log (the percentage as a badge, a cut marked *shortened by the platform*), searchable by its words; the task page shows a running stage's newest one (the screens table below).

> **S-23.10 (research/19 § 5.2 "Run"):** `transcript/view.tsx` draws the blocks as a **log**, as an Actions job does: a tool call is a collapsed **log step** — a native `<details>` whose line is chevron, `StatusIcon`, the tool (a platform tool in the vocabulary's words, any other by its name through `toolWords`), the argument summary (`argumentSummary`, the stage dialog's) and the duration right-aligned (`transcript/steps.ts`; a `ToolBlock` keeps `startedAt` beside `at`, which a folded result moves) — open on arrival while it has no result or after it failed, and the renderer registry's body is what opening it shows; assistant text is prose lines, thinking and the CLI's `system` notice are collapsed steps, the other kinds one-line rows. The scroller is a pane of its own (`scrollerClassName`; the run page sizes it to the viewport), and following its end is keyed on the tail's signature — a new block, a folded result, a streaming block's next words — not only on the count. Still not virtualised (the reason is `view.tsx`'s docblock).

## The sign-in page

Headline *"Tickets in, merge requests out."* left (about 7/12 on a wide screen), the form on a solid ink block right, one column below `lg`. **On a phone the whole form, button included, is on screen on arrival** (measured with Playwright's iPhone 14 and iPhone SE 3rd-generation profiles, over 100 px to spare for Safari's floating toolbar): below `lg` the content starts at the top rather than being centred, the gaps are tighter, the robot tucks up so its antenna passes under the text above it (the text column is drawn over it), and the subtitle is shown only from `sm` up. Behind it, full-bleed, an **ordered-dither pixel field** on a `<canvas>` (`features/dither-field.ts`, pure, and `features/dither-canvas.tsx`): one canvas pixel per ~5 CSS px cell, snapped to whole device pixels and scaled with `image-rendering: pixelated`; value noise advected left → right along narrow horizontal lanes, only a few lit at a time, thresholded by an 8×8 Bayer matrix into two colours (about 6 % of cells lit); the field fades to 8 % of itself behind every element marked `data-dither-quiet` (the headline column and the form block), easing back over 14 cells, so text sits on the plain ground; every 4.5 s an amber pixel crosses one lane and fades at the right edge. ## An upgraded server under an open tab
The bundle's response schemas are strict, so after an upgrade an open tab refuses the new server's answers as `invalid_response` (PROGRESS backlog 487). **Since WP-154 (d)** the bundle carries the commit it was built from — `APP_COMMIT`, compiled in by `vite.config.ts` as `__PLATFORM_BUILD_COMMIT__` from the same build argument the server reports at `GET /api/version` (`docker/app.Dockerfile`'s `web` stage), `dev` when there is none — and the SPA re-reads `/api/version` (a loose read of `commit` only) on every `invalid_response` and every SSE reconnect (`app/platform-version.ts`). When the server's `commit` differs from the bundle's and neither is `dev` or null, the API client throws `PlatformUpdatedError` instead of the schema error, `ErrorNotice` renders nothing for it — decided by the error's type since **WP-167** (backlog 524), never by its text, so a screen hands the notice the error itself (`error={…}`) and `apps/web/src/error-notice-census.test.ts` refuses `String(…)` in its `title`/`detail` — and the shell shows one banner: *The platform was updated — reload this page*. When the two are equal the schema error stands: a real contract defect stays visible.

## Failure containment
A render that throws must cost one region, never the tab. Two boundaries, because they catch different failures:
- **Route level** — `defaultErrorComponent` on the router. TanStack Router installs a catch boundary per match *only when that match has an error component*, so without this option the nearest boundary is the root's and a screen that throws replaces the header and the navigation too (measured at WP-20: the document held the router's built-in error component and nothing else). With it, the failure is contained inside `<main>` and the navigation stays usable.
- **Application level** — one `ErrorBoundary` outside every provider, for what the router cannot see: a throw in a provider, in a provider's effect, or in the router's own render.

The fallback names the area, shows the error's message **sanitised and bounded** (an error message can quote a provider's string, so BD-022 applies to it), and offers *Try again* plus *Reload the page*; a boundary also clears itself when the route changes, so navigating away is a recovery. The fallback is deliberately poor in dependencies: a fallback that throws is caught only by the next boundary out, and the application-level one has none.

## Accessibility, theming, i18n
Base UI APG behaviours (menu, dialog, tooltip — `ui/action-menu.tsx`, `ui/dialog.tsx`, `ui/tooltip.tsx`); every enabled clickable control shows a pointer (Tailwind v4's Preflight resets buttons to `cursor: default`; `styles.css` restores it in the base layer for buttons, `role="button"`, Base UI's `role="menuitem"`/`menuitemradio`/`menuitemcheckbox`/`tab`, submit/button/reset inputs, selects and `summary`, held by `cursor.test.ts`); `aria-live="polite"` for status changes; reduced-motion (the running pulse and the skeleton shimmer stop on their first frame); Shiki dual themes; keyboard shortcuts sheet (`g b`, `g q`, `/`, `?`, `j/k`, `f`); English-only strings with `Intl.*` formatting; Lingui later if needed.

**The visual design language is TD-033**: GitHub's (Primer's) grammar in the sign-in page's colours. Since S-23.1:

- **Tokens.** `styles.css` declares Primer-tier semantic tokens — `--bg-header/canvas/subtle/muted/inset`, `--border-default/muted/input`, `--fg-default/muted/subtle/link/on-emphasis`, `--accent-selected`, `--action-primary-bg/fg`, `--success/danger/attention/done/running-fg` and `-bg`, `--focus-ring` — for the **one dark theme**, mapped through `@theme inline` (`bg-canvas`, `bg-default`, `bg-subtle`, `border-line`, `text-link`, `bg-primary`, …). The pre-TD-033 utility names (`bg-surface`, `bg-surface-muted`, `text-accent`, `text-warning`, …) are aliases of them, so every screen took the look without an edit. Base hex values live in the token blocks only; the brand palette (`--brand-*`) is the sign-in page's, and `--signin-*` are aliases of it, unchanged in value. **Beacon amber `#f4b860` means "the thing to do / the thing happening"**: the primary button (night text), the selected underline, the running state and "needs you".
- **One theme, dark** (TD-033's 2026-11-05 amendment, the product owner's decision). There is no light theme, no `system` option, no theme control and no `data-theme` attribute: the tokens live in one `:root` block with `color-scheme: dark`. **The page is darker than its cards**, in four layers: the page (`--bg-canvas`, `bg-canvas`) is the top bar's deep night `#0f0d22`, separated from the bar by the bar's bottom border; cards, boxes, list boxes, dialogs and menus (`--bg-default`, `bg-default`; the pre-TD-033 `bg-surface` is an alias of it) are night `#15132b`; box header rows are ink `#1f1c3d` (`--bg-subtle`) and the hover state `#29254d` (`--bg-muted`). An input's fill is `bg-inset`, deep night, so a field reads as sunk into its card. The flow canvas's dotted ground is the page colour, the office its own dark room.
- **Contrast is enforced.** `ui/contrast.test.ts` parses `styles.css`, resolves the one `:root` block the way the cascade does, and holds every declared pair: 4.5:1 for text (every foreground on **both** the page and the card ground, and on the header row, hover and input grounds; status words on their tints; the beacon button), 3:1 for the input border, the focus ring, the selected underline and status icons against both grounds; the top bar's pairs too. It also fails if a `[data-theme]` rule comes back, or a hex value appears outside the token block, and it is calibrated against a planted regression. The ratios that used to be hand-measured here are its output now.
- **Type.** Inter Variable, self-hosted (`@fontsource-variable/inter`, OFL-1.1): one latin woff2 from `'self'`, `font-display: swap`, weight axis 100–900, so the sign-in headline is Inter Black on every OS; monospace stays `ui-monospace`. Body 14 px; scale 12 / 14 / 16 / 20 / 24 / 32; 6 px radius (`rounded-lg`); a 4 px spacing grid. `ui/typography.test.ts` holds the stylesheet to it, and `csp.spec.ts` loads the font under the production policy.
- **Icons** are Octicons (MIT), React SVG elements, never markup sinks.
- **Words, not identifiers** (since S-23.2). A screen prints a state, a stage, a role or an artifact type through `ui/humanize.ts` (`Waiting for approval`, `CI`, `Code review · Reviewer`), never the enum value. **No spec reference in UI text**: `apps/web/src/spec-reference-census.test.ts` fails on `BD-`/`TD-`/`WP-`/`Q` ids or `product/NN`/`technical/NN` anywhere in the application's sources outside a comment — the reason goes in a comment beside the string. Its docblock states the one spelling it cannot see.
