# 09 — UI architecture

> Round 2 design. Decisions: TD-013 (UI stack), TD-014 (real-time transport). Sources: product/10, /18, research/08.

## Stack
React 19 + Vite 8 + TypeScript; TanStack Router (SPA, code-based routes — one `createRoute` per screen in `apps/web/src/routes/tree.tsx`, no generated route tree (Q44) — zod search params) + TanStack Query; the hand-written primitive kit in `ui/` with `@base-ui/react` for menu, dialog, tooltip, popover and tabs (TD-033, not shadcn/ui) + Tailwind 4 + Octicons (`@primer/octicons-react`) + Inter Variable self-hosted; TanStack Table + Virtual (chat mode for transcripts); cmdk, sonner, react-hook-form + zod, react-hotkeys-hook, react-resizable-panels (the command palette and the shortcuts are hand-written instead of cmdk and react-hotkeys-hook — § "Visual design language"); CodeMirror 6 (+ yaml, markdown, lint, merge, json-schema); streamdown for live assistant markdown; react-markdown + rehype-sanitize + shiki (worker) for KB/artifacts; `@pierre/diffs` behind one `<Diff>` component (lazy-loaded); anser for ANSI; Recharts 3. Served as a static bundle by the app process with SPA fallback; same origin as the API and SSE — `apps/server/src/web/` since WP-15j, where the fallback is **allow-list shaped**: `index.html` is returned for a path whose first segment the route tree below declares and for nothing else, so `/api/*`, `/events`, `/webhooks/*` and the probes can never be answered with the shell, and a missing asset is a 404 rather than HTML. Hashed assets under `assets/` are immutable for a year; the shell itself is `no-cache`, because a shell a browser kept would pin a bundle a deploy deleted. `APP_WEB_ROOT` overrides the directory (technical/12); an absent bundle is named in a warning and leaves the API serving. The bundle is **coded on the wire** — `br` preferred, `gzip` otherwise, nothing below 1 024 bytes and nothing already compressed, each file coded once per coding and cached for the life of the process (`apps/server/src/web/encoding.ts`) — which is what makes TD-013:8's *gzipped* budget a statement about the bytes an instance ships rather than about a number only `pnpm bundle:check` ever sees; the API half is TD-002's `@fastify/compress`, with `text/event-stream` and `/api/auth/*` excluded. Every response the bundle answers carries `x-frame-options: DENY` and a **Content-Security-Policy measured on the built bundle** (`apps/server/src/web/csp.ts`): `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`. No `'unsafe-inline'` and no nonce: the shell has **no** inline script (there is one dark theme, set by `styles.css` alone, so nothing has to run before the first paint; `apps/web/index.html` says so on purpose), Tailwind emits one stylesheet at build time, and React applies a `style` prop through CSSOM, which `style-src` does not govern. What it excludes is stated where it is decided — `require-trusted-types-for` (react-dom writes `innerHTML` itself), `worker-src` beyond `'self'` (this bundle has no worker), and a library that writes a `style` attribute or injects a `<style>` element, which would be refused loudly rather than silently allowed. The proof that the application runs under it is a browser: the Playwright harness serves the built bundle under this exact header, `test/web-e2e/csp.spec.ts` fails on a single `securitypolicyviolation`, and a probe pair shows the policy is being enforced. zod's JIT compilation is turned off in the browser entry for the same reason (`apps/web/src/zod-jitless.ts`): its `Function("")` probe is refused by `script-src` and reported every page load, and a violation channel that is never empty is one nobody reads.

## Visual design language (TD-033)

GitHub's (Primer's) grammar in the sign-in page's colours, in one dark theme, decided as TD-033 and built as
milestone M23 (technical/13; one LEDGER line per slice). This section is the whole of it as built.

### Foundations

- **Tokens.** `styles.css` declares Primer-tier semantic tokens — `--bg-header/canvas/subtle/muted/inset`, `--border-default/muted/input`, `--fg-default/muted/subtle/link/on-emphasis`, `--accent-selected`, `--action-primary-bg/fg`, `--success/danger/attention/done/running-fg` and `-bg`, `--focus-ring` — for the **one dark theme**, mapped through `@theme inline` (`bg-canvas`, `bg-default`, `bg-subtle`, `border-line`, `text-link`, `bg-primary`, …). The pre-TD-033 utility names (`bg-surface`, `bg-surface-muted`, `text-accent`, `text-warning`, …) are aliases of them, so every screen took the look without an edit. Base hex values live in the token blocks only; the brand palette (`--brand-*`) is the sign-in page's, and `--signin-*` are aliases of it, unchanged in value. **Beacon amber `#f4b860` means "the thing to do / the thing happening"**: the primary button (night text), the selected underline, the running state and "needs you".
- **One theme, dark** (TD-033's 2026-11-05 amendment, the product owner's decision). There is no light theme, no `system` option, no theme control and no `data-theme` attribute: the tokens live in one `:root` block with `color-scheme: dark`. **The page is darker than its cards**, in four layers: the page (`--bg-canvas`, `bg-canvas`) is the top bar's deep night `#0f0d22`, separated from the bar by the bar's bottom border; cards, boxes, list boxes, dialogs and menus (`--bg-default`, `bg-default`; the pre-TD-033 `bg-surface` is an alias of it) are night `#15132b`; box header rows are ink `#1f1c3d` (`--bg-subtle`) and the hover state `#29254d` (`--bg-muted`). An input's fill is `bg-inset`, deep night, so a field reads as sunk into its card. **Fields are inset and cards are default** (S-25.10, the review of #85): every field — `Field`, a textarea, `CopyField`, `Select` and the `CheckboxList` box — sits on `bg-inset` inside `border-line-input`, and every bordered box on `bg-default`, so one form never mixes two field grounds. The flow canvas's dotted ground is the page colour, the office its own dark room.
- **Contrast is enforced.** `ui/contrast.test.ts` parses `styles.css`, resolves the one `:root` block the way the cascade does, and holds every declared pair: 4.5:1 for text (every foreground on **both** the page and the card ground, and on the header row, hover and input grounds; status words on their tints; the beacon button), 3:1 for the input border, the focus ring, the selected underline and status icons against both grounds; the top bar's pairs too. It also fails if a `[data-theme]` rule comes back, or a hex value appears outside the token block, and it is calibrated against a planted regression. The ratios that used to be hand-measured here are its output now.
- **Type.** Inter Variable, self-hosted (`@fontsource-variable/inter`, OFL-1.1): one latin woff2 from `'self'`, `font-display: swap`, weight axis 100–900, so the sign-in headline is Inter Black on every OS; monospace stays `ui-monospace`. Body 14 px; scale 12 / 14 / 16 / 20 / 24 / 32; 6 px radius (`rounded-lg`); a 4 px spacing grid. `ui/typography.test.ts` holds the stylesheet to it, and `csp.spec.ts` loads the font under the production policy. Since S-23.13a the build (`apps/web/vite-plugins/inter-font.mjs`, a Vite plugin) **preloads** the hashed woff2 from `index.html` and writes the package's OFL-1.1 text to `dist/inter-OFL.txt`, which the licence requires to travel with the font; `THIRD_PARTY_NOTICES.md`'s row says so.
- **Icons** are Octicons (MIT), React SVG elements, never markup sinks.
- **Accessibility is measured** (since S-23.13a, research/19 decision D4): `test/web-e2e/a11y.spec.ts` runs axe-core (`@axe-core/playwright`, WCAG 2.0 A/AA and 2.1 AA) over every screen in the built bundle — Home, Projects, the board and its list, the Pipeline tab and a stage dialog, each task tab, a run, the three Agents views, the inbox, Integrations and the add wizard, an org and a project settings section, the new-project wizard — and fails on a single violation. React Flow's `role="application"` wrapper raises nothing, so nothing is excluded. axe's `color-contrast` reads text, not borders, so a field's edge (WCAG 1.4.11, 3:1) is held by a census instead: `apps/web/src/form-edge-census.test.ts` fails when an `<input>`, `<select>` or `<textarea>` names the divider `border-line` rather than `border-line-input`, directly or through a string constant (thirty did, until S-23.13a). **A bordered box sits on the card ground** (S-25.10, the owner on Budgets' empty state: cards "use the same background colour as the body"): `apps/web/src/card-ground-census.test.ts` fails on an intrinsic element whose `className` has a radius and a `border` but no ground other than the page's own (`bg-canvas`, `bg-inset`, `bg-header`, `bg-transparent`) — controls and `rounded-full` pills exempt, the genuine exceptions (the two canvas frames, the fleet map's hollow slot, a key cap, the `CheckboxList` box — a field) listed in the test with their reasons and held in both directions; its docblock says what it cannot see. A box with no border at all — a form drawn straight on the page — is invisible to it, so **every box sits on the card ground** is held in a browser instead (S-25.10b, the owner's Chrome check of Policies): `test/web-e2e/support/card-ground.ts` fails on any visible text whose computed ground, up to the scanned root, is transparent or the canvas, with the page's chrome exempt (headings, a `<p>` of prose unless it is a form's, a list's or a label's own text, a link or button on its own, the page and project headers, navigation, steppers, `data-toolbar` rows, `data-timeline` timelines and the flow and fleet canvases and the office). `settings-cards.spec.ts` runs it over every org and project settings section and Admin screen, read from `ORG_SETTINGS_GROUPS` and `PROJECT_SETTINGS_GROUPS`; `page-cards.spec.ts` over `<main>` of the project tabs, the task and run pages, Agents, the inbox, Statistics and both wizards, against the fixture backend. Its `nestedCards` refuses a bordered card-ground box inside another (a disclosure's panel, a dialog and the canvases aside), which is why a Blankslate inside a card is `inset` (no border, no ground of its own). A settings section's body is a `SettingsCard` (`features/settings-frame.tsx`), unless it already draws its own boxes (Execution, Rules & limits, Prompt files).
- **Responsive at 1 024 and 390 px** (since S-23.13a): no screen scrolls the page sideways (the board's columns and the canvases scroll in their own boxes); below `sm` the org navigation folds into *More* and the running pill keeps only its count, and below `lg` *Search or jump to…* is its magnifier alone (S-23.13b); `PageHeader`'s title keeps 16 rem before its actions wrap under it; `ListRow`'s trailing facts take their own line and its meta breaks anywhere; a `NavList` is a one-line `<details>` naming the current item below the breakpoint where its grid stacks (`stackBelow`). `test/web-e2e/responsive.spec.ts` measures it.
- **Words, not identifiers** (since S-23.2). A screen prints a state, a stage, a role or an artifact type through `ui/humanize.ts` (`Waiting for approval`, `CI`, `Code review · Reviewer`), never the enum value. **No spec reference in UI text**: `apps/web/src/spec-reference-census.test.ts` fails on `BD-`/`TD-`/`WP-`/`Q` ids or `product/NN`/`technical/NN` anywhere in the application's sources outside a comment — the reason goes in a comment beside the string. Its docblock states the one spelling it cannot see.

### The frame, the keyboard and the lazy chunks

**The frame and the lazy screens since S-23.4 (TD-033 § 1, research/19 § 5.1).** `app/shell.tsx` is
the frame of every signed-in screen: the top bar (deep night, the page's own colour, separated from it by its bottom border — the wordmark, the project
switcher inside a project, *Search or jump to…* (below), the running indicator that also carries the connection state's dot and
live region, the `+` menu, the inbox count, since S-25.6 the *Settings* gear (`SettingsButton`: a
`Tooltip`ped link, current on `/settings/*` and every Admin screen, hidden below `sm`), the avatar
menu — which holds *Settings* too — ) and,
outside a project, the organisation's UnderlineNav (`NAV`, held to the user guide by
`user-guide-census.test.ts`). **Since S-25.6 the row is the five daily screens** — Home, Projects,
Inbox, Agents, Statistics (product/10's 2026-11-06 IA amendment, Q-UX-1). Integrations, Workers and
the Audit log are the *Admin* group of the org settings' NavList (`features/settings-sections.ts`):
their routes moved under a pathless layout (`adminRoute`, `features/admin-frame.tsx`, eager like the
project's layout) that draws that NavList around them with their entry current — except a route whose
`staticData.bare` says it takes the whole width (the two wizards, which have a Stepper column of their
own) — and **no path or
search schema changed** — `/workers/approve?code=…` (the device flow's `verification_uri`) and
`/workers/new?step=ready` resolve as before (`routes/admin-routes.test.tsx` reads the server's
`WORKER_APPROVE_PAGE` and opens it); `/settings/<admin id>` redirects to the screen's own URL. The
command palette offers all of them by name (`PALETTE_SCREENS` in `app/nav.ts`). Inside a
project, the `/projects/$key` **layout route** (`app/project-frame.tsx`) draws the project's
PageHeader and tabs above an `<Outlet/>`; no URL changed when it arrived. A route tells the frame
about itself through `staticData` — its project `tab`, `fullWidth` (the board and the run log;
everything else is centred at 1280 px) and `ownsHeading` (a task's page, so the project's name above
it is not a second `<h1>`). **The frame sticks** (S-23.18): the top bar always, and from `sm` the row
under it (the org UnderlineNav, or the project's tab row — the project's title scrolls away), at
`z-20` — above the page and the flow canvas, below a full-screen canvas (`z-30`), dialogs and every
portalled menu, tooltip and the palette. `styles.css` declares the rows' heights (`--app-bar-height`,
`--app-sticky-height`), which the run log pane and the Agents map subtract and `scroll-padding-top`
uses so an anchor, `scrollIntoView` or a `j`/`k` focus move stops below the frame;
`test/web-e2e/sticky-header.spec.ts` holds the declared heights to the drawn rows. **Every screen is a lazy route chunk** except the frame, the sign-in page
and Home: `lazyRouteComponent` per screen module, so the router preloads the chunk while it resolves
the match and shows `defaultPendingComponent` (a `Skeleton`) only past its pending delay. The chunks
are served from `'self'`, so the CSP is unchanged. The initial graph was 293 722 B gzipped before
the split and 260 557 B after it, frame included (`pnpm bundle:check`; BACKLOG 812 has the levers left
towards 250 kB). zod and `zod-jitless.ts` share a chunk of their own (`vite.config.ts`),
so the JIT is off before a shared chunk builds any schema.

**What the first paint does not load, below the route level (S-25.13).** By S-25.12 the graph had
grown back to 297 288 B of TD-013's 300 000 with every screen already a chunk, and the owner's rule
is to cut rather than raise the number. Two things in the frame were there for screens that had not
been opened. **Base UI's Menu** — with its focus manager, list navigation and typeahead, 21.4 kB
gzipped of the graph, measured — is a chunk of its own, `ui/action-menu-base.tsx`, loaded with
`import()`; `ui/action-menu.tsx`, the API every screen imports, decides a menu's shape once, when it
first renders. A menu drawn after the module has arrived — every screen's, since the frame's menus
fetch it as they mount — is Base UI's Menu as before. The frame's own menus on the first paint are a
plain trigger, the same element with the closed menu button's `aria-haspopup`/`aria-expanded`, which
swaps **only on a press**, `features/readiness-label.tsx`'s pattern for its popover (S-25.6): Base
UI's trigger replaces it, the focus is put back if the button had it, and the press is handed on as a
`click()` — the path a keyboard's Enter takes — so the menu opens by Base UI's own code; never a
swap when the module merely arrives, which would replace the element under a press on its way. A
failed load is forgotten and the trigger's title says to press again. The ui tier loads the module
before each test file (`test/support/web-lazy-chunks.ts`), and `bundle:check` refuses the Menu in
any initial asset by a marker (`LAZY_ONLY`). **The word maps only
lazy screens show** left `ui/humanize.ts`, which the frame imports, for `ui/words/*` modules of
their own that `humanize.ts` does not re-export (`readiness-criteria`, `loops`, `integrations`,
`project-execution`, `settings`): a module's statements sit in one chunk, so a map in `humanize.ts`
was in the initial graph whichever screen used it. The graph after both is 275 318 B (−21 970 B).

The account menu in the top bar (`app/shell.tsx`) is the first screen use of Base UI: who is signed
in, with which role, and **Sign out** (no theme choice: one dark theme, TD-033's 2026-11-05 amendment). `app/app.tsx` wraps the tree in
Base UI's `<CSPProvider disableStyleElements>`, because the production policy has no nonce for the
`<style>` element two of its parts would otherwise inject.

**The command palette and the keyboard shortcuts since S-23.13b** (research/19 § 3 rule 10, § 5.1).
The top bar's **Search or jump to…** — or ⌘K / Ctrl+K, or `/` — opens a palette over what the page
has already read, with no endpoint of its own: the organisation's screens (`app/nav.ts`'s
`PALETTE_SCREENS` — `NAV`, Settings, and Settings' Admin screens since S-25.6), the
current project's tabs, every project, every task in the project task reads the query cache holds,
and the actions *New project* (an administrator's), *Start a ticket in this project* (when the tasks
read's `can_start_task` says so), *Open inbox* and *Keyboard shortcuts*. It is **hand-written on Base
UI's `Dialog`** rather than `cmdk` (the stack line's): cmdk brings a Radix dialog of its own, a second
modal implementation beside Base UI's, for a list a filter and a sort cover. It follows the APG
combobox pattern with a listbox popup — the field keeps the focus, `aria-activedescendant` names the
active option, ↓/↑ move it, Enter takes it, Escape is the Dialog's — and an option's `id` is its
position, never its text; project names, ticket keys and titles are `UntrustedText`. The shortcuts
are `app/shortcuts.ts` (pure: the `g` chord, `decideKey`, the typing guard, `moveInList`, the setting)
applied by one `keydown` listener in `app/keyboard.tsx`: `g h`/`g p`/`g i`/`g a`/`g b` jump, `?` opens
the sheet (`SHORTCUT_GROUPS`, which the user guide's table is held to by `user-guide-census.test.ts`),
`j`/`k` move between the rows of the `ListBox` holding the focus (`data-list-box`), onto a row's row link when it has one. No single-key
shortcut fires in an input, a textarea, a select, anything `contenteditable`, or inside a dialog or a
menu; **Settings → Keyboard shortcuts** turns them off for the browser (`agentic.shortcuts`, WCAG
2.1.4), and ⌘K / Ctrl+K stays, because a modifier chord is not typed by accident. The palette and
the sheet are one lazy chunk (`command-palette.tsx`), fetched on first use or when the pointer or
focus reaches the button; `csp.spec.ts` opens both under the production policy.

### The primitive kit (`ui/`)

**`ui/` since S-23.1 (TD-033).** The primitives are hand-written thin components on Tailwind classes,
except the four with real APG behaviour, which are Base UI's (`@base-ui/react`, adopted by TD-033;
Q46's release-candidate blocker is gone at 1.9). Icons are `@primer/octicons-react`, imported per icon
(`@primer/octicons-react/CheckIcon`), so only the glyphs used are bundled. No router import anywhere
in `ui/`: a link is the caller's element, handed the class and `aria-current` through a `render` prop
(`ui/nav-item.ts`), so `ui/` writes no `href` (`no-html.test.ts`) and the worker's local page, which
has no TanStack Router, can import it. Every primitive has a happy-dom test of its contract beside it.

## Real-time state
- One multiplexed SSE stream per tab (`GET /events?topics=…`; topics `org`, `project:<id>`, `task:<id>`, `run:<id>`); subscribe/unsubscribe via POST; every event has `id: <seq>`; reconnect with `Last-Event-ID`; server replays from its ring buffer or sends `reset` → the client refetches via Query. Every stream a tab opens shares one `connection_id`, so the client (`realtime/client.ts`, S-23.16) POSTs a topic change only for a stream that has fired `open` — before it, the id can still name the stream being displaced — and on `open` sends one POST with the difference between the desired set and the set the stream's URL carried; at most one such POST is in flight, and a change made while one is pending is sent as one more POST when it settles.
- Resources (tasks, runs, questions, KB, settings) live in TanStack Query; events apply `setQueryData` for known shapes (card cost, time-in-stage, run status) and `invalidateQueries` for coarse changes.
- **What arrives live** (S-23.14): every `task.*` and `run.*` event reaches `org`, the event's `project:<id>` and its `task:<id>` as a `domain_event` frame whose `data` is ids and small enums only (technical/08 § "SSE contract") — so the bridge (`realtime/query-bridge.ts`) only ever **invalidates**: the project's and the task's and the run's prefixes from the ids, the inbox for `task.question.*`/`task.approval.*`, the agents list for any event naming a run, the workers list for a claim naming a worker. A mounted Agents, Inbox, board or task screen therefore refetches within the hint's round trip, without navigation; `setQueryData` on known shapes is still not built (a frame carries no DTO to set).
- Transcripts: event-sourced zustand store per run fed by `TranscriptEvent`s; rAF-batched delta application; coalesced text deltas; only the streaming block is "hot"; TanStack Virtual chat mode with follow-tail and "paused updates, N behind" indicator when scrolled up.
- Board (`features/board.tsx`, `features/board-card.tsx`, S-23.9a): below `xl` the five columns are a sideways-scrolling row that snaps per column, from `xl` a five-column grid; each card is the task's phase (`PhaseTrack` over the page's `stages`, with the agents read's activity while a run is live), its needs-you ◆ and count, its loop and conflict badges and a `···` menu (pause/resume, cancel and return-to-stage through Dialogs, the task page's commands; *Open ticket*/*Open merge request* through `ActionMenuLinkItem`; pause/resume only where the page's `can_pause_task`/`can_resume_task` say the caller may). `?view=list` is the same page as an Issues-style list with state/template/needs-you filters applied on the client. The start form is a Dialog opened by `#start-ticket`. Per-card selector subscriptions, a throttled `now` tick and virtualisation past ~200 cards are not built.

## Transcript model (shared package `@app/transcript`)
`TranscriptEvent { seq, runId, ts, kind: text|thinking|tool_use|tool_result|agent_start|agent_end|compaction|system|user|steer|result, parentToolUseId?, toolName?, payload }` produced by the server normaliser (versioned, golden-fixture tested); client reducer builds blocks; renderer registry: `Edit/Write/MultiEdit` → diff, `Bash` → ANSI terminal block, `Read/Grep/Glob` → code with line numbers, `Agent` → nested transcript, `WebFetch/WebSearch` → link cards, `mcp__*` → JSON viewer, `AskUserQuestion`/platform `ask_human` → question card, default → generic card.

> **2026-10-06 (PROGRESS backlog 496):** the stored kinds are `@platform/contracts`' `transcriptKindSchema`, and it gained `progress` — a line the agent reported through `report_progress` (`summary`, `percent_complete`, `truncated`). The run page renders it as a *progress* row of its log (the percentage as a badge, a cut marked *shortened by the platform*), searchable by its words; the task page shows a running stage's newest one (the screens table below).

> **S-23.10 (research/19 § 5.2 "Run"):** `transcript/view.tsx` draws the blocks as a **log**, as an Actions job does: a tool call is a collapsed **log step** — a native `<details>` whose line is chevron, `StatusIcon`, the tool (a platform tool in the vocabulary's words, any other by its name through `toolWords`), the argument summary (`argumentSummary`, the stage dialog's) and the duration right-aligned (`transcript/steps.ts`; a `ToolBlock` keeps `startedAt` beside `at`, which a folded result moves) — open on arrival while it has no result or after it failed, and the renderer registry's body is what opening it shows; assistant text is prose lines, thinking and the CLI's `system` notice are collapsed steps, the other kinds one-line rows. The scroller is a pane of its own (`scrollerClassName`; the run page sizes it to the viewport), and following its end is keyed on the tail's signature — a new block, a folded result, a streaming block's next words — not only on the count. Still not virtualised (the reason is `view.tsx`'s docblock).

## An upgraded server under an open tab
The bundle's response schemas are strict, so after an upgrade an open tab refuses the new server's answers as `invalid_response` (PROGRESS backlog 487). **Since WP-154 (d)** the bundle carries the commit it was built from — `APP_COMMIT`, compiled in by `vite.config.ts` as `__PLATFORM_BUILD_COMMIT__` from the same build argument the server reports at `GET /api/version` (`docker/app.Dockerfile`'s `web` stage), `dev` when there is none — and the SPA re-reads `/api/version` (a loose read of `commit` only) on every `invalid_response` and every SSE reconnect (`app/platform-version.ts`). When the server's `commit` differs from the bundle's and neither is `dev` or null, the API client throws `PlatformUpdatedError` instead of the schema error, `ErrorNotice` renders nothing for it — decided by the error's type since **WP-167** (backlog 524), never by its text, so a screen hands the notice the error itself (`error={…}`) and `apps/web/src/error-notice-census.test.ts` refuses `String(…)` in its `title`/`detail` — and the shell shows one banner: *The platform was updated — reload this page*. When the two are equal the schema error stands: a real contract defect stays visible.

## Failure containment
A render that throws must cost one region, never the tab. Two boundaries, because they catch different failures:
- **Route level** — `defaultErrorComponent` on the router. TanStack Router installs a catch boundary per match *only when that match has an error component*, so without this option the nearest boundary is the root's and a screen that throws replaces the header and the navigation too (measured at WP-20: the document held the router's built-in error component and nothing else). With it, the failure is contained inside `<main>` and the navigation stays usable.
- **Application level** — one `ErrorBoundary` outside every provider, for what the router cannot see: a throw in a provider, in a provider's effect, or in the router's own render.

The fallback names the area, shows the error's message **sanitised and bounded** (an error message can quote a provider's string, so BD-022 applies to it), and offers *Try again* plus *Reload the page*; a boundary also clears itself when the route changes, so navigating away is a recovery. The fallback is deliberately poor in dependencies: a fallback that throws is caught only by the next boundary out, and the application-level one has none.
