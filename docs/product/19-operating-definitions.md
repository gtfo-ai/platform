## 2. Protected paths defaults (BD-024/025)
`tests/**`, `**/*.test.*`, `**/*.spec.*`, `**/__tests__/**`, `.gitlab-ci.yml`, `.github/**`, `.agentic/**`, `.claude/**`, `CLAUDE.md`, `AGENTS.md`, `.mcp.json`, `Dockerfile*`, `docker-compose*.yml`, `**/migrations/**` (flag only, not block). Changes to protected paths are allowed only when the Implementation Plan lists them with a reason; otherwise the CI gate returns the task and the Reviewer sees a blocker.

## 3. Command policy defaults per stage (BD-025)
- **Block (all stages):** `rm -rf /*`, `git push --force*`, `git push origin :*`, `git branch -D *`, `git reset --hard origin/*` on protected branches, `docker *`, `sudo *`, `curl * | sh`, `wget * | sh`, `npm publish`, `pip upload`, `gh release *`, `glab release *`, any command writing outside the workspace, `kubectl *`, `terraform apply`.
- **Read-only stages (Refinement, Architecture, Investigation, Code review, Business review, Retrospective):** allow `git log/diff/show/blame/status`, `ls/cat/grep/rg/find`, `cat`, language-native read tools, the project's test/lint commands (review stages only); everything else → ask (rarely reached because write tools are absent).
- **Implementation:** allow the project's declared commands (`how-to-run.md`: test, lint, format, build, typecheck), `git add/commit/push origin agentic/*`, `git rebase`, `git fetch`, package manager *install from lockfile* (`npm ci`, `pnpm install --frozen-lockfile`, `pip install -r`), `make *` targets listed in the KB; **ask** for `npm install <pkg>`/`pip install <pkg>`/`composer require` (dependency policy), `git push` to any other branch, network calls to non-allow-listed hosts, database migrations against non-local databases; block as above.
- The organisation can only tighten these; projects can add to allow within the org maximum.

## 4. Significance scoring for knowledge proposals (BD-018, Q25)
Score in [0,1] assigned by the Curator with recorded reasons:
| Class | Score | Default handling |
|---|---|---|
| Formatting/typo/link fix in an existing item | 0.1 | discard threshold 0.2 → discarded (audit line only) |
| `last_confirmed` bump, reference item, new glossary term already used in the ticket | 0.3 | proposal, or direct commit when `auto_apply` is on |
| New lesson or pitfall with evidence from one task | 0.5 | proposal (auto-apply band if opted in) |
| Update to an existing lesson's guidance; new technical fact in `technical/*` | 0.6 | proposal (above `proposal_above` 0.6 → always proposal) |
| New rule; promotion lesson → rule; business rule; decision record; change to `direction.md` | 0.9 | always proposal, maintainer only |
Defaults: `discard_below: 0.2`, `proposal_above: 0.6`, `auto_apply: off`.

## 7. MR description and commit conventions (product/13)
- Title: `<type>(<scope>): <summary> [PROJ-123]` (Conventional Commits types; scope optional).
- Body sections: Summary · What changed · Acceptance criteria (checklist with evidence) · Validation (commands + results, CI link) · Deviations from plan · Follow-ups filed · Requested by · Task link · footer `Generated by Agentic (run <id>) · cost so far $X`.
- Commits: Conventional Commits, imperative, ≤ 72-char subject, body explains why, `Signed-off-by` (DCO), one logical change per commit; no `wip:` commits except the take-over export.

## 8. Onboarding interview question bank v1 (product/06)
Single English bank; the Product Manager role asks in the interviewee's language (BD-016) and stores answers verbatim plus an English summary line. Sections and questions: **Product** — what it is, for whom, what it is not, one-sentence value; **Users** — personas, their goals, what annoys them; **Business rules** — invariants that must never break, regulatory constraints, money/tax/privacy rules; **Glossary** — 10 words with special meaning; **Direction** — goals for 3–6 months, non-goals, accepted debt, planned rewrites; **Quality bar** — definition of done, test expectations, accessibility/performance/security expectations, documentation duties; **Review** — who reviews, what they care about most, MR size preference, must-have reviewers per area; **Communication** — language, tone, what goes to Slack, working hours for questions. Each question has a "skip" and "not applicable" option; skipped sections lower the completeness score with the stated unlock.

## 13. Shadow report specification (Q31)
Per ticket: agent artifacts (spec, plan, diff stats, tests added), human MR (if any): files touched, size; comparison: file-overlap Jaccard, size ratio, tests added ratio, acceptance criteria the human MR covers vs the agent's; Reviewer findings the human MR would have received (posted nowhere); predicted cost vs shadow cost; reviewer minutes estimate (from MR events); confidence note. Aggregate report per shadow batch: predicted cost per ticket by size, similarity distribution, list of "high similarity + low cost" tickets as the launch candidates.

## 15. Cost estimation model v1 (product/18)
Estimate at Refinement = median actual cost of the last 30 merged tasks in the project with the same template and size (S/M/L/XL); fewer than 5 samples → platform defaults (feature S $8, M $18, L $35, XL $60; bug S $6, M $14, L $28; chore $4) blended 50/50 once ≥ 3 samples exist. Shown as a range (p25–p75). Budget approval triggers when estimate p75 > threshold. Accuracy metric tracked per project; model revisited after dogfooding.

## 16. Human time accounting rules (product/18)
Minutes derived from events, never from tracking: review = from the first human MR activity (comment, approval, review start) to merge or last activity, capped at 8 h per calendar day and excluding gaps > 2 h; question = asked → answered, capped at 30 min per question (reading + answering); approval = 10 min flat; steer = 5 min flat per steer. Per-user breakdown off by default; totals per task always shown. Documented in the UI tooltip.

## 17. Ticket readiness linter comment (product/18)
One comment, marker `<!-- agentic:linter -->`, ≤ 10 lines: readiness score (0–100) with the top 3 missing elements (acceptance criteria, scope boundaries, validation), up to 5 questions a developer would ask, and a one-line offer ("add label `agentic` to have it delivered"). Never re-posted; updated in place if the ticket is edited and re-lint is enabled.

## 18. History bootstrap specification (product/18)
Inputs: last N merged MRs (default 200, max 1 000) with discussions and diff stats; closed tickets of the last 6 months (titles, descriptions, resolution comments); commit messages. Batches of ~20 MRs per Sonnet 5 run with a fixed extraction schema: recurring reviewer requests → rules candidates; conventions observed ≥ 3 times → `conventions.md` entries; pitfalls (MRs with ≥ 3 review rounds) → lessons; glossary terms; module ownership hints. Every proposal cites MR/ticket links as evidence. Budget cap default $20, shown before start. Output goes to the proposal queue only.

## 19. Take-over protocol (product/18)
Pause: current run is interrupted gracefully; the Developer commits WIP (`wip: hand-over to <user>`) and pushes `agentic/<task>`; workspace exported (transcript JSONL + optional tarball); task state `Paused (taken over by <user>)`; ticket workpad and Slack updated with: branch, resume command (`git fetch && git checkout agentic/PROJ-123`, plus `claude --resume` guidance and the transcript download), and how to hand back. Hand-back: the human pushes to the same branch and chooses a stage in the UI (default: Code review); the platform re-provisions a workspace from the branch, re-enters the stage with a note "continued by human: <summary>". Timeouts: a taken-over task escalates to `Needs human` after 5 working days of inactivity; retention of the exported workspace 14 days.

## 20. Storage gauge (Q13-b)
Org dashboard shows transcript storage size and monthly growth; at 50 GB a warning suggests setting `APP_TRANSCRIPT_RETENTION_DAYS`; purge is by month partitions with a confirmation listing affected months.

## 21. Dogfooding plan (Q17)
Two founder projects (both Jira Cloud; GitLab one gitlab.com, one self-managed). Phase A (after M1): onboarding + shadow mode on 10 closed tickets each; success = install < 1 hour, discovery draft accepted with ≤ 30 min edits, shadow similarity reported. Phase B (M1+M2): 10 live chore/bug tickets per project in Supervised mode; success ≥ 60 % merged, cost per merged task recorded, ≥ 5 accepted KB proposals per project. Phase C (M3): 10 feature tickets per project incl. review-only on 20 human MRs; MVP exit criteria in product/14. Timeline is milestone-relative (each phase ≤ 3 weeks); dates set when M1 ships.
