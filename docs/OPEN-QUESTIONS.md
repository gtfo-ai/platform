## Open

**Q42 TD-024 names `@slack/bolt` and `@slack/web-api`, and both contradict structural constraints technical/06 records as binding.** TD-024 says "Slack uses the official `@slack/bolt` (Socket Mode) with `@slack/web-api`", while the same decision's rationale for handwriting the other four clients is that they are "fully covered by contract tests with recorded fixtures". WP-10 found the two halves cannot both hold, and the evidence is specific rather than a preference. **(1)** `WebClient` retries by itself — "The client will retry a failed API method call up to 10 times, spaced out over about 30 minutes" — and waits out a 429 on its own wall clock (<https://docs.slack.dev/tools/node-slack-sdk/web-api/>, retrieved 2026-09-10). technical/06 § "Provider module layout" states the opposite as structural: "`fetch` is injected, and the client never retries. Backoff, the rate-limit budget and the shadow guard live in `IntegrationActionExecutor`, which owns the injected timer; a retry loop inside a provider would be a second one running on a wall clock" — which is also standing rule 2. **(2)** `WebClient` exposes no transport seam: only an `agent` and `slackApiUrl`, so "contract suite in replay" would need a live HTTP listener instead of an injected `fetch`, and the assertion that a shadow-mode call issues *zero* requests would have nothing to observe. **(3)** Bolt's `App` owns its own dispatch (`app.event`, `app.action`), a second router beside TD-005's, and its signature verification lives in a receiver the platform does not use (it is on Fastify, TD-002). WP-10 could not defer it: the acceptance criterion is a contract suite, and the suite's transport is the decision. — *Recommendation (implemented in `packages/integrations/src/providers/slack`):* treat Slack like the other four — a thin in-repo `fetch` client over the five Web API methods the port needs, in-house `v0` signature verification with `timingSafeEqual` (which is what TD-024's own title says for webhook signatures), and a Socket Mode client whose WebSocket factory, timer and clock are injected, so reconnect backoff is testable and the envelope path is exercised without a workspace. Nothing about the design forecloses Bolt: `SocketConnect` is one function and `SlackFetch` is one function. Confirm, and decide whether TD-024 should be amended to say "handwritten thin clients on native fetch for **all five** providers" — the neutral reading of its own rationale — or whether the dependency is wanted for a reason the record does not state (Bolt's assistant/agent features, or its reconnection handling, are the two candidates).
**Q43 Sentry publishes no comment endpoint, no merge-request link and no injectable agent tooling — so what does the `ObservabilityErrors` port promise?** technical/06 and the port declare `comment(issue, text)`, `linkMergeRequest(issue, mrUrl)` and `agentTooling()`, and product/08 describes the platform commenting on the issue when the fix merges. WP-11 found that Sentry's *published* API reference documents 21 endpoints for Events & Issues and **none of them creates or lists a comment or a code link**; the only comment surface Sentry publishes is the inbound `Sentry-Hook-Resource: comment` webhook. The agent-tooling half is the same shape: the hosted MCP server at `mcp.sentry.dev` states "All connections use OAuth. The first connection will trigger an authentication flow", which a run container cannot perform and which a tooling spec carrying *names only* (BD-002, BD-025) cannot express; the classic `sentry-cli` has a fully documented environment and **no issue commands at all**; and the new interactive CLI's documentation lives off the vendor's documentation site. WP-11 could not defer it: every fixture in this work package is built from published documentation, and an adapter that posts to an endpoint no vendor page names is an adapter that breaks without a changelog entry. — *Recommendation (implemented in `packages/integrations/src/providers/sentry`):* declare `capabilities().comments = false`, `linkMergeRequest = false` and `mcp = false` and **refuse** with `unsupported_capability`, which the shared contract suite already asserts on the false branch; discharge "tell Sentry the fix shipped" with the documented `resolve(issue, {inRelease})` plus the vendor's own `Fixes <SHORT-ID>` commit-message convention, which the setup guide makes the supported route; and return an agent-tooling spec that mounts nothing. Relaxing `expectAgentTooling` to allow that was paired with a **new** shared obligation so it is not a weakening (standing rule 23): a spec that mounts no CLI and no MCP server must declare **no secret variable at all**, because a credential injected into a run container for a tool that is not there is a secret handed out for no reason. Confirm, and decide three things: whether `ObservabilityErrorsPort` should keep `comment`/`linkMergeRequest` at all when its first provider cannot implement either against documented API (a self-hosted Sentry exposes the same surface, so this is a type-level question rather than a SaaS one); whether the platform should call Sentry's *undocumented* `…/issues/{id}/comments/` endpoint behind an opt-in config flag; and whether BD-025 should grow an OAuth-capable mount so a hosted MCP server can ever be given to an agent.

**Q40 A git provider token cannot be scoped to a branch pattern, so what enforces `push:agentic/*`?** BD-025 and the `GitProvider` port describe a minted credential carrying `branchPatterns` — `push:agentic/*` — and WP-09 found that GitLab has no such thing: a project access token carries *scopes* (`read_repository`, `write_repository`) and a *role*, and nothing narrower. GitHub's fine-grained tokens are the same shape. So the pattern on `MintedCredential` is a platform-side statement of intent that no provider enforces, and the only things actually keeping an agent's token off `main` are the repository's **protected branch** configuration and the workspace manager's own credential helper. WP-09 could not defer it: minting a `push` credential while saying nothing about what it can reach would ship a credential that reads as narrower than it is. — *Recommendation (implemented in `packages/integrations/src/providers/gitlab`):* keep `branchPatterns` on the credential as the constraint the **workspace manager** (WP-14) applies when it configures the push refspec; state at the adapter, in its divergence register, that no provider enforces it; and add the compensating control on the provider side — `isBranchProtected` and `branchProtection` on the GitLab adapter, plus a setup guide that makes "protect the default branch with *Allowed to push and merge: No one*" a prerequisite rather than a suggestion. Confirm, and decide two things: whether `GitProviderPort` should gain a branch-protection member so WP-15 can evaluate that gate through the type port instead of down-casting to a provider (GitHub has the same concept, so this is a type-level question rather than a GitLab one), and whether onboarding should **refuse** a project whose default branch is unprotected rather than warn about it.
**Q41 Whether the SDK session mirror is redacted.** TD-012 enumerates the write paths redaction applies to — `run_messages`, `integration_actions`, `events.payload`, `config_audit`, artifacts and KB commits — and the Agent SDK's `sessionStore` mirror is not among them. TD-007 puts the mirror outside the transcript deliberately ("the platform's own stream consumer, **not** the SDK `sessionStore` mirror, writes every completed SDK message"; the mirror exists "for cross-host resume (best-effort)"). WP-12 had to wire the mirror, so it could not defer the question: the mirror holds the session verbatim, including any credential a tool printed before the `PostToolUse` hook rewrote the model's copy. — *Recommendation (implemented in `packages/infrastructure/src/runner/session-mirror.ts`):* **the mirror is not redacted.** Its only consumer is `resume`, which replays it into the model's context, and a resumed run whose own earlier tool output has become `[REDACTED sha256:…]` has had its memory corrupted rather than protected — it would re-read a file it has already read, or re-run a command whose output it can no longer see. The mirror is therefore treated as credential-bearing storage: the same database and access control as `secrets`, never rendered to a human, never published on an event, never quoted in a log. Three consequences to confirm: the mirror should carry the same retention window as `run_messages` (`APP_TRANSCRIPT_RETENTION_DAYS`, technical/03) rather than living for ever; a take-over export (technical/04 § "Resume and take-over") hands a human the session JSONL, so **the export path is the one that must redact**, and that is WP-27's, not WP-12's; and the mirror is optional — an operator who does not want unredacted session copies in the database can leave it unwired, and cross-host resume then degrades to starting the stage again. Confirm, and decide whether the mirror should be encrypted at rest with `APP_SECRET_KEY` like `secrets` rather than stored as plain JSONB.

**Q39 How the first account on a fresh instance is created.** `technical/08` lists `POST /api/org/users/invite` and Better Auth's sign-in routes, and `product/06`'s wizard begins with an operator already signed in — but nothing says how that operator's account comes to exist on an instance whose `users` table is empty, nor whether self-registration is open. WP-06 could not defer it: an instance nobody can sign in to has no testable login. — *Recommendation (implemented in `apps/server/src/auth/bootstrap.ts` and `.env.example`):* **open registration is off by default** (`APP_ALLOW_SIGNUP=false`; with it on, a new account gets `member`), and the first administrator comes from the environment — `APP_BOOTSTRAP_ADMIN_EMAIL` plus `APP_BOOTSTRAP_ADMIN_PASSWORD` (or its `_FILE` variant), applied **only** while the instance has no users at all, and created through Better Auth's own sign-up path so the password is hashed by the same code a later login verifies it with. The account is promoted to `admin` in the same boot. The alternative — "the first person to sign up becomes the administrator" — hands the instance to whoever reaches it first in the window between the container starting and the operator opening the browser, which for a self-hosted product on a public address is a real race, not a theoretical one. An instance with no users and no bootstrap credential starts and logs a warning that nobody can sign in, rather than refusing: an operator adding the variable and restarting is a better failure than a container that will not boot. Confirm, and decide whether the onboarding wizard (WP-21) should end by forcing a password change on that account.

**Q38 Working-day calendar.** `technical/12` writes `limits.question_timeout: 1 working day` and `packages/contracts` publishes the grammar (`N [working] minutes|hours|days`), but no document says what a *working* day is: which weekdays count, which hours of them count, where holidays come from, and in whose time zone. WP-05 had to resolve deadlines to an absolute instant, so it could not defer the question. — *Recommendation (implemented in `packages/application/src/scheduling` and `.env.example`):* an **organisation-level** calendar — working days are an organisational fact, not a repository one, so `.agentic/config.yml` may not set it — with four fields: `timezone` (IANA, seeded from `TZ`, default UTC, never the host clock), `working_weekdays` (default Monday–Friday), `working_hours` (default 09:00–17:00 in that zone) and an explicit `holidays` list of dates (default empty; the platform never guesses a country's public holidays, and an operator who wants them pastes them in or the onboarding wizard offers a country list later). "Working time" is then time inside those windows and nothing else, which makes `1 working day` = one full window (Friday 16:00 + 1 working day = Monday 16:00) and `2 working hours` behave consistently. Confirm, and decide whether the wizard should offer a holiday preset per country (product/06 step 5) and whether quiet hours (WP-32) should reuse the same window.

**Q37 Hazards the command block-list of `product/19` §3 states as one spelling each.** The list gives `rm -rf /*`, `git push --force*`, `git push origin :*`, `git branch -D *` and `curl * | sh` / `wget * | sh`. Every one of them is a hazard written as a single spelling, and the other spellings of the same hazard do not match the pattern: `rm -fr /`, `rm -r -f /`; `git branch --delete --force main`; `git push -f`, `git push … --delete` / `-d`, the force refspec `git push origin +agentic/x:main`, and the plain refspec `git push origin agentic/foo:main`, which writes `main` under an allow entry that names only `agentic/*`; and `curl http://x|sh`, `| bash`, `| /bin/sh`, `|&`, `wget -O- http://x|sh`. WP-02 declined to invent the missing patterns (security rules belong in the document, not in code the document does not state), named the gap in `DECLINED_BLOCK_VARIANTS`, and recorded that they all land on `ask`, never `allow`. **WP-02a disproved that last claim:** `git push origin agentic/x -f`, `git push origin agentic/x --delete` and `git push origin agentic/foo:main` all returned **allow**, because the allow entry `git push origin agentic/*` was carrying them, and the `curl|sh` spellings returned `ask` rather than `block`. The line the code now draws: a missing spelling that only decides between `ask` and `block` stays the document's to fix — the command can never reach `allow`, so the code is not what is keeping it out; a missing spelling reachable from the **allow**-list is closed in code, because the allow-list is the one thing the module defends. So `git push -f*`, `git push --delete*`, `git push -d*` and `git push origin +*` joined the block list, the refspec form floors at `ask`, and the `curl|sh` family is caught by normalising a pipeline's spacing and spelling any shell stage `sh`; `rm -fr /` and `git branch --delete --force main` are unchanged and still `ask`. — *Recommendation:* amend product/19 §3 to state the hazards rather than one spelling of each — `rm` with any recursive flag outside the workspace; branch deletion in either form; force-pushing, deleting or retargeting a remote ref in any spelling, refspecs included; piping a download into any shell — so that the document and the code say the same thing. Two further items on that list (`any command writing outside the workspace`, `network calls to non-allow-listed hosts`) cannot be a command pattern at all and are enforced by the run container and the egress proxy (TD-021); they are recorded in `UNPATTERNABLE_BLOCK_ITEMS`. WP-02a also found that this module's approximation of the first of those two — flooring a `> file` redirection at `ask` — is walked around by flags that write a path directly (`git diff --output=`, `git log --output=`, GNU `find -fprintf` / `-fls`, all verified against the real tools); they are now floored by `HAZARDOUS_ARGUMENTS`, along with `pip install --target/--root/--prefix/--log/--report`. A second review round added two more families to the same list: `git difftool --extcmd`, and `git log --ext-diff` / `git show --textconv`, which run whatever the *repository's own* config names and so are untrusted input under BD-022.

**Q36 The full RBAC capability map.** `technical/08` names seven capabilities by example (`task.answer_question: member`, `task.approve_plan: maintainer`, `run.steer: member`, `kb.proposal.decide: maintainer`, `project.settings.write: admin`, `budget.write: maintainer`, `transcript.read: member`) and `product/11` describes the four roles in one sentence each; WP-02 needed a decision for every action the API of `technical/08` exposes. — *Recommendation (implemented in `packages/domain/permissions.ts`, asserted by an exhaustive role×action test):* keep the seven documented entries verbatim and derive the rest from product/11's sentences — **viewer** reads (org, projects, tasks, artifacts, runs, budgets, knowledge); **member** acts on a task without deciding for the team (create, pause/resume, retry or return a stage, take over and hand back, answer questions, steer, cancel or retry a run, give feedback, ask the task, export, read transcripts); **maintainer** decides (approve plans and budgets, decide knowledge proposals, write the KB, write budgets, pipeline and autonomy settings, cancel a task, `@agentic rework`, run shadow and discovery, read the audit log, read integrations); **admin** administers (users, project membership, project creation and settings, integrations, org settings). The judgement calls worth a veto: **cancelling a task, `rework` and `return_to_stage` are maintainer, not member** — the first two discard work the team paid for, and `return_to_stage` sends the task backwards and burns one of BD-008's bounded iterations exactly as `rework` does, so leaving it at `member` would make the maintainer gate on `rework` bypassable through the cheaper action (retrying the *current* stage costs a run rather than a loop and stays at `member`); and **`integration.read` is maintainer, not viewer** (integration config is close to credentials).
