**Q90 The release pull request gets no CI run of its own, and the only fix is a credential this repository does not carry.** `release.yml` runs release-please with `GITHUB_TOKEN`, and GitHub's rule is that *“events triggered by the `GITHUB_TOKEN` will not create a new workflow run”* with `workflow_dispatch` and `repository_dispatch` as the only exceptions (https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow). WP-42 handled the **tag** half of that rule — the release dispatches `image.yml` rather than relying on `push: tags` **when, and only when, it ran on the fallback**; a tag an administrator's token created starts `image.yml` by itself and the release watches that run instead — and missed the **pull request** half: `ci.yml`'s eleven jobs run on `pull_request`, `push: main` and `merge_group`, so not one of them, `dco` included, ever reports on the release PR, while `CONTRIBUTING.md` § Branch protection tells an administrator to require all eleven. That PR is then unmergeable until a human closes and reopens it (the event is then the human's, so a run starts), a merge queue evaluates it on `merge_group`, or an administrator bypasses — and `docs/TODO.md`'s first-release row told the merger to *read the `dco` verdict on the release PR*, a verdict that on this path never exists. It is **latent with a dated trigger**, like Q89: nothing is wrong until the first release PR, which is the first time anybody meets it. — *Recommendation, implemented:* `release.yml` takes `${{ secrets.RELEASE_PLEASE_TOKEN || secrets.GITHUB_TOKEN }}` — a fine-grained PAT or a GitHub App installation token an administrator creates, a pull request opened by either being an ordinary event that runs CI — and **states what the fallback costs in its own header** instead of leaving it to be discovered on the release: no checks on the PR, the close-and-reopen re-trigger, and a `dco` verdict reachable only through `merge_group` or the `push: main` run *after* the merge, which is after the tag exists. An unset secret is an empty string, so `||` is the whole fallback mechanism. The **name** is written down in `CONTRIBUTING.md` § *What an administrator sets up once* and in `docs/TODO.md`'s first-release row, and `scripts/release.test.ts` fails when either stops naming it; **no value is anywhere in this repository and none may be** (BD-002, TD-020). What is left for a human is the part a work package cannot decide: **which of the two, and who holds it.** A GitHub App is the shape release-please's own documentation recommends and the one that survives a maintainer leaving; a PAT is ten minutes and is tied to one person. *Recommendation: the App once there is more than one maintainer, the PAT until then* — a release mechanism nobody can run is worse than one person's credential. Whichever is chosen, **`signoff` in `release-please-config.json` changes with it**: the `dco` job compares a commit's `Signed-off-by` e-mail with its author's, and the checked-in `github-actions[bot]` identity is correct only on the fallback path (a PAT commits as its user, an App as `<app-name>[bot]`). **Owner:** the repository administrator, before the first release PR is merged — it is part of `docs/TODO.md`'s first-release row, which is where a merger will look. — *Closed by withdrawal (TD-019's amendment, 2026-09-16, the product owner's decision).* There is no release pull request to give CI to: the release-please job is **retired** — `release.yml` is `workflow_dispatch` only — and every push to `main` is the release, published by `image.yml` as `sha-<7>`, `edge` and `latest`. The question this entry leaves for **WP-71** is the one about identity, not CI: if release-please is ever dispatched by hand, `release-please-config.json`'s `signoff` still has to name whatever identity makes the commit.

**Q37 Hazards the command block-list of `product/19` §3 states as one spelling each.** The list gives `rm -rf /*`, `git push --force*`, `git push origin :*`, `git branch -D *` and `curl * | sh` / `wget * | sh`. Every one of them is a hazard written as a single spelling, and the other spellings of the same hazard do not match the pattern: `rm -fr /`, `rm -r -f /`; `git branch --delete --force main`; `git push -f`, `git push … --delete` / `-d`, the force refspec `git push origin +agentic/x:main`, and the plain refspec `git push origin agentic/foo:main`, which writes `main` under an allow entry that names only `agentic/*`; and `curl http://x|sh`, `| bash`, `| /bin/sh`, `|&`, `wget -O- http://x|sh`. WP-02 declined to invent the missing patterns (security rules belong in the document, not in code the document does not state), named the gap in `DECLINED_BLOCK_VARIANTS`, and recorded that they all land on `ask`, never `allow`. **WP-02a disproved that last claim:** `git push origin agentic/x -f`, `git push origin agentic/x --delete` and `git push origin agentic/foo:main` all returned **allow**, because the allow entry `git push origin agentic/*` was carrying them, and the `curl|sh` spellings returned `ask` rather than `block`. The line the code now draws: a missing spelling that only decides between `ask` and `block` stays the document's to fix — the command can never reach `allow`, so the code is not what is keeping it out; a missing spelling reachable from the **allow**-list is closed in code, because the allow-list is the one thing the module defends. So `git push -f*`, `git push --delete*`, `git push -d*` and `git push origin +*` joined the block list, the refspec form floors at `ask`, and the `curl|sh` family is caught by normalising a pipeline's spacing and spelling any shell stage `sh`; `rm -fr /` and `git branch --delete --force main` are unchanged and still `ask`. — *Recommendation:* amend product/19 §3 to state the hazards rather than one spelling of each — `rm` with any recursive flag outside the workspace; branch deletion in either form; force-pushing, deleting or retargeting a remote ref in any spelling, refspecs included; piping a download into any shell — so that the document and the code say the same thing. Two further items on that list (`any command writing outside the workspace`, `network calls to non-allow-listed hosts`) cannot be a command pattern at all and are enforced by the run container and the egress proxy (TD-021); they are recorded in `UNPATTERNABLE_BLOCK_ITEMS`. WP-02a also found that this module's approximation of the first of those two — flooring a `> file` redirection at `ask` — is walked around by flags that write a path directly (`git diff --output=`, `git log --output=`, GNU `find -fprintf` / `-fls`, all verified against the real tools); they are now floored by `HAZARDOUS_ARGUMENTS`, along with `pip install --target/--root/--prefix/--log/--report`. A second review round added two more families to the same list: `git difftool --extcmd`, and `git log --ext-diff` / `git show --textconv`, which run whatever the *repository's own* config names and so are untrusted input under BD-022.
