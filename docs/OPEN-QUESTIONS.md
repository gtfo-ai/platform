# Open questions

Answered questions move to the **Decision log** at the bottom with the founder's answer and the document that records it. Only genuinely open items stay in the top section.

## Open

**Q59 A task whose stage cannot be *started* has no product-visible ending, and the day a webhook can reach the pipeline is the day a real ticket meets one.** `StageExecutor` has exactly two endings for an agent stage — the run completed and produced an artifact, or the run ended without a usable result and the task is escalated. A `runner.start()` that **throws** had neither: transaction 1 has already created the `runs` row and emitted `run.created`/`run.started`, so the run stayed `running` for ever, the task sat at a stage nothing would move, and the `stage.execute` job retried into pg-boss, where no screen in the product shows it. That is not hypothetical in this build: `unavailableClaudeRunner` (`apps/server/src/pipeline.ts`) throws `RunnerUnavailableError` because the runner-to-launcher transport is **Q52**, deliberately unbuilt — and until WP-15c nothing produced a ticket, so nothing ever reached an agent stage. WP-15b's discovered work named the question and left it to whoever landed the ingress first. — *Recommendation (implemented in `packages/application/src/pipeline/stage-executor.ts`):* **no new task state.** `escalateTask` already means *a human must act*, it is what the executor does for every other run that ends without a usable result, and the product's screens, templates and `retry-stage` command all know it; a third spelling of "stuck" would be a state no query, template or screen knows about, and it would need a migration to an enum the interpreter reads. So a `start` that throws now fails the run it had already created (`run.failed`, `error_during_execution`, zero usage and zero cost) and escalates the task, in one transaction, with the error's **class name** in the reason and never its message — a runner's error may quote a provider, a URL or a credential, and the executor holds no redactor. Confirm, and decide two things. **(a) Retries.** The escalation happens on the *first* failure, so a transient start failure no longer gets the job's two retries; that is the direction that tells somebody, and `POST /api/tasks/:id/retry-stage` is the human's answer, but a transport that flaps (which Q52's answer may well produce) would escalate a task per flap. If that is wrong, the fix is a retryable/terminal distinction on the runner's errors rather than a new state. **(b) Whether `unavailableClaudeRunner` should exist at all once Q52 is answered** — a build with no transport could refuse to compose the pipeline instead of composing one that escalates every agent stage, which is louder but also stops the gates, the status mapping and the workpad from running at all.

**Q60 Nothing rate-limits the webhook endpoint, and it is the platform's only unauthenticated door.** technical/08 § "Rate limits and safety" says "webhook endpoints limited per integration" and WP-15c shipped none. What bounds the cost today is stated rather than implied: a **refused** delivery writes one `integration_actions` row and **no** event and **no** `inbox` row (the last is deliberate — a dedup key an unauthenticated caller can choose is a key it can poison), so the amplification an attacker who knows an integration's uuid can buy is one insert per request against a partitioned, append-only table; an **accepted** delivery costs one `inbox` row and its events, and requires the binding's own signature. — *Recommendation:* **a token bucket per `integrations.id` in front of `verify`, answering 429 with `Retry-After`, reusing `packages/application/src/integrations/rate-limiter.ts` rather than writing a second one.** It has to come *before* the signature check to be worth anything (verification is the expensive part of a flood) and *after* the integration lookup, so the bucket is per account rather than global — which means one database read survives the limit, and that is the honest cost. Confirm, and decide whether a limited delivery is audited (one row per refusal re-opens the amplification the limit exists to close, so probably a counter and a log line rather than a row) and whether the bucket is shared with the outbound budget of the same integration or is its own.

**Q58 Retrieval has no precision floor, and every mechanism that would give it one is a choice of ranking signal — which is a product decision, not an engineering one.** Nothing between a degenerate query and the context pack rejects it. WP-16 round 1 measured a single stopword query filling **87 %** of the token budget with padding; the *cause* found underneath it was different (`websearch_to_tsquery` joins bare words with **AND**, so the acceptance query matched **0 documents against a real PostgreSQL while the in-memory double returned 15**) and was fixed by extracting keywords and joining them with `OR`. **No relevance floor shipped**, and both candidate shapes were rejected by measurement rather than by preference (`packages/domain/src/knowledge/retrieval.ts:152` and `:163`): an **absolute** floor is backwards, because `ts_rank_cd` measures cover density and a common word is dense — `"the"` ranked padded pages at **0.947** while a good query ranked its correct answer at **0.048**, so every threshold that excludes the noise excludes the signal by a factor of twenty; and a floor **relative to the best text score** is store-dependent, because the correct second answer sits at **0.667** of the best against PostgreSQL and at **0.267** against the in-memory double on the same corpus and the same query, so the 0.3 ratio drawn from the PostgreSQL numbers dropped the right page on the store the acceptance figure is measured on. Those two are **pre-fix figures and cannot be reproduced** — that state is gone — so they are evidence about why a floor was rejected, not numbers to tune a new one against. What the shipped fix closes is narrow and store-independent: `MIN_QUERY_TERM_LENGTH = 4` (`packages/domain/src/knowledge/query.ts:45`) drops tokens of **three characters or fewer**, so `"the"` and `"and the of"` extract to no terms at all — and the module's own docblock says what survives: *"it keeps `with`, `that` and `from`"*. Round 2 measured the consequence (`retrieval.ts:176`): the query `"that this with from have been were will your they able such their"` yields 13 terms, returns **10 documents** at ranks **0.900 / 0.898 / 0.898 / 0.898**, and fills **10 707 of 12 000** tokens with **six tier-1 documents**, its top score **0.718** — *above* a good query's correct answer at **0.500** (that good query returns 12 documents and packs 10 552/12 000, the acceptance figure). The 87 %-padding pack is still reachable. A mechanism robust to function words of four letters or more cannot be a length rule and cannot be a fixed number: it needs a signal derived from the corpus, and each candidate trades something the product owns — which is why this is here and not in a work package. — *Recommendation:* **derive inverse document frequency from the project's own index at index time, drop a query term whose document frequency exceeds a threshold, and return no documents when no term survives.** Not a language dictionary and not a stopword list: the knowledge base is mixed Czech/English by design (the fixture vault is, and technical/07's `simple` text-search configuration was chosen for exactly that reason), so `english` would strip function words at both index and query time at the price of committing every project to one language and adding stemming, and a hand-written stopword list is a maintained scope that drifts in the dangerous direction (standing rule 7) and would need one list per language. IDF needs none of that: the indexer already tokenises every chunk, so a per-project lexeme document-frequency table is close to free, and a term that appears in most of a project's documents is uninformative *in that project* whatever language it is in. A query whose terms all drop must return **nothing** rather than everything — the pack then falls back to tier 0 plus the author's own `paths:` globs, which is exactly what a three-letter degenerate query already does today, and an empty result that is honest beats ten pages that are not (standing rule 18). Confirm, and decide three things. **(a) The fallback's visibility:** whether `ContextPackRecord` records that the text-match step contributed nothing and why, because today the absence of tier-1 documents cannot be told from "this stage asked for none" — the same gap Q57's option (c) raises about the code map. **(b) Whether a `ts_rank` normalisation is taken instead or as well** — `ts_rank_cd(..., 1|2)` divides by document length and would demote the measured pages; that is the cheap answer and it should be treated with suspicion, because the noisy pages in the fixture vault are the *padded* ones, so a length normalisation would look excellent there for a reason that is an artifact of the instrument rather than a property of a real corpus (standing rule 5; PROGRESS backlog entry 16). **(c) Where the signal lives:** it must be a property of the `KbSearch` **port**, computed the same way by the in-memory double and by the PostgreSQL adapter, or the double goes back on the kind side of standing rule 1 — the divergence this work package already measured between them is 0 documents against 15, and 0.667 against 0.267 on the same corpus and query. **Needs measurement, and none was taken here (rule 66):** the document-frequency threshold cannot be chosen on the fixture vault, whose padding is one repeated paragraph held by test to share no keyword with the test queries, so it can neither produce a false positive nor calibrate a cut-off; it needs one real repository corpus and a re-run of the four figures above. **No work package owns this today.** WP-16 built the retrieval layer and filed this rather than guessing; **WP-17** is the first consumer that puts a pack into a prompt and is the right home if the question is answered before it starts, otherwise it is a work package of its own. It does **not** block WP-17's delimiter obligation (PROGRESS backlog entry 12), and that delimiter does not close this: a delimiter makes junk text safe, not absent. PROGRESS backlog entry 15 carries the same measurements.

**Q57 TD-010's code map rests on `universal-ctags`, and nothing in this repository installs it.** TD-010 specifies `ctags --output-format=json` as the definition pass, and both the machine this was written on and the runner CI uses fail it in different ways. **Measured, not assumed:** on macOS `/usr/bin/ctags` resolves to `/Library/Developer/CommandLineTools/usr/bin/ctags`, which is **BSD ctags** — `--version` exits **1** with `illegal option -- -`, there is no `--output-format`, and its language list has no TypeScript, Python or Go in it; `universal-ctags` is not on Homebrew here and the only npm package of that name is a single unmaintained `0.0.1` emscripten build (npm, retrieved 2026-09-11), which is not a dependency to put in front of every code stage. A working universal-ctags **6.1.0** was obtained in an `alpine:3.20` container (`apk add --no-cache ctags`) and its output is the recorded fixture `packages/infrastructure/src/knowledge/ctags.test.ts` parses. — *Recommendation (implemented in `packages/infrastructure/src/knowledge/ctags.ts` and `packages/application/src/knowledge/code-mapper.ts`):* **probe, refuse, and let the pack omit the map.** `createCtagsSymbolExtractor` runs `--version` first and requires the string `Universal Ctags` in the banner; anything else — absent, BSD, Exuberant, unlaunchable — is a typed `{ status: 'unavailable', reason }` that `CodeMapper` propagates and `ContextPackRequest.codeMap` is optional to receive. It is **never** rendered as an empty map: zero symbols produces a perfectly well-formed repository map of a codebase with no code in it, which would then occupy tier 0 of every code-stage pack for the life of the deployment, cost tokens, say nothing, and give nobody a reason to look (standing rule 18). A degraded built-in extractor was rejected for the same reason TD-010 rejected writing a parser: a regex symbol pass that silently disagrees with ctags is worse than no map, because the map would look right. Confirm, and decide **where the binary comes from**: (a) `apk add ctags` in WP-22's runtime image and an `apt-get install universal-ctags` step in the CI jobs that exercise the mapper — cheapest, and makes the map a property of the deployment rather than of the developer's laptop; (b) a vendored static build committed under `vendor/`, which makes the platform self-contained and makes this repository responsible for a C binary's supply chain; or (c) accept that the code map is best-effort and absent on some deployments, in which case `ContextPackRecord` should carry a field saying so, because today the *absence* of a `code_map` tier-0 entry is the only signal and a reader cannot tell it from "this stage did not ask for one".

**Q52 TD-021 deploys the launcher as its own container, which implies an RPC surface between the runner and the launcher, and nothing says what it is.** `technical/01` lists `launcher` as a service of its own and TD-021 makes it the only component that may reach `docker-socket-proxy`; `technical/01`'s stage-run flow has the **runner** calling `WorkspaceProvider.create/attach`. Those two are only compatible if `create`, `attach`, `kill`, `export` and `destroy` cross a process boundary, and no document names the protocol, the authentication or the failure semantics of that crossing. WP-14 could not defer the *port* — WP-15 needs it — but it could defer the transport, because until WP-22 has a compose file there is no second process to talk to. — *Recommendation (implemented in `apps/launcher/src/service.ts` and `runtime.ts`):* **build the launcher as a plain object and compose it in-process for now.** Writing an HTTP surface in front of the Docker socket whose only exercise is the test written beside it is the worst kind of security-critical code, and the shape of the surface depends on decisions WP-22 makes — whether the runner and the launcher share the `ctl` volume (they must, for TD-025's socket, which means they already share a machine), whether the launcher gets a token or a Unix socket of its own, and whether `export` streams a tarball over it or writes to a shared volume. Confirm, and decide two things: whether the transport is a Unix socket on a shared volume (which needs no network at all and matches TD-025's own reasoning) or HTTP on the internal compose network with a bearer token; and whether `WorkspaceProvider` stays one interface with a remote implementation, or the remote surface is a *narrower* one — `create`/`destroy` only — with `attach` staying local because the control socket is already on a volume both processes mount.

**Q53 technical/05 §2 says the workspace's `.agentic/workspace/setup` script runs when the workspace is created, and there is no safe place in WP-14 to run it.** It needs the project's toolchain, so it belongs in the run container rather than in a helper; it is untrusted repository content read from the default-branch snapshot (BD-025); and the run container's entrypoint chain is `tini → agentic-runlet → claude`, which is WP-22's image rather than this work package's. WP-14 therefore does not run it, and says so in `docs/TODO.md` rather than pretending the lifecycle is complete. — *Recommendation:* **run it as an ordinary `spawn` through the control socket, issued by the runner before the agent's, rather than in the image's entrypoint.** The two candidates differ in one way that matters: an entrypoint runs the script *before* the shim is listening, so the platform's hooks, its command policy and its transcript are not yet in force and a repository's setup script would be the one piece of project-controlled code that executes with nothing watching. Through the control socket it is an ordinary child of the shim — the same policy, the same stdio, the same kill-on-disconnect — and its output lands in the run log where a failing install can be read. The cost is that the setup script cannot prepare anything the shim itself needs. Confirm, and decide whether a failing setup script fails the run or is reported and continued (the readiness check's answer is "report, never auto-remediate", Q21).

**Q49 `urlSchema` accepts every scheme, and it is shared with the server.** `packages/contracts/src/common.ts` defines `urlSchema = z.url()`, and `z.url()` accepts `javascript:alert(1)`, `data:text/html,<script>…</script>`, `vbscript:` and `file:///etc/passwd` — measured, not assumed (`ticketRefSchema.safeParse({… url: 'javascript:window.__pwned=true'})` succeeds). That schema types `ticket.url`, `mr_ref.url`, `artifacts[].url`, `repo_url`, Jira's `site_url`, `webhook_url` and every provider port's `url`, and WP-20 round 1 shipped five call sites that put those DTO strings straight into an `href`. WP-20 could not defer the *rendering* question, but it deliberately did not change the schema. — *Recommendation (implemented in `apps/web/src/ui/untrusted.tsx` and `apps/web/src/no-html.test.ts`):* **defend at the sink, not at the parse.** Every URL the SPA renders now goes through `safeHref`, and `no-html.test.ts` fails the build if `href=` or `src=` appears in any source file but `ui/untrusted.tsx`, so the guarantee is a property of the renderer rather than of the shape of the data. Narrowing `urlSchema` itself to http(s) was rejected for three reasons: it is the type of a **git remote** (`repo_url`), where `ssh://git@host/x.git` is legitimate and would start failing; it is the type of URLs the platform **receives** from Jira, GitLab, Slack, Sentry and Loki, where a refusal turns one odd link into a hard parse failure of the whole payload (standing rule 20 — fail closed on a mutation, fail open on an inbound notification); and a schema-level refusal would still not make a sink safe, because a DTO is not always the last thing that touches a string. Confirm, and decide two things: whether `packages/contracts` should publish a **separate** `webUrlSchema` (http(s) only) for the fields that exist to be rendered as links — `ticketRef.url`, `mergeRequestRef.url`, `artifactRef.url` — as defence in depth beside `safeHref`; and if so, whether an integration that reports such a URL with another scheme should be **rejected at ingest** (fail closed where the platform is about to write) rather than at read.

**Q47 A `stream_block` says which content block it is, but not which message it belongs to.** `transcriptStreamBlockEvent` carries `block_index`, `first_delta_at` and `last_delta_at`, and the envelope's `seq`; there is no message id anywhere in `TranscriptEvent`. A client rendering a live transcript has to decide when a coalesced partial is superseded by the completed `assistant` message that contains it, and with no identity to match on the only available answer is ordering. WP-20 could not defer it: the run screen is the "click and watch" requirement of product/10, and a client that never retires a partial renders every streamed sentence twice. — *Recommendation (implemented in `apps/web/src/transcript/blocks.ts`):* **pending stream blocks belong to the next `assistant` message and are replaced by it**; a partial for a `block_index` already pending replaces the earlier one; anything still pending when the list ends renders as the block the model is currently writing. This is correct for the stream the runner actually produces (technical/04 emits the partials of a message before the message), and it is wrong only if two messages ever interleave their partials, which the SDK's single-turn streaming does not do. Confirm, and decide whether `transcriptStreamBlockEvent` should gain the SDK message id so the rule stops being about order — it would also let a *replayed* transcript rebuild the same nesting a live one shows, which today it cannot.

**Q54 A ticket description and a merge-request description reach the platform with no byte bound at all, and `emitted-bounds.test.ts` cannot be extended to say so.** `packages/integrations/src/providers/emitted-bounds.test.ts` enumerates every field the two *observability* adapters emit and fails on any string past the largest **named cap** in that binding's configuration. The tracker and the code-hosting provider have no such cap over the text they emit: GitLab's two named caps (`max_codeowners_bytes`, and the 1 MiB job-log tail) cover neither an MR description nor a discussion note, and Jira has none at all. **Jira's `MAX_COMMENTS = 100` is not a cap** — it is `maxResults`, a *request* parameter, and nothing refuses, truncates or marks a larger page: a scripted response of **200** comments is mapped whole. The figures are **produced by a shipped test rather than quoted here** (standing rule 39, after this entry's first version carried a wrong one): `packages/integrations/src/providers/unbounded-emission.test.ts` drives both adapters through their real registrations with 128 KiB in every provider-controlled string and asserts one `readTicket` at **53,284,565 bytes** across **8** unbounded paths (`title`, `description`, `issue_type`, `status`, `priority`, `labels[]`, `comments[].body`, `comments[].author.display_name`) and one `getMergeRequest` at **1,180,284** across **9** (`title`, `description`, `source_branch`, `target_branch`, `labels[]`, `author.display_name`, `web_url`, `ref.url`, `ref.branch`). That value goes into a context pack (WP-16) and an `integration_actions` row. Adding these two adapters to `emitted-bounds.test.ts` would therefore either pass **vacuously** — every string is under GitLab's 1 MiB job-log cap, which is not a bound on anything being measured — or require caps that do not exist. — *Recommendation (stated here rather than implemented, because the fix is a cap that changes what an agent reads):* **bound at the consumer, not in the adapter.** A tracker that truncated a ticket description would silently change what the agent reads and what the platform stores, and nothing downstream could tell a short ticket from a cut one; the places that know a budget are the context-pack builder (WP-16, which is packing to a token budget anyway) and the executor's audit write. The observability adapters are the exception that proves the rule: an error event and a log window are *samples*, where "the newest 25, 1 KiB each" is a sensible product answer, and a ticket is not a sample. Confirm, and decide three things: whether WP-16 owns the cap (and therefore whether `Ticket`/`MergeRequest` should carry a `truncated` marker so a pack can say what it cut); whether `integration_actions.payload` needs a hard byte ceiling of its own — today `describeResult` decides what is written and nothing bounds the row; and whether the comment page should be **paginated to a decided number** rather than asked for one and handed another.

**Q56 A project's custom stage cannot send a task back, because no bounded loop counts its rounds.** BD-008 bounds six return cycles by name (code review, business review, CI fixes, human rounds, refinement questions, architecture revisions) and product/04 S6b adds the rebase gate's two attempts; `IterationLoop` is that closed set. A custom stage (technical/12 `custom_stages` — the documented example is a `security_scan` gate with `fail_to: implementation`) has a transition target and **no counter**, so the platform can either count its rounds against somebody else's budget or refuse them. WP-15 could not defer it: the interpreter is total, and "what happens when this stage fails" is a branch it has to have. — *Recommendation (implemented in `packages/domain/src/pipeline/interpreter.ts`, `RETURN_LOOPS`):* **refuse, loudly.** A return the platform cannot count is an unbounded loop, and BD-008's whole claim is "nothing retries silently"; the task escalates with a blocker brief naming the stage, which is a bad outcome a human can fix rather than a spend nobody bounded. Borrowing `ci_fix`'s budget was rejected because two stages sharing one counter means a project that adds a security gate silently halves the CI loop it already had. Confirm, and decide which of two shapes the fix takes: a `loop` field on `customStageSchema` naming one of the existing cycles (cheap, and lets a project deliberately share a budget), or a per-stage `max_iterations` that creates a counter of its own (honest, and grows `tasks.iteration_counters` to a key set the platform does not know at compile time). The same decision covers the two loops that exist but are **not configurable** — `refinement_questions` and `architecture_revisions` have no key in `pipeline.limits`, which WP-02 flagged and WP-15 did not change.

**Q55 The binding redactor cannot know a run-scoped credential, so `GitProviderPort.getJobLog`'s deferred obligation is not dischargeable as written.** `packages/application/src/ports/integrations/git-provider.ts` says a run-scoped credential "is not known to the adapter, so the caller passes it in `ProviderCreateInput.redactor`". **The ordering makes that impossible for the credential that matters most.** `create()` runs once, when a binding is instantiated; `mintCredential()` runs later, per run, and the token it returns did not exist when the redactor was built. A `SecretRedactor` built at binding time is a closure over a fixed secret set (`exactSecretRedactor`), so a token minted afterwards is not in it — and it is exactly the token a CI job prints when it echoes the command it ran, which is the leak `getJobLog` names. The adapter cannot close it either, and deliberately: `gitlab/provider.ts` keeps minted credentials **out** of its binding redactor because `cloneUrl` and `mintCredential` must hand the value back intact, and because holding them would mean an unbounded, mutable secret set inside a long-lived adapter whose contents depend on which calls ran first. — *Recommendation (the **mechanism** implemented at WP-15a in `packages/integrations/src/bindings/loader.ts`; the gate's cut deliberately left where WP-15 put it):* **make the run the scope.** WP-15 composes a redactor per run, over the credentials that run holds, and either (a) hands the pipeline a **per-run adapter instance** built with it, or (b) changes `ProviderCreateInput.redactor` to a `() => SecretRedactor` resolved at call time so the composition root can return the current run's. (a) costs an adapter instance per run and keeps the type honest; (b) is cheaper and makes every adapter's redactor a moving target, which is harder to reason about at a review. Either way the *run transcript's* redactor (WP-12) already holds the same values, so the two should be built from one list rather than two. Until it is decided, the obligation stays deferred and the port says so by pointing here instead of implying a caller can discharge it today.

**Q50 TD-025 says the workspace's credential helper uses "the same Unix socket" as the runner's control connection, and the two halves of that sentence cannot both hold.** §1 says the shim "accepts exactly **one** authenticated control connection"; §3 says "the git credential helper inside the workspace talks to the shim over **the same Unix socket** (`cred.get`)". A helper connecting to `/ctl/ctl.sock` *is* a second connection, and the single-connection rule is not a nicety — it is the reason a compromised agent cannot drive `spawn`, because the runner takes the slot before the child exists. WP-13 could not defer it: `cred.get` is a named deliverable and the socket is where it arrives. — *Recommendation (implemented in `packages/infrastructure/src/runlet`):* **two sockets on the same per-run control directory.** `/ctl/ctl.sock` is the runner's, one authenticated connection ever, every later connection refused before a decoder is attached. `/ctl/cred.sock` is the workspace's, and it is **unauthenticated on purpose**: the helper runs as the same uid as the shim, so it can read the shim's environment, the token file on `/ctl` and in most configurations the shim's memory — a token there would authenticate nothing, and pretending otherwise would be standing rule 18's shape (a credential that is not one). The teeth are elsewhere: the credential socket accepts exactly `cred.get` and `ping` and refuses every other frame; a `cred.get` can name **one lowercase DNS host over https** and nothing else (cleartext has no representation in the schema at all); the shim generates the `request_id` the runner sees, so one helper cannot name another's pending question; requests are capped per run and per concurrency, and refused outright before `spawn` and from the moment the child exits — the last of those was **false when this entry was first written**, and the correction is the interesting part: the guard read `child === null`, which `spawn` makes untrue for ever, so a `cred.get` arriving between the child's exit and the shim's teardown (at least `stdioFlushMs`, and unbounded while a grandchild holds the stdout pipe open) was forwarded to the runner. The shim now reads the child's *exit status*, and a test drives the window with a child that outlives its own exit; and **the shim holds no allow-list and no credential** — the decision is the runner's, on the platform side of the volume, where the agent cannot read it. Confirm, and decide two things: whether TD-025 §3 should be amended to say "the same control **volume**, a second socket" (the neutral reading of its own design), and whether a run's git-host allow-list should *also* be enforced inside the shim as defence in depth, which would mean shipping the list into the container that is trying to get past it.

**Q51 The run container and the platform's runner container must agree on a uid, and nothing in the record says which.** TD-025 §2 has the runner connect to `/run/agentic/ctl/<run-id>/ctl.sock`, a socket the shim creates inside the run container; technical/05 pins the *run* container at `user: 1000:1000`; nothing pins the platform's. WP-13 creates the socket `0600`, which is the fail-closed choice and means the runner must connect as uid 1000 as well — verified working with both containers at 1000 (`research/12`). WP-13 could not defer it: a socket is created with *some* mode, and a wide one on a shared volume would let anything else on that volume drive the run. — *Recommendation (implemented as `0600`, with no option to widen it):* keep `0600` and make **"the runner process runs as uid 1000"** a constraint WP-14 satisfies, rather than adding a mode knob an operator can widen. The alternative is a shared gid with `0660`, which needs a `RUNLET_SOCKET_MODE` and is one typo away from `0666`. Confirm, and decide whether the launcher should assert the two uids match when it creates a run and fail loudly, instead of letting the mismatch surface as a connection refused.

**Q42 TD-024 names `@slack/bolt` and `@slack/web-api`, and both contradict structural constraints technical/06 records as binding.** TD-024 says "Slack uses the official `@slack/bolt` (Socket Mode) with `@slack/web-api`", while the same decision's rationale for handwriting the other four clients is that they are "fully covered by contract tests with recorded fixtures". Backoff, the rate-limit budget and the shadow guard live in `IntegrationActionExecutor`, which owns the injected timer; a retry loop inside a provider would be a second one running on a wall clock" — which is also standing rule 2. **(2)** `WebClient` exposes no transport seam: only an `agent` and `slackApiUrl`, so "contract suite in replay" would need a live HTTP listener instead of an injected `fetch`, and the assertion that a shadow-mode call issues *zero* requests would have nothing to observe. **(3)** Bolt's `App` owns its own dispatch (`app.event`, `app.action`), a second router beside TD-005's, and its signature verification lives in a receiver the platform does not use (it is on Fastify, TD-002). WP-10 could not defer it: the acceptance criterion is a contract suite, and the suite's transport is the decision. — *Recommendation (implemented in `packages/integrations/src/providers/slack`):* treat Slack like the other four — a thin in-repo `fetch` client over the five Web API methods the port needs, in-house `v0` signature verification with `timingSafeEqual` (which is what TD-024's own title says for webhook signatures), and a Socket Mode client whose WebSocket factory, timer and clock are injected, so reconnect backoff is testable and the envelope path is exercised without a workspace. Nothing about the design forecloses Bolt: `SocketConnect` is one function and `SlackFetch` is one function. Confirm, and decide whether TD-024 should be amended to say "handwritten thin clients on native fetch for **all five** providers" — the neutral reading of its own rationale — or whether the dependency is wanted for a reason the record does not state (Bolt's assistant/agent features, or its reconnection handling, are the two candidates).

**Q40 A git provider token cannot be scoped to a branch pattern, so what enforces `push:agentic/*`?** BD-025 and the `GitProvider` port describe a minted credential carrying `branchPatterns` — `push:agentic/*` — and WP-09 found that GitLab has no such thing: a project access token carries *scopes* (`read_repository`, `write_repository`) and a *role*, and nothing narrower. **Q41 Whether the SDK session mirror is redacted.** TD-012 enumerates the write paths redaction applies to — `run_messages`, `integration_actions`, `events.payload`, `config_audit`, artifacts and KB commits — and the Agent SDK's `sessionStore` mirror is not among them. WP-12 had to wire the mirror, so it could not defer the question: the mirror holds the session verbatim, including any credential a tool printed before the `PostToolUse` hook rewrote the model's copy. — *Recommendation (implemented in `packages/infrastructure/src/runner/session-mirror.ts`):* **the mirror is not redacted.** Its only consumer is `resume`, which replays it into the model's context, and a resumed run whose own earlier tool output has become `[REDACTED sha256:…]` has had its memory corrupted rather than protected — it would re-read a file it has already read, or re-run a command whose output it can no longer see. **Q37 Hazards the command block-list of `product/19` §3 states as one spelling each.** The list gives `rm -rf /*`, `git push --force*`, `git push origin :*`, `git branch -D *` and `curl * | sh` / `wget * | sh`. Every one of them is a hazard written as a single spelling, and the other spellings of the same hazard do not match the pattern: `rm -fr /`, `rm -r -f /`; `git branch --delete --force main`; `git push -f`, `git push … --delete` / `-d`, the force refspec `git push origin +agentic/x:main`, and the plain refspec `git push origin agentic/foo:main`, which writes `main` under an allow entry that names only `agentic/*`; and `curl http://x|sh`, `| bash`, `| /bin/sh`, `|&`, `wget -O- http://x|sh`. WP-02 declined to invent the missing patterns (security rules belong in the document, not in code the document does not state), named the gap in `DECLINED_BLOCK_VARIANTS`, and recorded that they all land on `ask`, never `allow`. **WP-02a disproved that last claim:** `git push origin agentic/x -f`, `git push origin agentic/x --delete` and `git push origin agentic/foo:main` all returned **allow**, because the allow entry `git push origin agentic/*` was carrying them, and the `curl|sh` spellings returned `ask` rather than `block`. The line the code now draws: a missing spelling that only decides between `ask` and `block` stays the document's to fix — the command can never reach `allow`, so the code is not what is keeping it out; a missing spelling reachable from the **allow**-list is closed in code, because the allow-list is the one thing the module defends. So `git push -f*`, `git push --delete*`, `git push -d*` and `git push origin +*` joined the block list, the refspec form floors at `ask`, and the `curl|sh` family is caught by normalising a pipeline's spacing and spelling any shell stage `sh`; `rm -fr /` and `git branch --delete --force main` are unchanged and still `ask`. — *Recommendation:* amend product/19 §3 to state the hazards rather than one spelling of each — `rm` with any recursive flag outside the workspace; branch deletion in either form; force-pushing, deleting or retargeting a remote ref in any spelling, refspecs included; piping a download into any shell — so that the document and the code say the same thing. Two further items on that list (`any command writing outside the workspace`, `network calls to non-allow-listed hosts`) cannot be a command pattern at all and are enforced by the run container and the egress proxy (TD-021); they are recorded in `UNPATTERNABLE_BLOCK_ITEMS`. WP-02a also found that this module's approximation of the first of those two — flooring a `> file` redirection at `ask` — is walked around by flags that write a path directly (`git diff --output=`, `git log --output=`, GNU `find -fprintf` / `-fls`, all verified against the real tools); they are now floored by `HAZARDOUS_ARGUMENTS`, along with `pip install --target/--root/--prefix/--log/--report`. A second review round added two more families to the same list: `git difftool --extcmd`, and `git log --ext-diff` / `git show --textconv`, which run whatever the *repository's own* config names and so are untrusted input under BD-022.
