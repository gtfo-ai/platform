- [ ] A provider can **forge** the `agentic.truncation` marker — WP-16. It is a Sentry tag, a Loki stream label and a breadcrumb category, all namespaces the provider writes, so an application that tags its own events with it produces an answer claiming a cap fired when none did (WP-11a review round 1, confirmed reachable, judged non-blocking). A real truncation overwrites the forged value, so completeness cannot be faked and every cap still holds; what it buys is a false "truncated" claim plus platform-looking text inside a prompt. It is WP-16's because the harm is in the **context pack**: whatever assembles a pack must render provider text as provider text and must not read a marker key as the platform's own voice. Closing it in the adapters would mean stripping the key out of provider data first, a second rule about provider-chosen keys in a place that already has one (technical/06 § ObservabilityLogs).

- [ ] `apps/server`'s error handler logs an unexpected error as `{ err }` (`app.ts`), and `pino-std-serializers` emits the message and stack with the **whole** cause chain appended, an `AggregateError`'s `errors[]`, and a copy of every key `for…in` reaches. Errors that pass through `IntegrationActionExecutor` are scrubbed over exactly those routes before they leave it (round 2; asserted against the real serialiser in `apps/server/src/logging.test.ts`), but an adapter that throws *outside* the executor — a `testConnection` probe, a poll — is not covered at all — **WP-15**/WP-08 when the first such call site exists. **WP-08 claimed to have closed this for `jira-cloud` "by having no such path"; review round 1 found the claim false and round 2 made it true.** `transition` resolved the target status *after* its `resolve_transition` action had returned and then threw `no transition to "…"; available from "Ready for agent": "In Progress", "In Review"` — provider text, outside the choke point, straight past the scrub.
